# 손익분기를 넘는 파일에만 unified diff를 쓴다

## 요약

파일을 부분 수정할 때 **unified diff로 내는 것이 무조건 짧지 않다.** 승패는 파일 줄 수 `N`이 결정한다.

```
N  >  N*     →  diff 를 낸다
N  ≤  N*     →  파일 전체를 다시 낸다

N* ≈ 2m + C + k + 2      (m=변경 줄 수, C=방출될 컨텍스트 줄 수, k=hunk 수)
```

경험칙 `(라운드1·2 실측, proxy)`:

| 컨텍스트 | 실측 `N*` | 안전 권장 |
|---|---|---|
| 3줄 (`git diff` 기본값) | **38~40줄** | `N ≥ 60`에서 diff |
| 1줄 | **26~28줄** | `N ≥ 45`에서 diff |

30줄 YAML에서 컨텍스트 3줄 diff는 전체 재출력보다 **+25.6% 길었고**, 같은 변경 형상의 120줄 YAML에서는 **−66.7% 짧았다** `(proxy)`. 부호가 뒤집힌다.

**이 기법은 "diff를 써라"가 아니다.** 조건 없이 diff를 강제하면 짧은 파일에서 출력이 늘어난다 — 라운드 1이 그 기각 결과다.

## 적용법

### 1. 판정

수정 대상 파일의 줄 수 `N`을 센다. 위 표의 `N*`와 비교한다. **경계에서 3~5줄 안쪽이면 전체 재출력을 고른다** — 손익분기 근처에서 diff의 우위는 hunk 하나 갈리는 것만으로 사라진다(§한계).

### 2. 프롬프트 (조건부로 싣는다)

```
수정 내용을 unified diff 로 낸다.
파일 헤더는 `--- a/<path>` / `+++ b/<path>` 로 하고,
원본에 `git apply -p1` 로 적용 가능해야 한다.
각 hunk 의 컨텍스트 줄은 변경 줄 위아래 1줄씩으로 한다.
```

마지막 줄(컨텍스트 1줄)은 `N*`를 38~40줄에서 26~28줄로 내린다. **컨텍스트 0줄은 지시하지 않는다** — 표준 `git apply -p1`이 거부하고 `--unidiff-zero`가 필요하다 `(라운드1 실측)`.

### 3. 지시를 어디에 싣는가 (중요)

이 지시는 조건 A 대비 프롬프트를 **+67자(C=3) / +147자(C=1)** 늘린다 `(proxy)`.

| 파일 크기 | 출력 감소 | 입력 증가 | 순효과 |
|---|---|---|---|
| N=120, C=3 | −1646자 | +66자 | **압도적 이득** |
| N=30, C=1 | −34.5자 | +147자 | **문자 기준 순손실** (요청당 지시를 실을 때) |

→ 요청마다 지시를 새로 싣는 구조라면 **큰 파일에만 조건부로 붙인다.** 시스템 프롬프트에 상주시켜 캐시하면 입력 비용이 상각되지만, 그때는 짧은 파일에서 diff가 강제되지 않도록 조건문을 함께 넣어야 한다.

### 4. 방출 형식의 무료 절감

`git diff`가 붙이는 hunk 헤더 꼬리표(`@@ -13,11 +13,11 @@ healthcheck:`)는 unified diff 규격의 **선택 필드**이고 `git apply`·`patch`가 무시한다. 생략하면 적용성 손실 없이 `git diff` 대비 **−2.7% ~ −8.9%** `(라운드2 실측, proxy)`. 모델은 지시하지 않아도 대체로 생략한다 — 8시행 중 7시행. 굳이 요구할 필요는 없되, 기준선을 `git diff`로 잡으면 이 차이가 오버헤드 음수로 오측정된다.

## 경계 — 받는 쪽이 에이전트라면 컨텍스트는 잉여다 (라운드 5)

같은 재료(120줄, 6곳 수정)를 압축 5단으로 내고, 각 산출물을 **다른 naive 에이전트**에게 원본과 함께 넘겨 적용시켰다.

| 조건 | 형식 | `L_file` | 압축률 | 에이전트 복원 |
|---|---|---|---|---|
| W0 | 전체 재출력 | 2,469 | — | 2/2 |
| W1 | diff C=3 | 823 | 66.7% | 2/2 |
| W2 | diff C=1 | 533 | 78.4% | 2/2 |
| W3 | diff C=0 | 298 | 87.9% | **2/2** |
| W4 | 줄번호 + 치환쌍 | **217** | **91.2%** | **2/2** |

`(라운드5 실측, proxy, 조건당 n=2, 조건 내 분산 0)`

**한계 8("컨텍스트 0줄로 더 내려가면 안 된다")은 소비자 조건부로 정정한다.** `git apply -p1`이 C=0을 거부하는 것은 사실이고 이번 1차 에이전트 두 곳이 직접 재확인했다(`--unidiff-zero` 필요). 그러나 **같은 파일을 에이전트가 받으면 2/2가 정확히 적용한다.** 왜곡은 압축률의 함수가 아니라 **복호기의 함수**다.

- 받는 쪽이 **스크립트·CI**: C=1까지. 여기서 더 내려가면 표준 옵션으로 거부된다
- 받는 쪽이 **에이전트**: 줄번호+치환쌍까지. C=3 대비 **−73.6%**, 결과는 동일

**단 왕복까지 보면 C=0은 쓰지 않는다.** 1차 + 2차 보고문 합계가 C=1에서 1,198자로 최저였다가 C=0에서 1,229자로 올라간다 — 소비자가 해석 절차를 설명하느라 더 쓴다. 줄번호+치환쌍(1,102자)은 형식이 명시적이라 다시 내려간다. **가장 비싼 것은 가장 짧은 형식이 아니라 가장 모호한 형식이다.**

## 한계

1. **문자 수는 토큰이 아니다.** −66.7%는 `chars` proxy이며 토큰 절감률은 미측정이다. 이 환경에 `usage.output_tokens`가 없어 원리적으로 확인 불가.
2. **`N*`는 구간이지 값이 아니다.** `N`을 30과 120 두 점만 잡았다. 부호 역전의 **존재**는 보였으나 교차 지점은 구간으로만 말할 수 있다.
3. **`N* ≈ 2m + C + k + 2`는 사후 검산용이지 사전 예측기가 아니다.** 8/8 시행에서 방출된 diff의 줄 수와 정확히 일치했지만, `C`와 `k`가 diff 알고리즘의 **출력**이지 입력이 아니다. `C_total = 2ck`로 미리 대입하면 `N*`를 7.6~18.1% **과소추정**한다 — hunk 병합이 `2ck`를 넘는 컨텍스트를 끌어들이고, `k` 자체가 `C`에 의존해 변하기 때문(F120: C=3→k=3, C=1→k=**5**). C=1·N=30에서 예측 절감 −23% 대 실측 −6.8%로 **3.4배 과대**였다.
4. **N≈30, C=1의 −6.8%는 칼날 위 결과다.** 마진 34.5자는 hunk가 하나 더 갈리거나(약 +18자) 변경이 파일 중앙으로 옮겨져 경계 절단이 사라지면(약 +34자) 소진된다. 라운드 1은 같은 파일에서 `c=2`가 **+4%(패배)**임을 계산으로 보였다. **N≈30을 안전 권장 구간에 넣지 않는 이유가 이것이다.**
5. **`m`, `k`가 다른 경우로 외삽할 수 없다.** `m=6`, 3덩어리 형상만 시험했다. 변경이 흩어질수록(`k` 증가) `N*`가 올라가 diff가 불리해진다 — 방향은 예측되지만 크기는 미측정.
6. **YAML 외 형식은 미검증.** `N*`의 근사가 성립한 것은 hunk 헤더 폭이 줄당 평균 폭과 비슷했기 때문(`w`=17.0~20.6). 줄이 긴 언어(Python·TypeScript)는 `N*`가 내려가 diff가 **더** 유리해질 것으로 예측되나 미측정.
7. **`q`(적용 실패율)를 0이라고 주장하지 않는다.** n=4에서 `q`의 해상도는 0.25다. 관측된 것은 "8/8 성공"이며, 고유 앵커만 있는 짧은 합성 YAML에서의 값이다. 실제 코드베이스의 diff 적용 실패율은 이보다 확실히 높다.
8. **컨텍스트 0줄로 더 내려가면 안 된다.** −46%로 더 짧지만 표준 `git apply -p1`이 거부한다 `(라운드1 실측)`. C=1과 C=0 사이 어딘가에 문턱이 있고 그 위치는 미측정이다.
9. **합성 과제다.** 실제 코딩 에이전트 워크플로에서의 절감은 측정되지 않았다.
