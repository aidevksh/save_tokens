# 표 형태 페이로드는 전체 키 JSON 대신 헤더 TSV로 받는다

## 요약

동일 레코드 집합을 **레코드마다 키를 반복하는 JSON 객체 배열**로 받는 대신 **헤더 1줄 + 행 N줄의 TSV**로 받으면 산출물 문자 수가 크게 줄고, 이번 측정에서 셀 정확도 손실은 없었다.

절감의 출처는 명확하다: JSON 객체 배열은 **키 이름을 레코드 수만큼 반복**한다. 이번 과제(12레코드 × 8필드)에서 JSON 초과분 1297자 중 **1032자(79.6%)가 반복된 키 이름·따옴표·콜론**이었고, TSV는 그것을 62자짜리 헤더 1줄로 대체한다. 따라서 **절감폭은 레코드 수에 비례해 커지고, 필드 값이 길어질수록 상대적으로 작아진다.**

## 적용법

레코드 수 ≥ 약 5, 필드가 고정 스키마, 값에 탭·줄바꿈이 없는 표 형태 페이로드에 적용한다.

프롬프트의 출력 형식 지정을 다음처럼 바꾼다 (실측에 사용한 문구 그대로):

```
출력 형식: 결과를 TSV로 <경로> 에 저장하세요. 첫 줄은 헤더이고, 그 아래 레코드 1건당 1줄씩
총 N줄입니다. 헤더와 데이터 행 모두 열 구분자는 탭 문자 1개이며 열 순서는 다음과 같습니다.
<필드1>, <필드2>, ...
```

- **열 순서를 명시한다.** 헤더만 요구하면 순서가 흔들려 후처리가 깨진다.
- **행 수를 명시한다** (`총 N줄`). 누락 검출이 파싱 단계에서 가능해진다.
- 값 대응표(enum 허용값)는 JSON 조건과 동일하게 유지한다. 형식만 바꾸고 어휘는 바꾸지 않는다.
- 이 처치는 **출력 형식 지정 문단만** 바꾸므로 프롬프트 나머지와 직교한다.

**적용하면 안 되는 경우**
- 중첩 구조·가변 필드·배열 값이 있는 페이로드 (TSV로 표현 불가)
- 값에 탭이나 줄바꿈이 포함될 수 있는 경우 (이스케이프 규약이 필요해지고 그 순간 이점이 사라진다)
- 레코드가 1~2건 (헤더 고정비가 절감을 잡아먹는다)
- 소비자가 JSON 스키마 검증을 요구하는 경우

## 한계

1. **문자 수는 토큰이 아니다. −65.9%는 토큰 절감률의 상한으로 읽어야 한다.** 어긋나는 이유가 최소 세 개이고 전부 같은 방향(과대평가)을 가리킨다: (a) JSON의 반복 키(`"ticket_id": `)는 코퍼스에 흔해 소수 토큰으로 병합될 가능성이 높다, (b) TSV의 탭 91개는 `chars_nows`에서 0으로 계산되지만 토큰으로는 0이 아니다, (c) 탭으로 끊긴 짧은 토막의 나열은 문자당 토큰 수가 올라갈 수 있다. 실제 토큰 절감률은 `usage.output_tokens` 없이 **원리적으로 확인 불가**다.
2. **절감률을 다른 형상에 그대로 옮길 수 없다.** 절감의 79.6%가 반복 키에서 나오므로, 레코드가 적거나 필드 값이 길면 절감률이 급격히 낮아진다. 레코드 수 종속성은 미측정(축2 H8, 라운드 2 이월).
3. **조건 내 분산 0 = 반복 없음.** n=4로 적었지만 4개 산출물이 바이트 동일하므로 통계적 검정력은 n=1과 같다. 얻은 것은 "이 프롬프트에서 출력이 결정적"이라는 사실뿐이며, 좁은 재현성을 넓은 외적 타당도로 오독하면 안 된다.
4. **thinking 토큰 미측정.** 산출물 파일만 쟀다. TSV로 표를 짜맞추는 사고량이 JSON보다 많았다면 이 수치는 절감을 과대평가한다. 확인 수단은 `usage.output_tokens_details.thinking_tokens` 뿐이다.
5. **오염 조건 병기.** 조건 A·B 모두 이 저장소 `CLAUDE.md`의 억제 규칙이 걸린 Claude Code 세션에서 측정했다. 다만 조작 변수(직렬화 형식)가 그 규칙과 직교하고 지시 위반이 0건이라 차분은 유효하다고 판단했다. 일반 API 사용자 환경으로의 외삽은 미검증.
6. **모델 세대 간 이식 불가.** 토크나이저 세대 차 때문에 다른 세대와 문자 수 비율을 직접 비교하지 않는다.
7. **마크다운 표와의 비교는 미측정.** "TSV가 JSON보다 짧다"만 확인했고 "TSV가 최선"은 확인하지 않았다(축2 H6, 라운드 2 이월).
