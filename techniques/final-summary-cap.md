# 마지막 보고에 줄 수 상한을 준다

## 요약

코딩 에이전트에게 작업을 시킬 때 **`마지막 보고는 무엇을 바꿨는지 세 줄 이내로 씁니다.`** 한 줄을 넣는다. 대화 보고문이 **−48.6%**, 코드 변경분은 그대로(+0.3%), **총출력 −17.4%**. 테스트 통과율 9/9 유지.

**이 저장소에서 총량을 실제로 줄인 첫 억제 지시다.** 앞선 두 시도(자기검증 지시 제거, 입력 재진술 금지)는 한쪽에서 아낀 만큼 다른 쪽이 늘어 총합이 동률이었다.

## 적용법

과제 명세 뒤, 꼬리 지시 앞에 한 줄로 넣는다. 실측에 사용한 문구 그대로:

```
마지막 보고는 무엇을 바꿨는지 세 줄 이내로 씁니다.
```

**왜 이 문구인가.** 세 요소가 다 필요하다.

| 요소 | 역할 |
|---|---|
| `마지막 보고는` | 대상을 대화 보고문으로 한정한다. 코드나 파일에는 걸지 않는다 |
| `무엇을 바꿨는지` | 무엇을 남길지 지정한다. 이게 없으면 줄 수를 맞추려고 필요한 정보를 버린다 |
| `세 줄 이내로` | **분량을 직접 지시한다.** 이 부분이 절감을 만든다 |

**내용 규칙으로 바꾸지 않는다.** "장황하게 쓰지 마세요"·"입력에 있는 건 다시 쓰지 마세요" 같은 내용 규칙은 이 저장소에서 두 번 총합을 못 줄였다(라운드 3 −0.4%, 라운드 4 −2.0%). 듣는 것은 **분량 규칙**이다.

**줄 수는 과제에 맞춘다.** 세 줄은 "함수 하나 추가 + export 등록" 규모에서 정한 값이다. 변경 지점이 많으면 늘린다 — 실측에서 세 줄 조건의 산출물은 바꾼 것 세 가지를 정확히 한 줄씩 담았다.

## 한계

1. **문자 수는 토큰이 아니다.** −48.6%는 proxy이며 `usage.output_tokens` 없이는 확인 불가.
2. **코드 변경분은 파일에 남은 것만 센다.** 파일을 읽고 고치는 도구 호출 인자는 계측 밖이다. 실제 총출력에서 보고문이 차지하는 비중은 위 계산보다 작고, 따라서 **총출력 −17.4%는 상한**이다.
3. **품질은 테스트 통과로만 확인했다.** 세 줄 보고가 사람의 코드 리뷰나 나중의 이력 추적에 충분한지는 재지 않았다. **보고가 로그가 아니라 인수인계일 때는 다시 판단한다.**
4. **기준 조건이 이미 오염돼 있다 → −48.6%는 하한.** 피험자가 저장소 `CLAUDE.md`의 억제 규칙을 물고 시작한다.
5. **다른 억제 지시와 함께 걸면 합만큼 나오지 않는다.** 같은 라운드에서 세 지시 묶음이 개별 절감 합의 **64.6%**에 그쳤다(A5-H7 하위가산성). 이 −17.4%를 다른 기법의 절감률에 그대로 더하지 않는다.
6. 과제 1종(JS 기능 추가), 규모 1종(41줄 모듈)에서만 쟀다. 변경 지점이 많은 과제로의 외삽은 미검증.
