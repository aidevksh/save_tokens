## 2. 기법별 비용 모델 (수식 + 손익분기 조건)

### 공통 변수

| 기호 | 의미 |
|---|---|
| `N` | 요청 수 |
| `O_m` | 모델 `m`의 요청당 평균 **출력** 토큰 |
| `p_m` | 모델 `m`의 출력 토큰 단가 |
| `T` | 시스템 전체 출력 토큰 총합 |
| `C` | 출력 토큰 비용 총합 |

---

### 2.1 모델 라우팅

**baseline** — 전량 Opus:
```
T_base = N · O_o
C_base = N · O_o · p_o
```

**개선** — 비율 `f`를 저가 모델(h)로, 라우터가 요청당 `O_r` 출력 토큰 소비, 저가 라우팅 중 비율 `ε`가 오분류로 Opus 재실행:
```
T_route = N·O_r + N·f·(O_h + ε·O_o) + N·(1−f)·O_o
C_route = N·O_r·p_r + N·f·(O_h·p_h + ε·O_o·p_o) + N·(1−f)·O_o·p_o
```

**손익분기 (토큰):**
```
O_r  <  f · ( O_o·(1−ε) − O_h )
```
**손익분기 (비용):**
```
O_r·p_r  <  f · ( O_o·p_o·(1−ε) − O_h·p_h )
```

**필요조건 (라우터가 공짜여도 만족해야 함):**
```
토큰: ε < 1 − O_h/O_o
비용: ε < 1 − (O_h·p_h)/(O_o·p_o)
```

**해석 — 세 가지 임계:**
1. **라우터 판정 비용 `O_r`가 핵심.** 라우터가 LLM이면 `O_r > 0`이고, `f`가 작을수록 임계가 가혹해진다(`O_r < f·(...)`). 라우터를 **결정적 코드/정규식/임베딩 분류기**로 만들면 `O_r = 0`이 되어 조건이 필요조건만 남는다.
2. LLM 라우터를 써야 한다면 **구조화 출력 enum**으로 `O_r`을 수 토큰 수준까지 눌러야 한다.
3. `ε`(오분류율)는 **저가 모델의 상대 출력 효율에 의해 상한이 정해진다.** Haiku가 Opus와 비슷한 길이로 답한다면(`O_h ≈ O_o`) 토큰 기준 임계는 `ε < 0`, 즉 **토큰으로는 절대 이득이 없고 비용으로만 이득**이다. 비용 기준 임계는 단가비 5:1을 반영해 `ε < 1 − O_h/(5·O_o)`.

> **중요:** 라우팅의 이득은 대부분 **토큰 수가 아니라 단가**에서 나온다. 이 축의 지표를 "출력 토큰 총합"으로 잡으면 라우팅은 `O_h < O_o`인 만큼만 이득이고, `O_r`이 그것을 잠식한다.

### 2.2 부분 재생성 (변경분만 재생성)

`K`회 수정, 산출물 전체 길이 `L`, 변경 조각 길이 `L_Δ`, 주소지정 오버헤드(앵커·컨텍스트 라인·diff 헤더) `H`, 패치 적용 실패율 `q`(실패 시 전체 재생성 폴백):

```
T_base = K · L
T_part = K · [ (1−q)·(L_Δ + H) + q·(L_Δ + H + L) ]
       = K · ( L_Δ + H + q·L )
```

**손익분기:**
```
(L_Δ + H) / L  <  1 − q
```

**해석:** 좌변은 **"변경 비율 + 오버헤드 비율"**, 우변은 **패치 성공률**. 즉

- 변경 비율이 크면(리팩터링급) 이득 없음.
- 패치 성공률 `q`가 낮은 형식(모호한 앵커, 중복 문자열)에서는 `L_Δ`가 아무리 작아도 폴백 비용이 잠식.
- `H`는 형식이 결정한다. unified diff는 `H`가 크고, 라인 번호 기반 치환은 작지만 `q`가 크다. → **형식 선택이 손익분기점을 이동시킨다.**

### 2.3 결과 캐싱 / 중복 요청 제거

히트율 `h`, 조회 판정에 드는 출력 토큰 `k`, 오탐(잘못된 캐시 히트)율 `φ`, 정정 비용 `c`:

```
T_base  = N · O
T_cache = N · [ (1−h)·O + k + h·φ·(O + c) ]
```

**손익분기:**
```
k  <  h · [ O·(1−φ) − φ·c ]
```

**해석:**
- **정확 매칭 캐시(해시 키, 코드에서 조회)**: `k = 0`, `φ = 0` → **무조건 이득**, 크기는 `h·O`.
- **시맨틱 캐시(LLM/임베딩 판정)**: `k > 0`, `φ > 0`. 오탐 정정 비용 `c`가 `O`보다 크면(잘못된 답을 되돌리는 대화가 원래 답보다 길면) 우변이 음수가 되어 **어떤 히트율에서도 손해**.
- 필요조건: `φ < O/(O+c)`.

### 2.4 Programmatic Tool Calling (PTC)

자연어 도구 호출 baseline — `R` 라운드, 라운드당 도구 인자 `a` + 서술/전이 텍스트 `n`, 최종 답변 `A`:
```
T_base = R·(a + n) + A
```

PTC — 스크립트 작성 `S`, 스크립트 오류 재작성 기대 횟수 `ρ`:
```
T_ptc = S·(1 + ρ) + A
```

**손익분기:**
```
R  >  S·(1 + ρ) / (a + n)
```

**해석:**
- **라운드 수 `R`이 임계 라운드 수를 넘을 때만 이득.** 단발 도구 호출(`R=1`)에서는 스크립트 작성이 순손해.
- `S`는 도구 개수·스키마 복잡도에 따라 증가 → 도구가 많을수록 임계 `R`이 올라간다.
- `ρ`(스크립트 디버깅 루프)가 이 기법의 숨은 비용. 컨테이너 오류 → 재작성 → 재실행은 각각 `S`만큼의 출력을 다시 낸다.
- **2차 효과(문서화된 부분):** 중간 결과가 컨텍스트에 안 들어오므로 **후속 턴에서 모델이 그것을 서술·요약할 필요가 사라진다.** 위 식의 `n`이 후속 턴에서 0이 되는 효과 — 실측 −37%(총 토큰)의 상당 부분이 여기서 나올 가능성이 있으나 출력 토큰 분해값은 **측정 필요**.

### 2.5 도구로 계산·집계·필터링 (모델 서술 대체)

모델이 데이터를 재진술하며 계산하는 baseline — 재진술량 `D`(데이터 크기에 비례), 최종 답 `A`:
```
T_base = D + A
T_tool = q + A          (q = 도구 호출 인자 길이, 데이터 크기와 무관)
```

**손익분기:**
```
q < D
```

**해석:** `D`는 데이터 크기 `n`에 대해 `O(n)`, `q`는 `O(1)`. → **데이터가 커질수록 무조건 이득**이며, 손익분기는 `n`이 아주 작을 때만 문제가 된다.
**단, 예외 조건:** 산출물 자체가 열거/표라면 `A ≈ D`이므로 이득이 사라진다. 즉 **"계산 결과만 필요한가, 데이터 자체가 산출물인가"**가 판정 기준.

### 2.6 Batch API

```
T_batch = T_sync          (총 출력 토큰 불변)
C_batch = 0.5 · C_sync
```

**손익분기:** 토큰 기준 **손익분기 자체가 존재하지 않음**(효과 0). 비용 기준은 무조건 이득이나 다음 조건이 전제:

```
지연 허용 ≥ 24시간  ∧  요청 간 순차 의존 없음  ∧  동기 재요청 없음
```

**반전 조건:** 배치 결과를 기다리지 못해 동일 요청을 동기로도 보내면
```
T = 2·T_sync ,  C = 1.5·C_sync
```
→ **토큰 2배, 비용 1.5배**로 순손해.

### 2.7 멀티에이전트 (오케스트레이터 + k개 서브에이전트)

단일 에이전트가 `M`개 문서를 읽고 보고서 작성:
```
T_single = O_narr + O_report + γ·O_compact
```
- `O_narr`: 문서를 읽으며 내는 중간 서술/메모
- `γ`: 컨텍스트 초과로 인한 압축(compaction)/재독 사이클 횟수, `O_compact`: 1회 비용

멀티에이전트:
```
T_multi = O_plan + k·O_brief + Σ_{i=1..k} O_sub,i + O_synth
```
- `O_plan`: 오케스트레이터의 계획 서술
- `O_brief`: 서브에이전트 1개당 **재브리핑(task 명세) 출력 토큰** ← 이 축의 핵심 항
- `O_sub,i`: 서브에이전트 `i`의 보고서
- `O_synth`: 종합 출력

**손익분기:**
```
O_plan + k·(O_brief + O_sub) + O_synth  <  O_narr + O_report + γ·O_compact
```

문서당으로 정규화(`k = M`, 문서당 단일 에이전트 서술 `o_narr = O_narr/M`)하면:
```
O_brief + O_sub  <  o_narr + (γ·O_compact + O_report − O_synth − O_plan)/k
```

**해석 — 두 가지 서로 다른 이득 원천:**

1. **압축(compression) 이득:** `O_sub < o_narr`. 서브에이전트가 긴 원문을 읽고 짧게 보고하면 문서당 서술이 줄어든다. 그러나 **`O_brief`가 이것을 상쇄한다.** 손익은 `k`와 무관하게 `(O_brief + O_sub) vs o_narr` 비율만으로 결정 — **에이전트를 늘려도 비율은 개선되지 않는다.**
2. **컨텍스트 초과 회피 이득:** `γ·O_compact` 항. 단일 에이전트가 컨텍스트를 채워 압축 루프를 도는 경우에만 발생. `γ = 0`이면 이 항은 사라지고 **1번 이득만 남으며, 그것은 대개 음수**다.

**따라서 멀티에이전트가 총 출력을 줄이는 조건은 사실상:**
```
γ > 0  (단일 에이전트가 컨텍스트 압축 루프에 진입)
   ∧  γ·O_compact > O_plan + k·O_brief + (Σ O_sub − O_narr) + (O_synth − O_report)
```

문서화된 실측(멀티 ≈ 채팅 15배 vs 단일 ≈ 4배, 즉 **3.75배**)은 이 조건이 **일반적으로 만족되지 않는다**는 강한 경험적 증거다.

**서브에이전트를 저가 모델로 돌리는 변형(권장 패턴):**
```
C_multi = (O_plan + k·O_brief + O_synth)·p_o + Σ O_sub,i · p_h
```
→ **토큰 총합은 여전히 증가하지만 비용은 감소할 수 있다.** 손익분기:
```
(O_plan + k·O_brief + O_synth − O_report)·p_o  <  (O_narr·p_o − Σ O_sub,i·p_h)
```
출력 단가비 `p_o/p_h = 5`이므로, 읽기 위주 서브태스크에서 이 조건은 토큰 조건보다 **훨씬 느슨하다.** → **멀티에이전트는 "토큰 절감 기법"이 아니라 "비용 재배분 기법"으로 분류하는 것이 정확하다.**

### 2.8 재시도 / 자기수정 루프 제거

실패율 `P_f`, 재시도 시 동일 비용 `O` 가정:
```
T_base = O · Σ_{j≥0} P_f^j = O / (1 − P_f)
```

실패를 **파싱 실패 `P_parse`**와 **의미 실패 `P_sem`**로 분해(`P_f = P_parse + P_sem − P_parse·P_sem`):

구조화 출력 적용 후 `P_parse → 0`:
```
T_so = O / (1 − P_sem)
```

**손익분기 (출력 토큰):**
```
P_parse > 0  이면 항상 이득.  절감량 = O·[ 1/(1−P_f) − 1/(1−P_sem) ]
```
출력 토큰 기준으로는 **단조 개선**이며 손익분기점이 없다. 대가는 다른 축에서 발생:
- 입력 토큰 증가(형식 설명 시스템 프롬프트 자동 주입)
- `output_config.format` 변경 시 해당 스레드 prompt cache 무효화
- 최초 스키마 사용 시 문법 컴파일 지연(24시간 캐시)

**반전 조건:** `max_tokens` 도달로 JSON이 중간에 잘리면 스키마 준수 여부와 무관하게 **전량 재시도**가 필요하다. 즉
```
P_truncate > 0 이면  T = O/(1 − P_sem − P_truncate)
```
스키마가 장황할수록(중첩 객체, 긴 enum, 서술형 필드) `P_truncate`가 커진다 → **스키마 설계가 손익을 되돌릴 수 있다.**

**자기수정 루프의 별개 항:** "답을 다시 확인하라" 류 지시는 검증 턴 `V`를 `v`회 유발한다.
```
T = O/(1−P_f) + v·V
```
Opus 5는 지시 없이도 자체 검증하므로 이 지시는 **`v`만 늘리고 `P_f`는 줄이지 않는다**(§1.9). → 삭제가 순이득.

## 4. 실험 프로토콜 / 필요한 실측 파라미터

### 4.1 `[proxy 검증 가능]` 실험 설계 (naive 서브에이전트, API 호출 없음)

공통 규칙 (CLAUDE.md 측정 제약 준수):

- 피험 에이전트에게 **토큰 절감 실험임을 절대 알리지 않는다.** 프롬프트에 "간결", "짧게", "토큰", "효율" 어휘 금지.
- 모든 조건에서 **출력 언어를 한국어로 고정**한다(문자↔토큰 비율 보존).
- 측정 단위: **산출물 문자 수 / 줄 수 (proxy)**. 절대 토큰 수로 보고 금지. **조건 간 상대 비율로만** 보고.
- 시행 횟수 `n ≥ 3` (조건당). 중앙값과 범위를 함께 기록.
- **오케스트레이터가 서브에이전트에게 보낸 task 프롬프트 문자 수도 산출물에 포함한다.** ← 이 실험의 핵심. 이것을 빼면 결론이 뒤집힌다.
- 원시 결과는 `experiments/04-*/raw/` 에 조건·시행별 파일로 저장.

---

#### 실험 E1 — 멀티에이전트 총 산출물 (H4, H5)

**목적:** 서브에이전트 팬아웃이 총 출력(proxy)을 늘리는지 줄이는지, 그리고 `k`에 따라 부호가 바뀌는지 판정.

**재료 준비 (실험 운영자가 사전 수행, 피험자는 관여 안 함)**
1. 길이가 유사한(±20%) 장문 기술 문서 3개를 로컬 파일로 저장. 예: `platform.claude.com/docs` 3개 페이지의 `.md` 를 WebFetch로 받아 `experiments/04-multiagent/docs/{A,B,C}.md` 로 저장.
2. 각 문서의 문자 수를 기록(교란 통제용).

**공통 산출물 명세 (모든 조건에 동일하게 제시)**
```
세 문서를 읽고 다음 형식의 통합 보고서를 한국어로 작성하라.
1. 각 문서의 핵심 주장 (문서별 1개 문단)
2. 문서 간 공통점
3. 문서 간 상충하거나 다른 관점
4. 종합 결론
```

**조건 A — 단일 에이전트 (baseline)**
- naive 서브에이전트 1개 기동.
- 프롬프트: 문서 3개 경로 + 위 산출물 명세.
- 측정: `chars(최종 보고서)`. (도구 호출 인자·읽기 과정 서술은 대화 로그에서 분리 가능한 만큼만 별도 기록.)

**조건 B — 팬아웃 k=3**
- 오케스트레이터 역할 서브에이전트 1개를 기동하되, **"서브에이전트 3개에게 각각 문서 1개씩 맡기고 그 결과를 종합하라"**는 절차만 지시(효율 언급 없음).
- 측정 항목을 **분해해서** 기록:
  | 항목 | 기호 | 측정 대상 |
  |---|---|---|
  | 오케스트레이터 계획 서술 | `O_plan` | 위임 전 계획 텍스트 문자 수 |
  | 서브에이전트 브리핑 | `O_brief × 3` | 각 서브에이전트에게 보낸 task 프롬프트 문자 수 |
  | 서브에이전트 보고 | `O_sub × 3` | 각 서브에이전트 최종 산출물 문자 수 |
  | 종합 | `O_synth` | 최종 통합 보고서 문자 수 |

**조건 C — 팬아웃 k=1** (H5 검증용)
- 서브에이전트 1개에게 문서 3개 전부 위임 → 오케스트레이터가 종합.
- 동일 항목 분해 측정.

**판정 규칙**
```
R_B = (O_plan + 3·O_brief + 3·O_sub + O_synth) / chars(조건 A 최종 보고서)
R_C = (O_plan + 1·O_brief + 1·O_sub + O_synth) / chars(조건 A 최종 보고서)

H4 지지:  R_B > 1  (팬아웃이 총 산출물을 늘림)
H5 지지:  sign(R_B − 1) == sign(R_C − 1)   (부호가 k에 무관)
H5 반증:  R_B < 1 < R_C  또는 그 역
```

**교란 통제**
- 조건 간 문서 세트·산출물 명세·언어를 완전히 동일하게 유지.
- 조건 순서를 시행마다 무작위화(에이전트 간 독립이므로 영향 작지만 기록).
- 최종 보고서의 **품질은 이 실험의 측정 대상이 아니다.** 다만 조건 B/C의 보고서가 명세 4개 절을 모두 채웠는지 여부는 유효성 필터로 기록(미충족 시행은 제외하고 사유 기록).

**한계 (반드시 문서에 명시)**
- 문자 수는 토큰의 proxy. 조건 B는 3개 산출물의 서두·형식 상투구가 중복되어 문자 수를 과대평가할 수 있으나, 이는 토큰에서도 동일하게 발생하므로 방향성은 보존된다고 가정.
- `γ`(압축 루프)는 이 규모에서 발생하지 않는다. → **E1은 "압축 루프가 없는 경우"의 손익만 판정한다.** `γ > 0` 영역은 API 확보 후 별도 실험.

#### 실험 E2 — 부분 재생성 손익분기 (H3)

**목적:** `(L_Δ + H)/L < 1 − q` 부등식의 좌변을 실측하고, 출력 형식이 손익분기점을 이동시키는지 판정.

**재료**
- 200±20줄의 구조화 텍스트 파일 1개(설정 파일 또는 마크다운 문서). `experiments/04-partial/target.md`.
- 변경 요청 3종: **소(1~2줄)**, **중(약 10%)**, **대(약 40%)**. 각 요청은 사전에 고정 문구로 작성.

**조건 (3 변경 크기 × 3 출력 형식 = 9셀, 각 `n ≥ 3`)**

| 조건 | 지시문(효율 언급 없음) |
|---|---|
| **F (전체)** | "수정을 반영한 파일 전체를 출력하라." |
| **D (unified diff)** | "변경 사항을 unified diff 형식으로 출력하라." |
| **A (앵커 치환)** | "변경할 원본 문자열과 대체할 문자열을 쌍으로 출력하라." |

**측정**
- `chars(에이전트 산출물)` — 산문 설명 포함 전체.
- **적용 성공 여부** `q`: 산출물을 원본에 기계적으로 적용해 의도한 결과가 나오는지. 실패 시 실패 사유 분류(앵커 중복 / 앵커 불일치 / 컨텍스트 라인 어긋남 / 형식 오류).

**판정 규칙**
```
각 셀에서:  ratio = chars(조건) / chars(조건 F, 동일 변경 크기)
유효 비용  = ratio + q̂ · 1.0        # 실패 시 전체 재생성(=1.0) 폴백 가정
H3 지지: 변경 크기가 커질수록 유효 비용이 1.0에 수렴/초과하고,
         형식(D vs A)에 따라 교차 지점이 달라진다.
```

**교란 통제**
- 동일 파일·동일 변경 요청 문구를 모든 형식 조건에 사용.
- 언어 고정(한국어 설명 + 원문은 원어 유지 — 원문 언어가 조건 간 동일하므로 비율 비교 유효).
- 에이전트가 diff/치환 형식을 임의로 바꾸면 해당 시행은 형식 위반으로 별도 집계(형식 준수율 자체가 `q`의 일부).

## 5. 한계 — 특히 "오히려 총 출력이 느는" 반례 조건

이 절이 이 문서의 핵심이다. 아래 조건들은 각 기법이 **총 출력 토큰을 늘리는** 상황이다.

### 5.1 멀티에이전트 — 기본값이 손해

| # | 반례 조건 | 메커니즘 | 근거 |
|---|---|---|---|
| **M1** | **압축 루프가 없는 과제(`γ = 0`)** | 이득 항 `γ·O_compact`가 소멸하고 오버헤드 `O_plan + k·O_brief`만 남는다. 서브에이전트 보고 압축분이 브리핑 비용을 못 넘기면 순증. | §2.7 |
| **M2** | **일반 과제 전반** | 멀티에이전트 ≈ 채팅 15배, 단일 ≈ 4배 → **약 3.75배**. 즉 M1이 특수 조건이 아니라 **일반적 상황**이다. | [multi-agent-research-system](https://www.anthropic.com/engineering/multi-agent-research-system) |
| **M3** | **모든 에이전트가 같은 컨텍스트를 공유해야 하는 과제 / 에이전트 간 의존성이 많은 과제(대부분의 코딩)** | 브리핑에 공유 컨텍스트를 매번 다시 써야 하므로 `O_brief`가 `o_narr` 수준까지 팽창. 병렬화 가능한 작업 자체가 적다. | 위 동일 |
| **M4** | **`k`를 늘려 만회하려는 시도** | 오버헤드와 이득이 둘 다 `k`에 선형 → **손익 부호가 `k`에 불변**(H5). 에이전트 추가는 손해를 배수로 키운다. | §2.7 |
| **M5** | **Opus 5를 오케스트레이터로 쓰면서 위임 상한을 두지 않은 경우** | Opus 5는 Opus 4.8 대비 **서브에이전트를 더 적극적으로 스폰**한다. 4.8 시절의 "더 위임하라" 프롬프트가 남아 있으면 팬아웃이 폭주. | `shared/model-migration.md` → Migrating to Claude Opus 5 |

### 5.2 모델 라우팅 — 두 가지 반전

| # | 반례 조건 | 메커니즘 |
|---|---|---|
| **R1** | **LLM 라우터의 판정 출력이 `f·(O_o(1−ε) − O_h)`를 초과** | 라우팅 판정 자체가 절감분을 잠식. `f`가 작을수록(저가 라우팅 대상이 드물수록) 임계가 가혹해진다 — **"어려운 요청이 대부분인 시스템"에 라우터를 붙이면 순손해.** |
| **R2** | **오분류율 `ε ≥ 1 − O_h/O_o` (토큰) 또는 `ε ≥ 1 − O_h·p_h/(O_o·p_o)` (비용)** | 오분류 1건이 저가 출력 + Opus 출력을 모두 소비. Haiku가 Opus만큼 길게 답하면(`O_h ≈ O_o`) **토큰 기준 임계가 `ε < 0`이 되어 어떤 라우터도 토큰을 줄이지 못한다.** |
| **R3** | **저가 모델이 verbose한 경우** | Haiku 4.5가 Opus 5보다 **더 긴** 답을 내면(`O_h > O_o`) 토큰은 물론 비용 이득도 5배 단가차 안에서 잠식된다. 저가 모델의 평균 출력 길이는 반드시 실측해야 한다. |
| **R4** | **라우팅 결과를 사용자가 재요청하는 경로** | `ε`에 잡히지 않는 숨은 재실행. 사용자 불만족 재요청률을 `ε`에 합산해야 한다. |
| **R5** | **컨텍스트 캐시 파괴** | 세션 중간에 모델을 바꾸면 prompt cache는 모델 스코프이므로 전량 무효화. 이는 입력 비용이지만, 캐시 손실을 만회하려 대화를 다시 요약하면 **출력 토큰도 증가**한다. |

### 5.3 PTC / 도구 위임

| # | 반례 조건 | 메커니즘 |
|---|---|---|
| **P1** | **도구 라운드 수 `R < S(1+ρ)/(a+n)`** | 단발 호출·2~3회 호출 구간에서는 스크립트 작성 비용이 순손해. |
| **P2** | **스크립트 디버깅 루프 `ρ`가 큰 경우** | 컨테이너 오류·스키마 착오로 재작성할 때마다 `S`만큼 다시 출력. 도구 스키마가 복잡할수록 `ρ` 증가. |
| **P3** | **PTC 비호환 구성 강행** | `strict: true` / `disable_parallel_tool_use` / 강제 `tool_choice` / MCP 도구와 비호환. 이를 우회하려 도구를 이중 정의하면 스키마 출력이 늘어난다. |
| **P4** | **도구 결과가 커서 모델이 요약 서술하는 경우** | 도구를 붙였는데 응답을 자르지 않으면, 모델이 그 결과를 사용자에게 다시 서술한다 → 출력 순증. Slack 예시 206→72 토큰(−65%)은 **도구 응답 형식 설계로만 얻어진다.** |
| **P5** | **산출물 자체가 열거·표인 경우** | §2.5의 `A ≈ D`. 계산을 코드로 옮겨도 결과를 전부 출력해야 하면 이득 없음. |

### 5.4 부분 재생성 / 캐싱 / 배치 / 구조화 출력

| # | 반례 조건 | 메커니즘 |
|---|---|---|
| **B1** | **변경비율 + 오버헤드비율 ≥ 패치 성공률** | 전체 재생성 폴백이 `L`을 통째로 추가 → `K·(L_Δ+H+L)`로 **baseline보다 크다.** 앵커 중복이 많은 파일에서 특히 위험. |
| **B2** | **시맨틱 캐시 오탐** | `φ ≥ O/(O+c)`이면 어떤 히트율에서도 손해. 잘못된 캐시 응답을 정정하는 대화가 원래 답변보다 길어지는 경우가 흔하다. |
| **B3** | **Batch API + 동기 재요청** | 배치 지연(최대 24h)을 못 기다려 동기로 재전송하면 **토큰 2배, 비용 1.5배**. Batch는 총 토큰을 전혀 줄이지 않으므로, 이 축의 KPI로는 **효과 0**이다. |
| **B4** | **구조화 출력 + 장황한 스키마** | `max_tokens` 절단으로 전량 재시도. 구조화 출력의 실패 모드는 파싱이 아니라 **절단**으로 이동한다. |
| **B5** | **구조화 출력 + 잦은 스키마 변경** | `output_config.format` 변경 시 해당 스레드 prompt cache 무효화 + 문법 재컴파일. 다중 스키마를 요청마다 바꾸는 설계는 캐시를 전부 잃는다. |
| **B6** | **Opus 5에 남아 있는 검증 지시 / 자기수정 스캐폴딩** | Opus 5는 지시 없이 자체 검증한다. 이전 모델용 "다시 확인하라" 지시와 하네스의 별도 검증 단계는 `v`만 늘리고 `P_f`는 줄이지 않는다 → **삭제가 순이득.** |

### 5.5 측정 자체의 한계

- 현재 환경에 `ANTHROPIC_API_KEY`·`ant` CLI가 없어 `usage.output_tokens` / `count_tokens` 사용 불가. 모든 실측은 **문자 수 proxy**이며, 절대 토큰 수로 보고하면 안 된다.
- **멀티에이전트 실험(E1)에서 오케스트레이터의 브리핑 텍스트를 산출물에서 빠뜨리면 결론이 정확히 반대로 뒤집힌다.** 이 항목이 이 축의 유일한 진짜 오버헤드 항이다.
- E1은 `γ = 0` 영역(압축 루프 없음)만 판정한다. `γ > 0` 영역, 즉 멀티에이전트의 실제 정당화 근거는 이 환경에서 검증 불가 — API 확보 후 컨텍스트 초과 시나리오로 별도 실험 필요.
- §1의 인용 수치(−37%, −85%, −98.7%, 3.75배)는 모두 **총 토큰 또는 입력 토큰** 기준이며, **출력 토큰 단독 분해값은 어느 출처에도 없다.** 이 축의 모든 출력 토큰 결론은 수식 + 실측 파라미터 확보 후에만 확정할 수 있다.
