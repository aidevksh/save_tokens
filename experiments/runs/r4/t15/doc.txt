요청 제한(Rate Limit) 동작 명세 — 신입 개발자 안내

이 문서는 우리 서비스가 클라이언트의 요청량을 어떻게 제한하는지 설명합니다.
방식은 토큰 버킷(token bucket)입니다. 요청 1건마다 버킷에서 토큰 1개를 꺼내 쓰고,
버킷은 시간이 지나면 정해진 속도로 다시 채워집니다.


1. 버킷 용량 — 60

한 번에 담아둘 수 있는 토큰의 최대 개수가 60개입니다.
즉, 한동안 요청을 보내지 않아 버킷이 가득 찬 상태라면 순간적으로 60건까지
연속으로 보낼 수 있습니다. 이것을 "버스트(burst) 허용량"이라고 부릅니다.
버킷은 60을 넘겨 채워지지 않습니다. 하루 종일 놀려도 61개가 되지는 않습니다.


2. 리필 속도 — 초당 1개

버킷은 1초에 토큰 1개씩 다시 채워집니다.
따라서 장기적으로 유지 가능한 평균 요청 속도는 초당 1건입니다.
버킷을 다 비운 뒤 다시 가득 채우려면 60초가 걸립니다.

정리하면 이 두 값의 조합은 이렇게 읽습니다.
- 짧은 순간의 폭발적 요청: 최대 60건까지 허용
- 지속적인 평균 속도: 초당 1건


3. 집계 단위 — API 키 (IP 주소가 아님)

버킷은 API 키 하나당 하나씩 존재합니다. IP 주소 기준이 아닙니다.

이 차이가 실제로 의미하는 것:
- 같은 API 키를 여러 서버·여러 IP에서 나눠 써도 버킷은 하나로 합산됩니다.
  서버를 늘린다고 허용량이 늘어나지 않습니다.
- 반대로 같은 사무실(같은 공인 IP)에서 서로 다른 API 키로 호출하면
  서로의 제한에 영향을 주지 않습니다.
- 따라서 트래픽이 많은 별도 워크로드는 별도의 API 키를 발급받는 것이 맞습니다.


4. 초과 시 상태 코드 — 429

버킷에 토큰이 없는 상태에서 요청이 들어오면 서버는 HTTP 429
(Too Many Requests)를 반환합니다.

클라이언트를 만들 때는 429를 "요청이 잘못됐다"가 아니라
"지금은 안 되지만 나중에 다시 하면 된다"는 신호로 다뤄야 합니다.
4xx라고 해서 재시도 없이 바로 실패 처리하면 안 됩니다.


5. 재시도 안내 헤더 — Retry-After (초 단위 정수)

429 응답에는 Retry-After 헤더가 함께 옵니다. 값은 초 단위 정수입니다.

    HTTP/1.1 429 Too Many Requests
    Retry-After: 5

위 예시는 "5초 뒤에 다시 시도하라"는 뜻입니다.
(HTTP 규격상 Retry-After에는 날짜 형식도 있지만, 우리 서비스는 항상 정수 초를 씁니다.)

클라이언트 구현 지침:
- 임의로 정한 간격이 아니라 Retry-After 값을 그대로 기다린 뒤 재시도합니다.
- 여러 클라이언트가 동시에 429를 맞으면 같은 시각에 몰려서 재시도하게 되므로,
  약간의 무작위 지연(jitter)을 더하는 편이 안전합니다.
- 재시도 횟수 상한을 두고, 그래도 실패하면 상위로 오류를 올립니다.


6. 예외 — admin 스코프 키

admin 스코프를 가진 API 키는 요청 제한을 적용받지 않습니다.
버킷을 소모하지 않으며 429도 발생하지 않습니다.

주의할 점:
- 운영/관리 목적의 키이므로 일반 서비스 트래픽에 사용하면 안 됩니다.
  제한이 없다는 것은 실수로 무한 루프를 돌렸을 때 막아줄 안전장치도 없다는 뜻입니다.
- 부하 테스트를 admin 키로 하면 실제 사용자 경로의 제한 동작을 검증할 수 없습니다.
  테스트는 반드시 일반 스코프 키로 합니다.


요약 표

  항목              값
  버킷 용량         60
  리필 속도         초당 1개
  집계 단위         API 키 (IP 주소 아님)
  초과 시 응답      429
  재시도 안내       Retry-After 헤더, 초 단위 정수
