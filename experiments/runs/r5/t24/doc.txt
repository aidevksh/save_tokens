# 요청 제한(Rate Limit) 동작 안내

이 문서는 우리 서비스의 요청 제한 동작을 처음 접하는 분을 위해 작성되었습니다. 요청 제한은
특정 사용자가 과도한 요청을 보내 서비스 전체가 느려지는 것을 막기 위한 장치입니다. 클라이언트를
개발하든 서버를 다루든, 언제 요청이 막히고 막힌 뒤에 어떻게 해야 하는지 알아 두는 것이 좋습니다.

## 1. 버킷 용량 — 60

요청 허용량은 "토큰 버킷"이라는 방식으로 관리됩니다. 물이 담기는 양동이를 떠올리면 됩니다.
양동이에는 최대 60개의 토큰이 담기고, 요청 하나를 보낼 때마다 토큰 하나가 빠집니다. 토큰이
남아 있으면 요청은 그대로 통과하고, 하나도 없으면 거절됩니다.

용량이 60이라는 것은 곧 **한 번에 몰아서 보낼 수 있는 최대 요청 수가 60건**이라는 뜻입니다.
한동안 요청을 보내지 않아 양동이가 가득 차 있었다면, 순간적으로 60건까지는 제한 없이 처리됩니다.
이런 순간적 몰아치기를 버스트(burst)라고 부릅니다.

## 2. 리필 속도 — 초당 1개

빠져나간 토큰은 **1초에 1개씩** 다시 채워집니다. 단, 양동이가 넘치지는 않으므로 최대 60개까지만
쌓입니다.

이 두 값을 합치면 서비스의 성격이 드러납니다. 장기적으로 유지 가능한 평균 속도는 초당 1건이고,
잠깐 동안은 60건까지 몰아서 보낼 수 있습니다. 예를 들어 60건을 한꺼번에 보내 양동이를 비웠다면,
그 직후에는 1초에 1건씩만 통과합니다. 다시 60건을 몰아 보내려면 60초를 기다려 양동이가 가득
차야 합니다.

## 3. 집계 단위 — API 키

제한은 **API 키 단위**로 계산됩니다. IP 주소 단위가 아니라는 점이 중요합니다.

이 차이는 실무에서 자주 헷갈립니다. 같은 사무실에서 여러 사람이 하나의 IP를 공유하더라도 각자
다른 API 키를 쓴다면 서로의 사용량에 영향을 주지 않습니다. 반대로 여러 서버에 같은 API 키를
심어 두었다면, 서버가 몇 대이든 관계없이 하나의 양동이를 함께 나눠 쓰게 됩니다. 즉 서버를
늘려서 제한을 우회할 수는 없습니다. 처리량을 늘려야 한다면 키를 나누거나 상향을 요청해야 합니다.

## 4. 초과 시 상태 코드 — 429

토큰이 없는 상태에서 요청이 들어오면 서버는 HTTP 상태 코드 **429 (Too Many Requests)** 를
돌려줍니다.

429는 요청 내용이 잘못되어서 생긴 오류가 아닙니다. 요청 자체는 정상이지만 지금은 때가 아니라는
뜻이므로, 잠시 뒤 같은 요청을 다시 보내면 성공합니다. 400번대 오류라고 해서 무조건 코드를
고쳐야 하는 상황으로 오해하지 않도록 주의하세요.

## 5. 재시도 안내 헤더 — Retry-After

429 응답에는 `Retry-After` 헤더가 함께 실려 옵니다. 값은 **초 단위 정수**이며, "이만큼 기다린
뒤에 다시 보내라"는 의미입니다. 예를 들어 `Retry-After: 5` 라면 5초 뒤에 재시도하면 됩니다.

클라이언트를 만들 때는 이 헤더 값을 그대로 사용하는 것이 가장 좋습니다. 값을 무시하고 즉시
재시도하면 다시 429를 받을 뿐이고, 오히려 서버 부하만 키웁니다. 헤더가 없는 예외적인 상황에
대비해 재시도 간격을 점점 늘리는 방식(백오프)을 함께 넣어 두면 안전합니다.

## 6. 예외 — admin 스코프 키

`admin` 스코프를 가진 API 키는 요청 제한을 적용받지 않습니다. 운영 중 장애 대응이나 관리 작업이
제한 때문에 막히는 상황을 피하기 위한 예외입니다.

편리해 보이지만, 일반적인 애플리케이션 트래픽에 admin 키를 사용해서는 안 됩니다. 제한이 없다는
것은 곧 실수로 만든 무한 루프도 그대로 서비스에 전달된다는 뜻입니다. admin 키는 관리 목적에만
쓰고, 일반 기능은 반드시 제한이 적용되는 일반 키로 개발해 실제 동작 환경과 같은 조건에서
검증하세요.
