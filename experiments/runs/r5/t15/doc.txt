# 요청 제한(Rate Limit) 동작 안내

이 문서는 우리 서비스의 요청 제한 동작을 처음 접하는 분을 위해 작성되었습니다. 요청 제한은
특정 사용자가 서비스 자원을 지나치게 많이 쓰는 것을 막아 전체 사용자가 안정적으로 API를
쓸 수 있게 하는 장치입니다. 어떤 기준으로 얼마나 허용되는지, 걸렸을 때 무엇이 돌아오는지
정확히 알아 두면 클라이언트를 만들 때 헤매지 않습니다.

## 1. 버킷 용량 — 60

요청 허용량은 "토큰 버킷"이라는 방식으로 관리됩니다. 버킷에는 토큰이 담겨 있고, 요청이
하나 들어올 때마다 토큰을 하나 꺼내 씁니다. 토큰이 남아 있으면 요청은 통과하고, 바닥나면
거절됩니다.

이 버킷이 담을 수 있는 최대 토큰 수가 60입니다. 즉 한동안 요청을 전혀 보내지 않아 버킷이
가득 찬 상태라면, 그 순간에 최대 60개의 요청을 한꺼번에 몰아서 보낼 수 있습니다. 이 값은
순간적으로 몰리는 요청(버스트)을 어디까지 받아 줄지를 정합니다.

## 2. 리필 속도 — 초당 1개

써서 줄어든 토큰은 초당 1개씩 다시 채워집니다. 버킷은 60을 넘겨서는 채워지지 않으므로,
아무리 오래 쉬어도 쌓아 둘 수 있는 여유분은 60개까지입니다.

여기서 두 가지 서로 다른 한도가 나옵니다.

- **순간 한도**: 한 번에 몰아서 보낼 수 있는 양 — 최대 60개
- **지속 한도**: 계속 보낼 때 유지 가능한 평균 속도 — 초당 1개

예를 들어 버킷이 가득 찬 상태에서 60개를 한꺼번에 보내면 버킷은 0이 됩니다. 그 다음부터는
1초에 1개 꼴로만 요청이 통과합니다. 비어 있던 버킷이 다시 가득 차려면 60초가 걸립니다.

## 3. 집계 단위 — API 키 (IP 주소가 아님)

버킷은 **API 키마다 하나씩** 따로 존재합니다. IP 주소 기준이 아니라는 점이 중요합니다.

이 때문에 다음과 같은 결과가 나옵니다.

- 같은 서버(같은 IP)에서 서로 다른 API 키로 요청을 보내면, 각 키가 독립된 60개 버킷을
  가집니다. 한 키가 한도를 다 써도 다른 키는 영향을 받지 않습니다.
- 반대로 하나의 API 키를 여러 서버나 여러 인스턴스가 나눠 쓰면, 그 모두가 **하나의 버킷을
  공유**합니다. 서버를 늘려도 허용량은 늘어나지 않습니다. 트래픽을 늘리려면 인스턴스가
  아니라 키를 나눠야 합니다.

## 4. 초과 시 상태 코드 — 429

토큰이 없는 상태에서 요청이 들어오면 서버는 HTTP 상태 코드 **429 (Too Many Requests)** 를
돌려줍니다. 이 요청은 처리되지 않으므로, 클라이언트 쪽에서 429를 별도로 처리해 주어야
합니다. 400번대 오류라고 해서 요청 내용이 잘못된 것은 아니며, 같은 요청을 나중에 다시
보내면 정상적으로 처리됩니다.

## 5. 재시도 안내 헤더 — `Retry-After`

429 응답에는 `Retry-After` 헤더가 함께 실려 옵니다. 값은 **초 단위 정수**이며, "이만큼
기다린 뒤에 다시 보내면 된다"는 뜻입니다. 예를 들어 `Retry-After: 5` 라면 5초 뒤에
재시도하십시오.

클라이언트를 만들 때는 이 값을 그대로 쓰는 것이 좋습니다. 임의로 짧은 간격을 정해 계속
재시도하면 429만 더 받게 되고, 회복이 오히려 늦어집니다. 헤더 값만큼 기다렸다가 보내는
방식으로 구현하십시오.

## 6. 예외 — `admin` 스코프 키

`admin` 스코프를 가진 API 키는 요청 제한의 적용을 받지 않습니다. 버킷 소모나 429 응답 없이
요청이 처리됩니다.

다만 운영·관리 용도로 열어 둔 예외이므로, 일반 애플리케이션 트래픽을 `admin` 키로 흘려
제한을 피하는 식으로 쓰면 안 됩니다. 일반 기능은 일반 스코프 키로 호출하고, 제한에 걸린다면
재시도 처리를 제대로 구현하거나 별도로 한도 조정을 요청하는 것이 올바른 방향입니다.
