# 요청 제한(Rate Limit) 정책 안내

이 문서는 우리 서비스의 요청 제한 동작을 처음 접하는 분을 위해 작성되었습니다. 요청 제한은
특정 이용자가 짧은 시간에 과도한 요청을 보내 전체 서비스 품질을 떨어뜨리는 일을 막기 위한
장치입니다. 어떤 기준으로 얼마나 허용되는지, 걸렸을 때 어떤 응답이 돌아오는지 알아 두면
클라이언트를 만들 때나 장애를 조사할 때 도움이 됩니다.

## 1. 버킷 용량 — 60

요청 제한은 흔히 말하는 토큰 버킷 방식으로 동작합니다. 이용자마다 토큰을 담는 통(버킷)이
하나 있다고 생각하면 됩니다. 요청이 한 번 들어올 때마다 토큰을 하나 꺼내 쓰고, 통이 비면
더 이상 요청을 받지 않습니다. 이 통의 최대 크기가 60입니다. 즉 토큰이 가득 찬 상태라면
연달아 60번까지는 곧바로 요청을 보낼 수 있습니다. 이 여유분 덕분에 평소에 조용하다가
잠깐 몰아서 요청을 보내는 사용 방식도 막히지 않습니다. 토큰은 60을 넘겨 쌓이지 않으므로,
오래 쉬었다고 해서 61개 이상의 여유가 생기지는 않습니다.

## 2. 리필 속도 — 초당 1개

비워진 토큰은 초당 한 개씩 다시 채워집니다. 따라서 장기적으로 유지할 수 있는 요청 속도는
초당 1회이고, 앞서 말한 용량 60은 그 위에 얹히는 순간적인 여유분입니다. 예를 들어 60번을
연속으로 보내 통을 완전히 비웠다면, 1초 뒤에 한 번, 10초 뒤에는 열 번을 보낼 수 있습니다.
다시 60번을 몰아 보낼 수 있으려면 60초를 쉬어야 합니다.

## 3. 집계 단위 — API 키

제한은 API 키 단위로 계산됩니다. IP 주소 단위가 아니라는 점이 중요합니다. 같은 API 키를
쓰는 서버가 여러 대라면 그 서버들이 하나의 버킷을 나눠 쓰게 되므로, 대수를 늘려도 전체
허용량은 늘어나지 않습니다. 반대로 한 대의 서버에서 서로 다른 API 키로 요청을 보낸다면
각각 별도의 버킷을 갖습니다. 사용량을 분리하고 싶다면 서버가 아니라 키를 나눠야 합니다.

## 4. 초과 시 상태 코드 — 429

토큰이 없는 상태에서 요청이 들어오면 서버는 HTTP 429(Too Many Requests)로 응답합니다.
이것은 요청 내용이 잘못되었다는 뜻이 아니라 지금은 받을 수 없다는 뜻이므로, 클라이언트는
400번대 오류라고 해서 그대로 실패 처리하지 말고 잠시 뒤 다시 시도하도록 만드는 것이
좋습니다.

## 5. 재시도 안내 헤더 — Retry-After

429 응답에는 `Retry-After` 헤더가 함께 실립니다. 값은 초 단위 정수이며, 그만큼 기다린 뒤
다시 요청하면 된다는 안내입니다. 예를 들어 값이 5라면 5초 뒤에 재시도하면 됩니다.
재시도 간격을 임의로 정해 곧바로 다시 두드리면 계속 429만 받게 되므로, 클라이언트에서는
이 헤더 값을 그대로 읽어 대기 시간으로 쓰는 것을 권장합니다.

## 6. 예외 — admin 스코프 키

`admin` 스코프를 가진 API 키는 요청 제한에서 제외됩니다. 이 키로 보낸 요청은 버킷을
소모하지 않고 429도 받지 않습니다. 운영 작업이나 일괄 처리를 위한 통로이므로, 일반적인
서비스 트래픽에는 사용하지 않는 것이 원칙입니다. 또한 테스트 중 429가 재현되지 않는다면
사용 중인 키의 스코프가 `admin`은 아닌지 먼저 확인해 보시기 바랍니다.
