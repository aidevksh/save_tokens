웹훅(Webhook) 전달 명세 — 신입 백엔드 개발자를 위한 안내

===========================================================
0. 전체 그림
===========================================================

주문 도메인에서 상태 변화가 생기면 이벤트 버스에 이벤트가 하나 올라갑니다.
전달기(deliverer)는 그 이벤트를 구독 중인 엔드포인트마다 하나씩 HTTP POST 로 보냅니다.

  주문 도메인 --(이벤트 1건)--> 이벤트 버스 --> 전달기 --+--> 엔드포인트 A (전달 1건)
                                                        +--> 엔드포인트 B (전달 1건)
                                                        +--> 엔드포인트 C (전달 1건)

엔드포인트는 팀별로 등록하며, 한 팀이 여러 개를 둘 수 있습니다.
전달기는 엔드포인트별로 독립된 큐를 쓰므로, 한 엔드포인트가 느려도 다른 엔드포인트의
전달은 밀리지 않습니다.

용어 (헷갈리기 쉬우니 먼저 확실히 해둡니다)
  - 이벤트(event): 도메인에서 발생한 사실 하나.
  - 전달(delivery): 그 이벤트를 엔드포인트 하나에 보내는 시도 하나.
  - 이벤트 1건이 엔드포인트 3개에 나가면 전달은 3건입니다.
  - 실패와 재시도는 "전달" 단위로 셉니다. 이벤트 단위가 아닙니다.

아래 열 가지가 수신 측이 반드시 알아야 할 규약입니다.


===========================================================
1. 재시도 횟수
===========================================================

수신 서버가 2xx 를 돌려주지 않으면 최대 5회까지 다시 보냅니다.
5회를 모두 실패하면 그 이벤트는 폐기되고, 전달 로그에 `dropped` 로 남습니다.

수신 측 관점: 처리에 성공했다면 반드시 2xx 를 주세요. 2xx 가 아닌 응답은
"다시 보내 달라"는 신호로 해석됩니다.


===========================================================
2. 백오프(backoff)
===========================================================

재시도 간격은 지수 백오프입니다.
  - 첫 간격: 2초
  - 실패할 때마다 2배로 증가
  - 상한: 64초
  - 무작위 흔들림(jitter)은 넣지 않습니다.

즉 간격은 2초 → 4초 → 8초 → 16초 → 32초 순으로 늘어나며, 64초를 넘지 않습니다.
jitter 가 없다는 것은 재시도 시점이 결정적(deterministic)이라는 뜻이므로,
장애 복구 시점에 재시도가 한꺼번에 몰릴 수 있다는 점을 염두에 두세요.


===========================================================
3. 서명 헤더 (X-Signature)
===========================================================

모든 요청에 `X-Signature` 헤더가 붙습니다.
  - 값 = HMAC-SHA256(요청 본문 전체, 엔드포인트 비밀키) 의 16진수 문자열

수신 측은 **본문을 파싱하기 전에** 이 값을 먼저 검증해야 합니다.
파싱 후 검증하면, 검증되지 않은 데이터를 이미 역직렬화한 뒤가 되어 안전하지 않습니다.

검증 순서:
  1) 원본 바이트 그대로의 본문을 확보한다 (프레임워크가 재가공하기 전 raw body).
  2) 엔드포인트 비밀키로 HMAC-SHA256 을 계산한다.
  3) `X-Signature` 값과 비교한다. 비교는 타이밍 공격에 안전한 함수를 쓴다.
  4) 일치할 때만 본문을 JSON 으로 파싱한다.


===========================================================
4. 타임아웃
===========================================================

수신 서버가 10초 안에 응답 헤더를 보내지 않으면 실패로 처리합니다.
연결 타임아웃과 읽기 타임아웃을 따로 두지 않고 전체를 10초로 잽니다.

수신 측 관점: 무거운 처리는 요청 안에서 끝내지 말고, 검증 후 큐에 넣고
바로 2xx 를 반환하는 구조를 권장합니다. 10초를 넘기면 성공 처리했더라도
전달기 쪽에서는 실패로 기록되고 재시도가 발생합니다.


===========================================================
5. 중복 전달 (at-least-once)
===========================================================

전달 보장 수준은 at-least-once 입니다. 같은 이벤트가 두 번 이상 도착할 수 있습니다.
(예: 수신 측은 정상 처리했는데 응답이 10초를 넘겨 실패로 간주된 경우)

따라서 수신 측은 본문의 `event_id` 로 멱등(idempotent) 처리를 해야 합니다.
이미 처리한 `event_id` 면 다시 처리하지 말고 2xx 만 돌려주세요.


===========================================================
6. 순서 보장 없음
===========================================================

이벤트 순서는 보장하지 않습니다. 나중에 발생한 이벤트가 먼저 도착할 수 있습니다.
(재시도가 걸린 이벤트는 뒤늦게 도착하므로 특히 그렇습니다.)

수신 측은 도착 순서를 믿지 말고 본문의 `occurred_at` 을 기준으로 정렬해야 합니다.
상태를 갱신할 때는 "이미 저장된 것보다 `occurred_at` 이 오래된 이벤트는 무시"하는
식의 방어가 필요합니다.


===========================================================
7. 페이로드 크기 상한
===========================================================

본문은 256KB 를 넘지 않습니다.
넘는 경우 본문 대신 `payload_url` 필드가 들어가고, 수신 측이 그 주소에서 직접
내려받아야 합니다.

수신 측은 두 가지 모양을 모두 처리해야 합니다.
  - 일반: `data` 안에 실제 내용이 들어 있음
  - 대용량: `payload_url` 이 들어 있음 → 해당 주소에서 내려받아 처리


===========================================================
8. 이벤트 타입
===========================================================

현재 보내는 타입은 세 가지입니다.
  - `order.created`
  - `order.updated`
  - `order.canceled`

구독하지 않은 타입은 전달되지 않습니다.
앞으로 타입이 늘어날 수 있으므로, 모르는 `type` 이 오면 오류를 내지 말고
조용히 무시(2xx 반환)하도록 만드는 편이 안전합니다.


===========================================================
9. 자동 비활성화
===========================================================

한 엔드포인트에서 다음 조건 중 하나에 이르면, 그 엔드포인트를 자동으로
비활성화하고 관리자에게 메일을 보냅니다.
  - 연속 실패가 100회에 도달
  - 실패 상태가 7일 지속

비활성화되면 그 엔드포인트로는 더 이상 전달이 나가지 않습니다.
장애 복구 후에는 콘솔에서 다시 활성화하고, 그 사이 놓친 이벤트는
재전송 API(10번)로 복구하세요.


===========================================================
10. 재전송 API
===========================================================

  POST /webhooks/{id}/redeliver

지난 이벤트를 다시 보낼 수 있습니다.
  - 대상 범위: 최근 30일치
  - 한 번 호출에 최대 100건

30일이 지난 이벤트는 재전송할 수 없으므로, 장애를 오래 방치하지 마세요.
100건을 넘겨 복구해야 하면 여러 번 나누어 호출합니다.
재전송으로 온 이벤트도 `event_id` 는 같으므로, 멱등 처리(5번)가 되어 있으면
중복 반영 걱정 없이 마음 편히 호출할 수 있습니다.


===========================================================
전달 로그
===========================================================

관리 콘솔의 "전달" 탭에서 볼 수 있고, 다음 필드를 담습니다.

  delivery_id  전달 시도 하나의 식별자
  event_id     원본 이벤트 식별자. 재시도해도 값이 같습니다
  attempt      몇 번째 시도인지. 1 부터 셉니다
  status_code  수신 서버가 준 HTTP 상태 코드. 타임아웃이면 비어 있습니다
  duration_ms  요청을 보내고 응답 헤더를 받기까지 걸린 밀리초
  result       ok / retrying / dropped 셋 중 하나

디버깅 요령:
  - `status_code` 가 비어 있고 `duration_ms` 가 10000 근처면 타임아웃(4번)입니다.
  - `result` 가 `dropped` 면 5회 재시도를 모두 실패한 것입니다(1번).
  - 같은 `event_id` 의 여러 행을 `attempt` 순으로 보면 재시도 이력을 볼 수 있습니다.


===========================================================
본문 예시
===========================================================

{
  "event_id": "evt_01H9Z2",
  "type": "order.created",
  "occurred_at": "2026-03-14T05:21:09Z",
  "data": {"order_id": "ord_8812", "amount": 42900, "currency": "KRW"}
}


===========================================================
비밀키 관리
===========================================================

비밀키는 엔드포인트를 등록할 때 한 번만 보여주고 이후에는 다시 볼 수 없습니다.
등록 시점에 반드시 안전한 곳(시크릿 매니저 등)에 보관하세요.

분실하면 콘솔에서 회전(rotate)해야 합니다.
회전 직후 5분 동안은 옛 키와 새 키로 만든 서명을 둘 다 받아 줍니다.
이 5분이 무중단 교체를 위한 창(window)이므로, 그 안에 수신 측 설정을 새 키로
바꾸면 검증 실패 없이 넘어갈 수 있습니다.

회전 이력도 전달 로그와 같은 탭에서 확인할 수 있습니다.


===========================================================
수신 측 구현 체크리스트
===========================================================

  [ ] raw body 를 보존한 뒤 X-Signature 를 먼저 검증한다 (3번)
  [ ] 검증 실패 시 본문을 파싱하지 않고 거부한다 (3번)
  [ ] event_id 기준 멱등 처리를 한다 (5번)
  [ ] occurred_at 기준으로 정렬/순서 역전을 방어한다 (6번)
  [ ] 무거운 처리는 큐로 넘기고 10초 안에 2xx 를 반환한다 (4번)
  [ ] payload_url 형태의 본문도 처리한다 (7번)
  [ ] 모르는 type 은 오류 대신 무시한다 (8번)
  [ ] 비밀키는 시크릿 저장소에 보관하고, 회전 시 5분 창 안에 교체한다
