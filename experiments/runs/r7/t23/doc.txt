웹훅(Webhook) 전달 명세 — 신입 백엔드 개발자용 안내

이 문서는 우리 서비스가 외부(또는 사내 다른 팀)의 HTTP 엔드포인트로 이벤트를 보내는
방식을 처음 접하는 사람을 위해 정리한 것입니다. 수신 서버를 만드는 쪽에서 반드시 알아야
할 규약 열 가지를 중심으로 설명합니다.


0. 전체 그림과 용어

주문 도메인에서 상태 변화가 생기면 이벤트 버스에 이벤트가 하나 올라갑니다. 전달기는 그
이벤트를 구독 중인 엔드포인트마다 하나씩 HTTP POST 로 보냅니다. 엔드포인트는 팀별로
등록하고, 한 팀이 여러 개를 둘 수 있습니다.

용어를 먼저 구분해 두면 이후 설명이 훨씬 쉽습니다.

- 이벤트(event): 도메인에서 발생한 사실 하나. 예를 들어 "주문 ord_8812 가 생성되었다".
- 전달(delivery): 그 이벤트를 엔드포인트 하나에 보내는 시도 하나.

즉 이벤트 1건이 엔드포인트 3개에 나가면 전달은 3건입니다. 실패와 재시도는 이벤트가 아니라
전달 단위로 셉니다. 엔드포인트 A 로 가는 전달이 실패해도 엔드포인트 B 의 전달과는 무관합니다.

전달기는 엔드포인트별로 독립된 큐를 씁니다. 그래서 한 엔드포인트가 느리거나 죽어 있어도
다른 엔드포인트의 전달은 밀리지 않습니다. 반대로 말하면, 내 엔드포인트가 느리면 그 지연은
온전히 내 큐에만 쌓입니다.


1. 재시도 횟수

수신 서버가 2xx 를 돌려주지 않으면 최대 5회까지 다시 보냅니다. 5회를 모두 실패하면 그
이벤트는 폐기되고 전달 로그에 `dropped` 로 남습니다.

- 2xx 가 아닌 모든 응답(4xx 포함)은 실패로 봅니다. 즉 수신 측 버그로 400 을 돌려주면
  재시도가 일어나고, 결국 폐기될 수 있습니다.
- 성공 처리를 마쳤다면 반드시 2xx 를 돌려주세요. 처리에 시간이 오래 걸리는 작업이라면
  먼저 큐에 넣고 2xx 를 즉시 반환하는 편이 안전합니다(항목 4 타임아웃 참고).


2. 백오프

재시도 간격은 지수 백오프입니다.

- 첫 간격 2초
- 실패할 때마다 2배로 증가 (2초 → 4초 → 8초 → 16초 → 32초 …)
- 상한 64초

무작위 흔들림(jitter)은 넣지 않습니다. 따라서 여러 엔드포인트가 동시에 실패했다가 동시에
복구되면 재시도가 같은 시각에 몰릴 수 있습니다. 수신 측에서 이 점을 감안해 순간 부하를
견딜 수 있게 해 두는 편이 좋습니다.


3. 서명 헤더

모든 요청에 `X-Signature` 헤더가 붙습니다.

- 값 = 요청 본문 전체를 엔드포인트 비밀키로 HMAC-SHA256 한 결과의 16진수 문자열
- 수신 측은 본문을 파싱하기 전에 이 값을 먼저 검증해야 합니다.

파싱보다 검증이 먼저인 이유는, 검증되지 않은 입력을 파서에 넣는 것 자체가 공격 표면이기
때문입니다. 또 서명 대상은 "요청 본문 전체"이므로, 프레임워크가 본문을 재직렬화한 결과가
아니라 원본 바이트를 그대로 가지고 계산해야 값이 맞습니다.


4. 타임아웃

수신 서버가 10초 안에 응답 헤더를 보내지 않으면 실패로 처리합니다. 연결 타임아웃과 읽기
타임아웃을 따로 두지 않고 전체를 10초로 잽니다.

핵심은 "응답 헤더까지"의 시간이라는 점입니다. 무거운 처리를 동기로 끝내고 응답하려 하면
10초를 넘기기 쉽습니다. 접수만 하고 바로 2xx 를 반환한 뒤 실제 처리는 비동기로 돌리는
구조를 권장합니다.


5. 중복 전달

전달 보장 수준은 at-least-once 입니다. 같은 이벤트가 두 번 이상 도착할 수 있습니다.

예를 들어 수신 서버가 처리를 마쳤는데 응답이 타임아웃되면, 전달기 입장에서는 실패이므로
같은 이벤트를 다시 보냅니다. 수신 측에서는 본문의 `event_id` 를 키로 멱등 처리를 해야
합니다. 이미 처리한 `event_id` 라면 다시 처리하지 말고 2xx 만 돌려주면 됩니다.

`event_id` 는 재시도해도 값이 같습니다(바뀌는 것은 `delivery_id` 입니다).


6. 순서 보장

이벤트 순서는 보장하지 않습니다. 나중에 발생한 이벤트가 먼저 도착할 수 있습니다.

따라서 도착 순서를 그대로 상태 전이에 반영하면 안 됩니다. 본문의 `occurred_at` 을 기준으로
정렬하거나, 이미 저장된 레코드의 `occurred_at` 보다 오래된 이벤트는 무시하는 식으로
처리하세요. 항목 5의 멱등 처리와 함께 쓰면 "중복되고 순서가 섞여도 결과가 같은" 수신기가
됩니다.


7. 페이로드 크기 상한

본문은 256KB 를 넘지 않습니다. 넘는 경우 본문에 데이터를 담는 대신 `payload_url` 필드가
들어가고, 수신 측이 그 주소에서 직접 내려받아야 합니다.

즉 수신기는 두 가지 형태를 모두 다룰 수 있어야 합니다.

- 일반: 본문 안에 `data` 가 들어 있음
- 큰 페이로드: 본문에 `payload_url` 이 들어 있고 실제 데이터는 그 주소에 있음


8. 이벤트 타입

현재 보내는 타입은 세 가지입니다.

- `order.created` — 주문 생성
- `order.updated` — 주문 변경
- `order.canceled` — 주문 취소

구독하지 않은 타입은 전달되지 않습니다. 다만 앞으로 타입이 늘어날 수 있으므로, 모르는
`type` 값을 받았을 때 오류를 내지 말고 조용히 무시(그리고 2xx 반환)하도록 만들어 두는
편이 안전합니다.


9. 자동 비활성화

한 엔드포인트에서 다음 중 하나에 해당하면 그 엔드포인트를 자동으로 비활성화하고 관리자에게
메일을 보냅니다.

- 연속 실패가 100회에 이른 경우
- 실패 상태가 7일 이어진 경우

비활성화되면 그 엔드포인트로는 전달이 나가지 않습니다. 배포 중 장애나 인증서 만료 등으로
장시간 실패가 쌓이면 조용히 끊길 수 있으므로, 관리자 메일 수신처를 실제로 보는 주소로
등록해 두세요.


10. 재전송 API

`POST /webhooks/{id}/redeliver` 로 지난 이벤트를 다시 보낼 수 있습니다.

- 대상 범위: 최근 30일치
- 한 번 호출에 최대 100건

수신 측 장애로 이벤트를 놓쳤을 때 복구하는 수단입니다. 30일이 지난 이벤트는 재전송할 수
없으므로, 장기간 누락이 의심되면 그 전에 확인해야 합니다. 재전송된 이벤트도 `event_id` 는
동일하므로 항목 5의 멱등 처리가 그대로 적용됩니다.


전달 로그

관리 콘솔의 전달 탭에서 볼 수 있고 다음 필드를 담습니다.

| 필드 | 뜻 |
|---|---|
| `delivery_id` | 전달 시도 하나의 식별자 |
| `event_id` | 원본 이벤트 식별자. 재시도해도 값이 같습니다 |
| `attempt` | 몇 번째 시도인지. 1 부터 셉니다 |
| `status_code` | 수신 서버가 준 HTTP 상태 코드. 타임아웃이면 비어 있습니다 |
| `duration_ms` | 요청을 보내고 응답 헤더를 받기까지 걸린 밀리초 |
| `result` | `ok` / `retrying` / `dropped` 셋 중 하나 |

디버깅할 때는 `event_id` 로 묶어서 보면 한 이벤트가 몇 번 시도됐고 각 시도가 어떻게 끝났는지
한눈에 볼 수 있습니다. `status_code` 가 비어 있으면 타임아웃입니다.


본문 예시

```json
{
  "event_id": "evt_01H9Z2",
  "type": "order.created",
  "occurred_at": "2026-03-14T05:21:09Z",
  "data": {"order_id": "ord_8812", "amount": 42900, "currency": "KRW"}
}
```


비밀키 관리

비밀키는 엔드포인트를 등록할 때 한 번만 보여주고 이후에는 다시 볼 수 없습니다. 그 자리에서
안전한 곳(시크릿 매니저 등)에 저장하세요.

분실하면 콘솔에서 회전(rotate)해야 합니다. 회전 직후 5분 동안은 옛 키와 새 키로 만든 서명을
둘 다 받아 줍니다. 이 유예 시간 덕분에 무중단으로 키를 교체할 수 있습니다.

- 회전 → 5분 안에 수신 측 설정을 새 키로 교체 → 완료
- 5분이 지나면 옛 키로 만든 서명은 더 이상 통과하지 않습니다.

회전 이력도 전달 로그와 같은 탭에서 확인할 수 있습니다.


수신기 구현 체크리스트

1. 본문 원본 바이트로 `X-Signature` 를 먼저 검증한다 (항목 3)
2. 검증 후 파싱하고, `event_id` 로 중복인지 확인한다 (항목 5)
3. `occurred_at` 을 기준으로 순서를 판단한다 (항목 6)
4. `payload_url` 이 있으면 본문 대신 그 주소에서 내려받는다 (항목 7)
5. 모르는 `type` 은 무시하고 2xx 를 반환한다 (항목 8)
6. 무거운 처리는 비동기로 넘기고 10초 안에 응답한다 (항목 4)
7. 성공했으면 반드시 2xx 를 반환한다 — 아니면 재시도 후 폐기된다 (항목 1, 2)
8. 장애로 놓친 이벤트는 30일 안에 재전송 API 로 복구한다 (항목 10)
9. 자동 비활성화 알림 메일을 받을 주소를 실제로 확인한다 (항목 9)
