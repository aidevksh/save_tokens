요청 제한(rate limit) 동작 안내

우리 서비스는 토큰 버킷(token bucket) 방식으로 요청 수를 제한합니다. 각 호출자에게 토큰이 담긴 양동이가 하나 있다고 생각하면 됩니다. 요청 한 건마다 토큰 하나를 꺼내 쓰고, 토큰이 없으면 요청이 거절됩니다.

1) 버킷 용량: 60
양동이에 한 번에 담을 수 있는 토큰의 최대 개수가 60개입니다. 즉 한동안 요청을 보내지 않아 토큰이 가득 찬 상태라면, 순간적으로 최대 60건까지 연속으로 요청을 보낼 수 있습니다. 이것을 버스트(burst) 허용량이라고 부릅니다. 토큰이 60개를 넘겨 쌓이지는 않으므로, 하루를 쉬었다고 해서 그다음에 수백 건을 몰아 보낼 수는 없습니다.

2) 리필 속도: 초당 1개
비워진 토큰은 1초에 1개씩 다시 채워집니다. 따라서 장기적으로 유지 가능한 평균 요청 속도는 초당 1건이고, 60이라는 용량은 그 평균을 넘어서는 순간적인 몰림을 흡수해 주는 여유분입니다. 버킷을 완전히 비운 뒤 다시 가득 채우려면 60초가 걸립니다.

3) 집계 단위: API 키
제한은 **API 키 단위**로 계산합니다. IP 주소 단위가 아닙니다. 이 차이는 실무에서 중요합니다.
- 서버 여러 대가 같은 API 키를 쓰면, 서버가 몇 대든 그 키 하나의 버킷을 함께 나눠 씁니다. 대수를 늘려도 처리량은 늘어나지 않습니다.
- 반대로 같은 IP(예: 하나의 NAT 게이트웨이나 사무실 네트워크) 뒤에서 서로 다른 API 키로 호출하면 서로 영향을 주지 않습니다.
- 그러므로 처리량을 늘리고 싶다면 인스턴스를 늘릴 것이 아니라 별도의 API 키를 발급받아 분리해야 합니다.

4) 초과 시 상태 코드: 429
토큰이 없는 상태에서 요청이 들어오면 HTTP 상태 코드 **429 Too Many Requests**로 응답합니다. 429는 요청 자체가 잘못되었다는 뜻이 아니라 "지금은 너무 빠르다"는 뜻이므로, 클라이언트는 요청 내용을 고치지 말고 잠시 기다렸다가 그대로 다시 보내면 됩니다. 서버 장애를 뜻하는 5xx와 구분해서 처리하세요.

5) 재시도 안내 헤더: Retry-After
429 응답에는 `Retry-After` 헤더가 함께 옵니다. 값은 **초 단위 정수**입니다. 예를 들어 `Retry-After: 5`는 5초 뒤에 다시 시도하라는 뜻입니다. 클라이언트를 구현할 때는 임의의 간격으로 재시도하지 말고 이 헤더 값을 그대로 따르세요. 헤더를 무시하고 즉시 재시도하면 계속 429만 받게 되고 서버 부하만 커집니다. 여러 클라이언트가 동시에 같은 시각에 깨어나 몰리는 것을 막으려면 헤더 값에 약간의 무작위 지연(지터)을 더하는 것을 권장합니다.

6) 예외: admin 스코프 키
`admin` 스코프를 가진 API 키는 이 제한을 적용받지 않습니다. 즉 버킷 소모, 429 응답, `Retry-After` 대기가 모두 해당되지 않습니다. 운영·점검 목적의 키이므로 일반 애플리케이션 트래픽에 사용하지 마세요. 또한 개발 중 `admin` 키로만 테스트하면 제한 관련 코드 경로가 한 번도 실행되지 않아 429 처리 버그를 놓치게 됩니다. 재시도 로직을 검증할 때는 반드시 일반 스코프 키로 시험하세요.

정리하면, 평상시에는 초당 1건 페이스를 지키고, 짧은 몰림은 60건까지 허용되며, 429를 받으면 `Retry-After`가 알려주는 초만큼 기다렸다가 재시도하면 됩니다. 제한의 기준은 언제나 IP가 아니라 API 키입니다.
