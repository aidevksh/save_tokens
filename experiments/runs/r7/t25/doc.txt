우리 서비스의 요청 제한(rate limit)은 토큰 버킷(token bucket) 방식으로 동작합니다. 호출자마다 토큰이 담긴 양동이가 하나씩 있다고 생각하면 됩니다. 요청이 들어올 때마다 토큰을 하나 꺼내 쓰고, 토큰이 없으면 요청이 거절됩니다. 아래에서 여섯 가지 항목을 차례로 설명합니다.

1. 버킷 용량: 60

양동이에 최대로 담기는 토큰이 60개입니다. 즉 한 번에 몰아서 보낼 수 있는 요청이 최대 60건입니다. 오랫동안 쉬고 있었다면 토큰이 가득 차 있으므로 순간적으로 60건까지 통과하지만, 그 이상은 통과하지 않습니다. 이렇게 평소에는 여유를 두었다가 필요할 때 몰아 쓰는 것을 버스트(burst)라고 부릅니다. 용량은 이 버스트의 크기를 정하는 값이며, 토큰이 60개를 넘어 쌓이지는 않습니다.

2. 리필 속도: 초당 1개

소모된 토큰은 초당 1개씩 다시 채워집니다. 따라서 장기적으로 유지 가능한 평균 처리량은 초당 1회입니다. 용량 60과 함께 보면 "평소에는 초당 1회, 아껴 두었다면 최대 60회까지 한꺼번에" 라는 뜻이 됩니다. 예를 들어 토큰을 모두 써서 0이 되었다면 1초 뒤에 1건, 10초 뒤에는 10건을 보낼 수 있고, 완전히 다시 채워지려면 60초가 걸립니다.

3. 집계 단위: API 키 (IP 주소가 아님)

버킷은 IP 주소가 아니라 API 키 단위로 관리됩니다. 이 차이는 실무에서 중요합니다.

- 같은 서버에서 서로 다른 API 키로 호출하면 각각 별도의 버킷을 사용하므로 서로 영향을 주지 않습니다.
- 반대로 여러 대의 서버나 여러 지역에 인스턴스를 띄워도 API 키가 같으면 하나의 버킷을 공유합니다. 서버를 늘린다고 한도가 늘어나지 않습니다.
- 프록시나 NAT 뒤에 있어서 출발지 IP가 같아지는 상황이라도 키가 다르면 서로 제한을 나눠 쓰지 않습니다.

따라서 한도를 늘리고 싶다면 인스턴스를 늘리는 것이 아니라 키를 분리하거나 한도 상향을 요청해야 합니다.

4. 초과 시 상태 코드: 429

토큰이 없는 상태에서 요청이 들어오면 HTTP 상태 코드 429 Too Many Requests 를 돌려줍니다. 429는 요청 자체가 잘못되었다는 뜻이 아니라 "지금은 너무 빠르니 잠시 뒤에 다시 오라"는 뜻입니다. 400번대 다른 오류(예: 400, 401, 403)처럼 요청 내용을 고쳐야 하는 것이 아니므로, 클라이언트에서는 같은 요청을 그대로 다시 보내면 됩니다. 다만 즉시 재시도하면 다시 429를 받게 되므로 아래 헤더를 참고해야 합니다.

5. 재시도 안내 헤더: Retry-After (초 단위 정수)

429 응답에는 Retry-After 헤더가 함께 옵니다. 값은 초 단위 정수입니다. 예를 들어

    HTTP/1.1 429 Too Many Requests
    Retry-After: 5

라면 5초 뒤에 다시 시도하라는 뜻입니다. 구현할 때는 이 값을 파싱해서 그만큼 기다린 뒤 재시도하도록 만드십시오. 값을 무시하고 즉시 재시도하거나 임의의 간격으로 반복하면 429만 계속 쌓입니다. 실무에서는 Retry-After 값을 기본 대기 시간으로 삼고, 여러 인스턴스가 동시에 깨어나 다시 몰리는 것을 막기 위해 약간의 무작위 지연(지터)을 더하는 방식을 권장합니다. 참고로 Retry-After 는 날짜 형식도 허용하는 표준 헤더이지만, 우리 서비스는 초 단위 정수만 사용합니다.

6. 예외: admin 스코프 키

admin 스코프를 가진 API 키는 위 제한을 적용받지 않습니다. 용량과 리필 속도의 영향을 받지 않고, 429도 반환되지 않습니다. 운영·관리 목적의 작업이 제한에 걸려 막히는 것을 피하기 위한 예외입니다.

주의할 점은, 이 예외 때문에 개발 중 테스트가 왜곡되기 쉽다는 것입니다. admin 키로 확인하면 제한이 전혀 걸리지 않아 정상으로 보이지만, 실제 서비스에서 일반 키를 쓰는 클라이언트는 429를 받습니다. 재시도 로직을 검증할 때는 반드시 일반 스코프 키로 테스트하십시오. 또한 admin 키는 제한이 없는 만큼 유출 시 영향이 크므로 취급에 주의해야 합니다.

정리하면, 클라이언트를 만들 때 지켜야 할 것은 세 가지입니다. 첫째, 평균 초당 1회를 넘기지 않도록 호출 속도를 설계합니다. 둘째, 429를 오류로 취급해 실패 처리하지 말고 Retry-After 만큼 기다린 뒤 재시도합니다. 셋째, 한도는 API 키 단위로 공유되므로 서버 대수가 아니라 키 기준으로 사용량을 계산합니다.
