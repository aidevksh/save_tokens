웹훅(Webhook) 전달 명세 안내 — 신입 백엔드 개발자용
=====================================================

0. 전체 그림
------------
주문 도메인에서 상태 변화가 생기면 이벤트 버스에 이벤트가 하나 올라갑니다.
전달기(deliverer)는 그 이벤트를 구독 중인 엔드포인트마다 하나씩 HTTP POST 로 보냅니다.

  주문 도메인 → 이벤트 버스 → 전달기 → (엔드포인트 A / B / C 로 각각 POST)

엔드포인트는 팀별로 등록하며, 한 팀이 여러 개를 둘 수 있습니다.
전달기는 엔드포인트마다 독립된 큐를 쓰기 때문에, 어떤 엔드포인트 하나가 느리거나 죽어 있어도
다른 엔드포인트의 전달은 그것 때문에 밀리지 않습니다.

용어 두 가지를 먼저 구분해 두세요. 이 문서 전체가 이 구분 위에 서 있습니다.

  - 이벤트(event) : 도메인에서 발생한 사실 하나
  - 전달(delivery) : 그 이벤트를 엔드포인트 하나에 보내는 시도 하나

이벤트 1건이 엔드포인트 3개에 나가면 전달은 3건입니다.
실패와 재시도는 이벤트 단위가 아니라 **전달 단위**로 셉니다. 즉 엔드포인트 A 로 가는 전달이
실패해도 엔드포인트 B 로 가는 전달의 재시도 횟수에는 아무 영향이 없습니다.


수신 측이 알아야 할 열 가지 규약
================================

1. 재시도 횟수
--------------
수신 서버가 2xx 를 돌려주지 않으면 전달기가 최대 5회까지 다시 보냅니다.
5회를 모두 실패하면 그 이벤트는 폐기되고, 전달 로그에 `dropped` 로 남습니다.
폐기된 뒤에는 전달기가 알아서 다시 보내지 않습니다. 되살리려면 10번의 재전송 API 를 씁니다.

  ▶ 실무 포인트: 2xx 가 아닌 응답은 전부 실패입니다. 3xx 리다이렉트도 성공이 아닙니다.
    본문을 정상적으로 받았다면 반드시 2xx 를 돌려주세요.

2. 백오프
---------
재시도 간격은 지수 백오프입니다. 첫 간격이 2초이고, 실패할 때마다 2배로 늘어나며,
상한은 64초입니다. 간격에 무작위 흔들림(jitter)은 넣지 않습니다.

  2초 → 4초 → 8초 → 16초 → 32초 (이후로도 이어진다면 64초에서 멈춤)

jitter 가 없다는 말은 간격이 예측 가능하다는 뜻입니다. 장애가 나면 여러 이벤트의 재시도가
같은 시점에 몰려 들어올 수 있으니, 수신 서버 쪽 용량을 잡을 때 이 점을 감안하세요.

3. 서명 헤더
------------
모든 요청에 `X-Signature` 헤더가 붙습니다.
값은 **요청 본문 전체**를 **엔드포인트 비밀키**로 HMAC-SHA256 한 결과의 16진수 문자열입니다.

수신 측은 본문을 **파싱하기 전에** 이 값을 먼저 검증해야 합니다. 순서가 중요합니다.
검증 전에 JSON 파싱부터 하면, 정체불명의 입력을 파서에 그대로 먹이는 셈이 됩니다.
서명 계산에 쓰는 것은 파싱된 객체가 아니라 원본 바이트 그대로임에 주의하세요.

4. 타임아웃
-----------
수신 서버가 10초 안에 응답 헤더를 보내지 않으면 실패로 처리합니다.
연결 타임아웃과 읽기 타임아웃을 따로 두지 않고 전체를 10초로 잽니다.

  ▶ 실무 포인트: 무거운 처리를 요청 처리 안에서 동기로 돌리지 마세요.
    받자마자 큐에 넣고 곧바로 2xx 를 돌려준 뒤, 실제 처리는 비동기로 하는 편이 안전합니다.

5. 중복 전달
------------
전달 보장 수준은 at-least-once 입니다. 즉 "최소 한 번"은 가지만, 두 번 이상 도착할 수도 있습니다.
같은 이벤트가 중복으로 올 수 있으므로 수신 측은 본문의 `event_id` 로 멱등(idempotent) 처리를
해야 합니다. 이미 처리한 `event_id` 라면 다시 처리하지 말고 그대로 2xx 를 돌려주면 됩니다.

  ▶ 왜 중복이 생기나: 수신 서버가 처리는 끝냈는데 응답이 늦어 타임아웃이 나면,
    전달기 입장에서는 실패이므로 재시도합니다. 그래서 같은 이벤트가 또 옵니다.

6. 순서 보장
------------
이벤트 순서는 보장하지 않습니다. 나중에 발생한 이벤트가 먼저 도착할 수 있습니다.
따라서 도착 순서를 신뢰하지 말고, 본문의 `occurred_at` 을 기준으로 정렬해서 판단해야 합니다.

  ▶ 실무 포인트: 같은 주문에 대해 `order.updated` 가 `order.created` 보다 먼저 도착할 수
    있습니다. 상태를 덮어쓸 때는 저장된 `occurred_at` 보다 오래된 이벤트인지 확인하고,
    오래된 것이면 무시하세요.

7. 페이로드 크기 상한
---------------------
본문은 256KB 를 넘지 않습니다.
넘는 경우에는 본문 대신 `payload_url` 필드가 들어가고, 수신 측이 그 주소에서 직접
내려받아야 합니다. 즉 수신 코드는 두 가지 형태를 모두 처리할 수 있어야 합니다.

  - 일반 : `data` 안에 실제 내용이 들어 있음
  - 초과 : `payload_url` 이 들어 있고, 그 주소를 따로 GET 해서 내용을 가져와야 함

8. 이벤트 타입
--------------
현재 보내는 타입은 세 가지입니다.

  - `order.created`   주문 생성
  - `order.updated`   주문 변경
  - `order.canceled`  주문 취소

구독하지 않은 타입은 애초에 전달되지 않습니다. 그래도 수신 코드는 모르는 타입이 들어왔을 때
에러를 내지 말고 조용히 무시(2xx 응답)하도록 짜 두는 편이 좋습니다. 나중에 타입이 늘어나도
안전합니다.

9. 자동 비활성화
----------------
한 엔드포인트에서 다음 중 하나에 해당하면 그 엔드포인트를 자동으로 비활성화하고
관리자에게 메일을 보냅니다.

  - 연속 실패가 100회에 이른 경우
  - 실패 상태가 7일 이어진 경우

비활성화되면 그 엔드포인트로는 더 이상 전달이 나가지 않습니다. 배포 사고나 장기 점검으로
수신 서버를 오래 내려두면 여기에 걸릴 수 있으니, 복구 후에는 콘솔에서 엔드포인트가
살아 있는지 확인하세요.

10. 재전송 API
--------------
지난 이벤트를 다시 보내고 싶으면 아래를 호출합니다.

  POST /webhooks/{id}/redeliver

  - 대상 : 최근 30일치 이벤트
  - 한도 : 한 번 호출에 최대 100건

`dropped` 로 폐기된 이벤트를 되살리거나, 수신 측 버그로 잘못 처리한 구간을 다시 받을 때
사용합니다. 30일이 지난 이벤트는 재전송할 수 없으므로, 사고를 늦게 발견할수록 복구 폭이
좁아진다는 점을 기억하세요. 재전송으로 들어온 것도 결국 중복 전달이므로 5번의 멱등 처리가
그대로 필요합니다.


전달 로그
=========
전달 로그는 관리 콘솔의 **전달 탭**에서 볼 수 있고, 다음 필드를 담습니다.

| 필드 | 뜻 |
|---|---|
| `delivery_id` | 전달 시도 하나의 식별자 |
| `event_id` | 원본 이벤트 식별자. 재시도해도 값이 같습니다 |
| `attempt` | 몇 번째 시도인지. 1 부터 셉니다 |
| `status_code` | 수신 서버가 준 HTTP 상태 코드. 타임아웃이면 비어 있습니다 |
| `duration_ms` | 요청을 보내고 응답 헤더를 받기까지 걸린 밀리초 |
| `result` | `ok` / `retrying` / `dropped` 셋 중 하나 |

디버깅할 때는 `event_id` 로 묶어서 보면 한 이벤트의 시도 전체(attempt 1..5)가 한눈에 들어옵니다.
`status_code` 가 비어 있으면 응답 자체가 오지 않은 것, 즉 타임아웃입니다.


본문 예시
=========
```json
{
  "event_id": "evt_01H9Z2",
  "type": "order.created",
  "occurred_at": "2026-03-14T05:21:09Z",
  "data": {"order_id": "ord_8812", "amount": 42900, "currency": "KRW"}
}
```

  - `event_id`    : 멱등 처리의 키 (5번)
  - `type`        : 이벤트 타입 (8번)
  - `occurred_at` : 정렬 기준 (6번)
  - `data`        : 실제 내용. 256KB 를 넘으면 이 자리 대신 `payload_url` (7번)


비밀키 관리
===========
비밀키는 엔드포인트를 등록할 때 **한 번만** 보여주고 이후에는 다시 볼 수 없습니다.
받은 즉시 안전한 곳(비밀 관리 저장소 등)에 보관하세요.

분실하면 콘솔에서 회전(rotate)해야 합니다. 회전 직후 5분 동안은 옛 키와 새 키로 만든 서명을
둘 다 받아 줍니다. 이 5분이 무중단 교체를 위한 여유 구간입니다.

  회전 → (5분간 옛 키·새 키 모두 유효) → 이 사이에 수신 측 배포를 끝냄 → 새 키만 유효

회전 이력도 전달 로그와 같은 탭(전달 탭)에서 확인할 수 있습니다.


수신 서버 구현 체크리스트
=========================
1. 본문을 원본 바이트 그대로 읽어 `X-Signature` 를 먼저 검증한다 (3번)
2. 검증에 통과하면 파싱하고, `event_id` 로 이미 처리한 건인지 확인한다 (5번)
3. 처리 대상이면 큐에 넣고 즉시 2xx 를 돌려준다 — 10초 안에 (4번, 1번)
4. 상태를 반영할 때는 `occurred_at` 으로 순서를 판단한다 (6번)
5. `payload_url` 이 있으면 별도로 내려받아 처리한다 (7번)
6. 모르는 `type` 은 에러 없이 무시한다 (8번)
7. 장애로 오래 실패하면 자동 비활성화될 수 있으니 복구 후 콘솔을 확인한다 (9번)
8. 놓친 구간은 30일 이내에 재전송 API 로 복구한다 (10번)
