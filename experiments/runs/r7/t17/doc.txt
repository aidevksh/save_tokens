요청 제한(Rate Limit) 동작 설명

우리 서비스는 토큰 버킷(token bucket) 방식으로 요청 수를 제한합니다. 각 클라이언트는 토큰이 담긴 양동이(버킷)를 하나 가진다고 생각하면 됩니다. 요청을 한 번 보낼 때마다 버킷에서 토큰 1개를 꺼내 쓰고, 토큰이 없으면 요청이 거절됩니다. 아래 여섯 가지가 이 동작을 결정하는 전부입니다.

1. 버킷 용량: 60

버킷에 담을 수 있는 토큰의 최대 개수가 60개입니다. 즉 잠시 쉬었다가 한꺼번에 몰아서 보낼 수 있는 요청은 최대 60건입니다. 이것을 버스트(burst) 허용량이라고 부릅니다. 아무리 오래 쉬어도 61개가 되지는 않습니다. 용량은 상한선이라서 그 위로는 쌓이지 않습니다.

2. 리필 속도: 초당 1개

버킷은 1초에 토큰 1개씩 다시 채워집니다. 비어 있던 버킷이 가득 차려면 60초가 걸립니다. 이 값이 곧 장기 평균 허용 속도이기도 합니다. 계속 요청을 보내는 상황이라면 결국 초당 1건 페이스로 수렴합니다. 버스트 60건은 어디까지나 미리 아껴둔 토큰을 쓰는 것일 뿐, 지속 처리량을 올려주지는 않습니다.

정리하면 이렇습니다.
- 짧은 순간: 최대 60건까지 몰아서 가능
- 지속적으로: 초당 1건

3. 집계 단위: API 키

제한은 API 키 하나당 하나의 버킷으로 계산합니다. IP 주소 기준이 아닙니다. 이 차이가 실무에서 자주 혼동을 부르니 두 가지만 기억하세요.

- 서로 다른 서버 여러 대가 같은 API 키를 쓰면, 그 서버들이 버킷 하나를 나눠 씁니다. 서버를 늘려도 총 허용량은 늘지 않습니다.
- 같은 장비(같은 IP)에서 서로 다른 API 키로 요청하면, 각 키가 독립된 버킷을 가집니다. 서로 영향을 주지 않습니다.

따라서 처리량을 늘리고 싶다면 인스턴스를 늘릴 게 아니라 키를 분리하거나 상향 요청을 해야 합니다.

4. 초과 시 상태 코드: 429

버킷이 비었을 때 들어온 요청은 처리하지 않고 HTTP 429 Too Many Requests 로 응답합니다. 429는 "요청 자체는 올바른데 지금은 너무 많다"는 뜻입니다. 400번대이지만 요청 내용이 잘못된 것이 아니므로, 요청을 고칠 필요 없이 그대로 다시 보내면 됩니다. 클라이언트 코드에서는 4xx를 전부 뭉뚱그려 실패 처리하지 말고 429는 재시도 대상으로 따로 분기해 주세요.

5. 재시도 안내 헤더: Retry-After

429 응답에는 `Retry-After` 헤더가 함께 실려 옵니다. 값은 초 단위 정수입니다.

예: `Retry-After: 5` → 5초 뒤에 다시 시도하면 됩니다.

날짜 형식(HTTP-date)이 아니라 정수 초라는 점에 주의하세요. 파싱할 때 그냥 정수로 읽으면 됩니다. 이 값은 토큰이 다시 생길 때까지 남은 시간을 알려주는 것이므로, 임의로 정한 간격으로 재시도하는 것보다 이 헤더를 따르는 편이 정확하고 서버에도 부담이 적습니다. 헤더를 무시하고 즉시 재시도하면 429만 반복해서 받게 됩니다.

6. 예외: admin 스코프 키

`admin` 스코프를 가진 API 키는 요청 제한을 적용받지 않습니다. 버킷 소모도, 429 응답도 없습니다. 운영 도구나 내부 배치 작업처럼 제한을 걸면 곤란한 용도를 위한 것입니다.

주의할 점은, 개발 중에 admin 키로 테스트하면 제한 동작을 한 번도 마주치지 않는다는 것입니다. 그 상태로 배포하면 일반 키를 쓰는 실제 환경에서 처음으로 429를 만나게 됩니다. 429 처리 로직을 검증할 때는 반드시 일반 스코프 키로 테스트하세요.

클라이언트 구현 체크리스트

- 429 응답을 별도로 감지한다.
- `Retry-After` 값을 초로 읽어 그만큼 기다린 뒤 재시도한다.
- 재시도 횟수 상한을 두어 무한 반복을 막는다.
- 여러 인스턴스가 같은 키를 공유한다면 전체 합산이 초당 1건 페이스를 넘지 않도록 호출 측에서 조절한다.
- 제한 동작 테스트는 admin이 아닌 일반 키로 한다.
