요청 제한(Rate Limit) 동작 명세 — 신입 개발자용 설명

이 서비스는 "토큰 버킷(token bucket)" 방식으로 요청 수를 제한합니다.
요청을 하나 보낼 때마다 버킷에서 토큰을 하나 꺼내 쓰고, 토큰이 없으면 요청이 거절됩니다.


1. 버킷 용량 = 60

버킷에 담을 수 있는 토큰의 최대 개수가 60개입니다.
즉 토큰이 가득 찬 상태라면 순간적으로 60번의 요청을 연속으로 보낼 수 있습니다.
이것을 "버스트(burst) 허용량"이라고 부릅니다. 평소에 요청을 보내지 않고 쉬었더라도
토큰은 60개를 넘어서 쌓이지 않습니다.


2. 리필 속도 = 초당 1개

써서 없어진 토큰은 1초에 1개씩 다시 채워집니다.
따라서 장기적으로 유지 가능한 평균 요청 속도는 초당 1회입니다.
60개를 한꺼번에 소진했다면, 완전히 다시 가득 차기까지 60초가 걸립니다.
1초를 기다리면 1번, 10초를 기다리면 10번 보낼 수 있는 식입니다.

용량(60)은 "한 번에 몰아 쓸 수 있는 양", 리필 속도(초당 1개)는
"꾸준히 쓸 수 있는 양"을 정한다고 이해하면 됩니다.


3. 집계 단위 = API 키 (IP 주소가 아님)

버킷은 API 키마다 하나씩 따로 존재합니다. IP 주소 기준이 아닙니다.

- 같은 API 키를 여러 서버·여러 IP에서 나눠 써도 버킷은 하나이므로 한도를 공유합니다.
- 반대로 같은 사무실(같은 IP)에서 서로 다른 API 키로 호출하면 서로 영향을 주지 않습니다.

그러므로 여러 인스턴스에서 같은 키를 쓰는 구조라면, 인스턴스 수만큼
한도가 늘어나지 않는다는 점을 설계 단계에서 감안해야 합니다.


4. 초과 시 상태 코드 = 429

토큰이 없는 상태에서 요청이 들어오면 서버는 HTTP 상태 코드 429
(Too Many Requests)를 돌려줍니다.
클라이언트 코드에서는 이 429를 4xx 일반 오류와 똑같이 처리하면 안 됩니다.
요청 자체가 잘못된 것이 아니라 "지금은 너무 빠르다"는 뜻이므로,
잠시 뒤 같은 요청을 그대로 재시도하면 성공합니다.


5. 재시도 안내 헤더 = Retry-After (초 단위 정수)

429 응답에는 Retry-After 헤더가 함께 들어옵니다.
값은 초 단위 정수이며(예: `Retry-After: 5`), "이만큼 기다린 뒤 다시 보내라"는 뜻입니다.

권장 처리 방식:
- 429를 받으면 Retry-After 값만큼 대기한 뒤 재시도한다.
- 임의로 짧은 간격을 정해 즉시 재시도하지 않는다. 오히려 복구가 늦어집니다.
- 재시도 횟수 상한을 두고, 그래도 실패하면 오류로 처리한다.


6. 예외 = admin 스코프 키

admin 스코프를 가진 API 키는 요청 제한을 적용받지 않습니다.
토큰 소모 없이 호출할 수 있고 429도 발생하지 않습니다.
운영·관리 목적의 작업이 제한에 걸려 막히는 것을 막기 위한 장치입니다.

다만 일반 서비스 트래픽을 admin 키로 우회해서는 안 됩니다.
제한이 없다는 것은 곧 실수로 서버에 과부하를 줄 수 있다는 뜻이기도 하므로,
admin 키는 용도를 한정해 사용하고 유출되지 않도록 특히 조심해서 보관해야 합니다.
