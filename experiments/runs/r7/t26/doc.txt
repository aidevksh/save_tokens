요청 제한(Rate Limit) 동작 설명

이 서비스는 토큰 버킷(token bucket) 방식으로 요청을 제한합니다. 각 사용 주체마다 토큰이 담긴 양동이가 하나 있고, 요청 한 건마다 토큰 하나를 씁니다. 토큰이 없으면 요청이 거절됩니다.

1. 버킷 용량: 60
양동이에 담을 수 있는 토큰의 최대 개수가 60개입니다. 즉 토큰이 가득 찬 상태라면 순간적으로 최대 60건까지 연속 요청을 보낼 수 있습니다. 이것이 순간 폭주(burst) 허용치입니다. 토큰이 이미 가득 차 있으면 그 위로 더 쌓이지는 않습니다.

2. 리필 속도: 초당 1개
비워진 토큰은 1초에 1개씩 다시 채워집니다. 따라서 장기적으로 지속 가능한 평균 요청 속도는 초당 1건입니다. 60건을 한 번에 소진했다면 완전히 회복되기까지 60초가 걸리고, 1초 기다릴 때마다 1건씩 다시 보낼 수 있습니다.

3. 집계 단위: API 키
제한은 API 키 단위로 계산합니다. IP 주소 기준이 아닙니다. 그래서 같은 서버에서 여러 API 키로 요청하면 각 키가 별도의 양동이를 가지며, 반대로 한 API 키를 여러 서버나 여러 IP에서 나눠 쓰면 그 사용량이 모두 합산됩니다. 클라이언트를 늘려도 키가 같으면 한도가 늘어나지 않는다는 점에 주의하세요.

4. 초과 시 상태 코드: 429
토큰이 없는 상태에서 요청하면 HTTP 429 (Too Many Requests) 응답이 돌아옵니다. 이는 요청 내용이 잘못되었다는 뜻이 아니라 지금은 때가 이르다는 뜻이므로, 400번대 오류라도 요청을 고칠 것이 아니라 잠시 후 같은 요청을 다시 보내면 됩니다.

5. 재시도 안내 헤더: Retry-After
429 응답에는 Retry-After 헤더가 함께 옵니다. 값은 초 단위 정수이며, 이만큼 기다린 뒤 재시도하라는 의미입니다. 예를 들어 `Retry-After: 5` 는 5초 후에 다시 보내라는 뜻입니다. 클라이언트는 이 값을 읽어 대기하도록 구현하세요. 헤더를 무시하고 즉시 재시도하면 429만 반복해서 받게 됩니다.

6. 예외: admin 스코프 키
admin 스코프를 가진 API 키는 위 제한을 적용받지 않습니다. 토큰 소모나 429 응답 없이 요청할 수 있습니다. 다만 이런 키는 보호 장치가 없는 만큼 운영 도구 등 꼭 필요한 곳에만 쓰고, 일반 서비스 트래픽에는 사용하지 마세요.

구현 시 체크리스트
- 429를 정상적인 흐름의 일부로 처리하고, Retry-After 값만큼 대기 후 재시도한다.
- 평균 초당 1건을 넘지 않도록 호출 쪽에서 속도를 조절한다.
- 한도를 나누려면 IP가 아니라 API 키를 분리해야 한다.
