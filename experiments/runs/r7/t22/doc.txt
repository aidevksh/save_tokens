요청 제한(Rate Limit) 동작 명세

신입 백엔드 개발자를 위한 설명 문서입니다. 우리 서비스가 과도한 요청을 어떻게 막는지, 그리고 클라이언트가 그 상황에서 무엇을 해야 하는지를 설명합니다.

--------------------------------------------------
1. 버킷 용량: 60
--------------------------------------------------
우리 서비스는 "토큰 버킷(token bucket)" 방식을 씁니다. 요청 한 건마다 버킷에서 토큰 하나를 꺼내 쓴다고 생각하면 됩니다.

버킷의 최대 용량은 60개입니다. 즉 한동안 요청을 전혀 보내지 않아 버킷이 가득 찬 상태라면, 순간적으로 최대 60건의 요청을 연속해서 보낼 수 있습니다. 이것을 "버스트(burst) 허용량"이라고 부릅니다.

주의할 점은 버킷이 60을 넘어서 쌓이지는 않는다는 것입니다. 한 시간을 쉬든 하루를 쉬든 모아둘 수 있는 최대치는 60개입니다.

--------------------------------------------------
2. 리필 속도: 초당 1개
--------------------------------------------------
비어 가는 버킷은 초당 1개씩 다시 채워집니다.

이는 장기적인 평균 처리량이 초당 1회 요청(60 RPM)이라는 뜻입니다. 버킷 용량 60은 어디까지나 일시적인 몰림을 흡수하기 위한 여유분이고, 지속적으로 보낼 수 있는 속도는 리필 속도가 결정합니다.

예를 들어 가득 찬 버킷에서 60건을 한 번에 소진했다면, 그 직후에는 1초에 1건 꼴로만 요청이 통과합니다. 버킷을 다시 60까지 채우려면 약 60초가 필요합니다.

--------------------------------------------------
3. 집계 단위: API 키 (IP 주소가 아님)
--------------------------------------------------
버킷은 API 키 하나당 하나씩 관리됩니다. IP 주소 기준이 아닙니다.

실무에서 이 차이는 꽤 중요합니다.

- 같은 API 키를 여러 서버(여러 IP)에서 나눠 쓰면, 그 서버들이 하나의 버킷을 공유합니다. 서버를 늘려도 총 허용량은 늘어나지 않습니다.
- 반대로 같은 IP에서 서로 다른 API 키로 요청을 보내면, 각 키가 독립된 버킷을 가지므로 서로 영향을 주지 않습니다.
- NAT나 공용 프록시 뒤에 있는 여러 사용자가 서로의 한도를 깎아먹는 문제도 발생하지 않습니다.

따라서 트래픽을 늘려야 한다면 인스턴스를 늘릴 것이 아니라 키 발급 또는 한도 상향을 검토해야 합니다.

--------------------------------------------------
4. 초과 시 상태 코드: 429
--------------------------------------------------
버킷에 남은 토큰이 없는 상태에서 요청이 들어오면 서버는 HTTP 429 (Too Many Requests) 를 반환합니다.

429는 "요청 자체가 잘못됐다"는 뜻이 아니라 "지금은 너무 빠르니 나중에 다시 오라"는 뜻입니다. 그러므로 클라이언트 코드에서 429는 4xx 계열의 다른 오류(400, 401, 403 등)와 다르게 처리해야 합니다. 다른 4xx는 그대로 재시도해도 결과가 같지만, 429는 시간이 지나면 성공합니다.

--------------------------------------------------
5. 재시도 안내 헤더: Retry-After (초 단위 정수)
--------------------------------------------------
429 응답에는 Retry-After 헤더가 함께 실려 옵니다. 값은 초 단위 정수입니다.

    HTTP/1.1 429 Too Many Requests
    Retry-After: 5

위 예시는 "5초 뒤에 다시 시도하라"는 의미입니다.

클라이언트를 만들 때는 이 값을 반드시 읽어서 그만큼 기다린 뒤 재시도하십시오. 헤더를 무시하고 즉시 재시도하는 반복문은 429만 계속 받아내며 서버와 클라이언트 양쪽의 자원을 낭비합니다.

권장 처리 방식:

- Retry-After 값만큼 대기한 뒤 재시도한다.
- 재시도 횟수에 상한을 두고, 그 이상은 실패로 처리한다.
- 여러 워커가 동시에 429를 받은 경우 모두가 같은 시각에 깨어나지 않도록 약간의 무작위 지연(지터)을 더한다.

--------------------------------------------------
6. 예외: admin 스코프 키
--------------------------------------------------
admin 스코프를 가진 API 키는 요청 제한에서 제외됩니다. 버킷을 소비하지 않고 429도 받지 않습니다.

운영 도구나 내부 배치 작업처럼 제한에 걸리면 곤란한 용도를 위한 장치입니다. 다만 제한이 없다는 것은 실수로 만든 무한 루프가 그대로 서비스에 부하로 전달된다는 뜻이기도 합니다. admin 키는 꼭 필요한 곳에만 쓰고, 일반 애플리케이션 트래픽에는 사용하지 마십시오.

--------------------------------------------------
요약
--------------------------------------------------
- 평상시: 초당 1건 페이스를 유지하면 제한에 걸리지 않습니다.
- 일시적 몰림: 최대 60건까지는 한꺼번에 통과합니다.
- 걸렸을 때: 429와 Retry-After를 확인하고 그만큼 기다렸다가 재시도합니다.
- 한도는 API 키 단위이므로 서버 대수를 늘려도 늘어나지 않습니다.
- admin 스코프 키만 이 규칙의 예외입니다.
