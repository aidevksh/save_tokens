웹훅(Webhook) 전달 명세 — 신입 백엔드 개발자용 설명 문서
================================================================

0. 전체 흐름과 용어
----------------------------------------------------------------

주문 도메인에서 상태 변화가 생기면 이벤트 버스에 이벤트가 하나 올라갑니다.
전달기(deliverer)는 그 이벤트를 구독 중인 엔드포인트마다 하나씩 HTTP POST 로
보냅니다. 엔드포인트는 팀별로 등록하며, 한 팀이 여러 개를 둘 수 있습니다.

  주문 도메인 → 이벤트 버스 → 전달기 → (엔드포인트별 큐) → 수신 서버

먼저 두 단어를 구분해야 합니다. 이 문서 전체가 이 구분 위에 서 있습니다.

  - 이벤트(event): 도메인에서 발생한 "사실" 하나.
  - 전달(delivery): 그 이벤트를 엔드포인트 하나에 보내는 "시도" 하나.

이벤트 1건이 엔드포인트 3개에 나가면 전달은 3건입니다. 실패와 재시도는
이벤트 단위가 아니라 전달 단위로 셉니다. 즉 엔드포인트 A 로의 전달이 실패해도
엔드포인트 B 로의 전달과는 무관합니다.

전달기는 엔드포인트별로 독립된 큐를 씁니다. 그래서 한 엔드포인트가 느려도
다른 엔드포인트의 전달은 밀리지 않습니다. 반대로 말하면, 내 엔드포인트가
느리면 그 피해는 온전히 내 큐에만 쌓입니다.

아래 열 가지가 수신 측이 반드시 알아야 할 규약입니다.


1. 재시도 횟수
----------------------------------------------------------------

수신 서버가 2xx 를 돌려주지 않으면 전달기가 최대 5회까지 다시 보냅니다.
5회를 모두 실패하면 그 이벤트는 폐기되고, 전달 로그에 `dropped` 로 남습니다.

  - 성공 기준은 오직 2xx 입니다. 3xx, 4xx, 5xx 는 모두 실패로 봅니다.
  - 폐기된 이벤트는 자동으로 되살아나지 않습니다. 되살리려면
    아래 10번의 재전송 API 를 직접 호출해야 합니다.
  - 수신 서버에서 처리 중 오류가 났는데 200 을 돌려주면, 전달기는 성공으로
    보고 재시도하지 않습니다. 처리 실패는 반드시 비 2xx 로 알려야 합니다.


2. 백오프
----------------------------------------------------------------

재시도 간격은 지수 백오프입니다. 첫 간격이 2초이고, 실패할 때마다 2배로
늘어나며, 상한은 64초입니다. 간격에 무작위 흔들림(jitter)은 넣지 않습니다.

  간격: 2초 → 4초 → 8초 → 16초 → 32초 (상한 64초)

jitter 가 없다는 점이 실무에서 중요합니다. 대량 장애가 나서 많은 전달이 동시에
실패하면, 재시도도 정확히 같은 시각에 몰려 들어옵니다. 수신 서버가 복구되는
순간 재시도 폭풍을 맞을 수 있으므로, 수신 측에서 유량 제어를 고려하세요.


3. 서명 헤더
----------------------------------------------------------------

모든 요청에 `X-Signature` 헤더가 붙습니다. 값은 요청 본문 전체를 엔드포인트
비밀키로 HMAC-SHA256 한 결과의 16진수 문자열입니다.

수신 측은 본문을 파싱하기 전에 이 값을 먼저 검증해야 합니다. 순서가 규약입니다.
검증 전에 JSON 파싱부터 하면, 서명되지 않은 임의의 입력을 파서에 통과시키는
셈이 됩니다.

구현 시 주의점:

  - 서명 대상은 "요청 본문 전체" 원문 바이트입니다. 파싱했다가 다시 직렬화한
    문자열로 계산하면 공백·키 순서가 달라져 서명이 어긋납니다. 프레임워크에서
    raw body 를 그대로 얻을 수 있는 경로를 확보하세요.
  - 비교는 타이밍 공격에 안전한 상수 시간 비교 함수를 쓰세요.


4. 타임아웃
----------------------------------------------------------------

수신 서버가 10초 안에 응답 헤더를 보내지 않으면 실패로 처리합니다.
연결 타임아웃과 읽기 타임아웃을 따로 두지 않고 전체 10초로 잽니다.

기준은 "응답 헤더"입니다. 따라서 수신 측은 무거운 처리를 요청-응답 안에서
끝내려 하지 말고, 검증만 마친 뒤 큐에 넣고 곧바로 2xx 를 돌려주는 구조를
권장합니다. 10초를 넘기면 재시도가 걸리고, 이는 곧 중복 전달로 이어집니다.

타임아웃으로 실패한 전달은 전달 로그의 `status_code` 가 비어 있습니다.


5. 중복 전달
----------------------------------------------------------------

전달 보장 수준은 at-least-once 입니다. 즉 "최소 한 번"은 보장하지만
"정확히 한 번"은 보장하지 않습니다. 같은 이벤트가 두 번 이상 도착할 수 있습니다.

수신 측은 본문의 `event_id` 로 멱등 처리를 해야 합니다.

  - `event_id` 는 재시도해도 값이 같습니다. 반면 `delivery_id` 는 시도마다
    달라지므로 멱등 키로 쓰면 안 됩니다.
  - 흔한 구현: `event_id` 에 유니크 제약을 건 처리 이력 테이블을 두고,
    삽입이 충돌하면 이미 처리한 것으로 보고 2xx 를 돌려줍니다.
  - 중복은 예외 상황이 아니라 정상 동작입니다. 예컨대 수신 측이 처리는
    끝냈는데 응답이 10초를 넘겨 타임아웃 나면, 전달기는 실패로 보고 다시
    보냅니다.


6. 순서 보장
----------------------------------------------------------------

이벤트 순서는 보장하지 않습니다. 나중에 발생한 이벤트가 먼저 도착할 수 있으므로
수신 측은 본문의 `occurred_at` 을 기준으로 정렬해야 합니다.

  - 도착 순서를 발생 순서로 믿고 상태를 덮어쓰면 안 됩니다. 예를 들어
    `order.canceled` 가 먼저 도착하고 `order.updated` 가 나중에 도착하면,
    도착 순으로 처리했을 때 취소된 주문이 다시 살아납니다.
  - 안전한 패턴: 저장된 레코드의 `occurred_at` 보다 오래된 이벤트가 오면
    무시합니다(이 경우에도 응답은 2xx 로 돌려줍니다. 처리 대상이 아닐 뿐
    전달 자체는 성공이기 때문입니다).
  - 재시도와 백오프가 있으므로 역전은 드문 일이 아닙니다. 앞선 이벤트가
    2초·4초·8초 밀리는 동안 뒤 이벤트는 한 번에 성공할 수 있습니다.


7. 페이로드 크기 상한
----------------------------------------------------------------

본문은 256KB 를 넘지 않습니다. 넘는 경우 본문 대신 `payload_url` 필드가
들어가고, 수신 측이 그 주소에서 직접 내려받아야 합니다.

따라서 수신 측 파서는 두 갈래를 모두 처리해야 합니다.

  - `data` 가 들어 있는 일반 본문
  - `payload_url` 이 들어 있는 본문 → 해당 주소를 받아서 본문을 완성

`payload_url` 분기를 구현하지 않으면 평소에는 잘 돌다가 큰 주문 하나에서
갑자기 처리에 실패하는 형태로 문제가 드러납니다. 처음부터 함께 구현하세요.
또한 이 다운로드도 4번의 10초 응답 시간 안에 끝내려 하지 말고 비동기로
처리하는 편이 안전합니다.


8. 이벤트 타입
----------------------------------------------------------------

현재 보내는 타입은 세 가지입니다.

  - `order.created`   주문 생성
  - `order.updated`   주문 변경
  - `order.canceled`  주문 취소

구독하지 않은 타입은 전달되지 않습니다. 어떤 타입이 안 온다면 먼저 그
엔드포인트의 구독 설정을 확인하세요.

타입은 앞으로 늘어날 수 있으므로, 모르는 `type` 을 받았을 때 오류를 내며
비 2xx 를 돌려주지 말고, 조용히 무시하고 2xx 를 돌려주는 방어적 구현을
권장합니다. 그러지 않으면 새 타입 하나가 추가되는 순간 재시도가 쌓이고
9번의 자동 비활성화까지 갈 수 있습니다.


9. 자동 비활성화
----------------------------------------------------------------

한 엔드포인트에서 아래 둘 중 하나에 해당하면, 그 엔드포인트를 자동으로
비활성화하고 관리자에게 메일을 보냅니다.

  - 연속 실패가 100회에 이름
  - 실패 상태가 7일 이어짐

비활성화는 엔드포인트 단위입니다. 같은 팀의 다른 엔드포인트는 영향받지
않습니다. 비활성화된 동안 발생한 이벤트는 그 엔드포인트로 가지 않으므로,
복구한 뒤에는 10번의 재전송 API 로 공백을 메워야 합니다.


10. 재전송 API
----------------------------------------------------------------

`POST /webhooks/{id}/redeliver` 로 지난 이벤트를 다시 보낼 수 있습니다.

  - 대상 범위: 최근 30일치
  - 한 번 호출당: 최대 100건

30일이 넘은 이벤트는 되살릴 수 없습니다. 장애를 오래 방치하면 복구 불가능한
구간이 생긴다는 뜻이므로, 자동 비활성화 메일을 받으면 30일 안에 반드시
처리해야 합니다. 100건 상한이 있으므로 밀린 양이 많으면 나눠서 호출합니다.

재전송된 전달도 똑같이 at-least-once 이므로, 이미 처리한 이벤트가 다시 올 수
있습니다. 5번의 멱등 처리가 되어 있으면 안전합니다.


전달 로그
----------------------------------------------------------------

관리 콘솔의 전달 탭에서 볼 수 있습니다. 담기는 필드는 다음과 같습니다.

  delivery_id   전달 시도 하나의 식별자
  event_id      원본 이벤트 식별자. 재시도해도 값이 같습니다
  attempt       몇 번째 시도인지. 1 부터 셉니다
  status_code   수신 서버가 준 HTTP 상태 코드. 타임아웃이면 비어 있습니다
  duration_ms   요청을 보내고 응답 헤더를 받기까지 걸린 밀리초
  result        ok / retrying / dropped 셋 중 하나

디버깅할 때 읽는 법:

  - `status_code` 가 비어 있고 `duration_ms` 가 10000 근처면 4번 타임아웃입니다.
  - 같은 `event_id` 의 `attempt` 가 1..5 까지 늘어나며 `result` 가 마지막에
    `dropped` 면 1번의 5회 실패입니다.
  - `result` 가 `retrying` 이면 아직 재시도가 남아 있는 상태입니다.


본문 예시
----------------------------------------------------------------

{
  "event_id": "evt_01H9Z2",
  "type": "order.created",
  "occurred_at": "2026-03-14T05:21:09Z",
  "data": {"order_id": "ord_8812", "amount": 42900, "currency": "KRW"}
}

앞서 나온 규약이 이 본문 안에서 어떻게 쓰이는지 정리하면 이렇습니다.

  event_id     5번 멱등 처리의 키
  type         8번 이벤트 타입
  occurred_at  6번 정렬 기준
  data         7번에서 256KB 를 넘으면 이 자리가 payload_url 로 바뀝니다


비밀키 관리와 회전
----------------------------------------------------------------

비밀키는 엔드포인트를 등록할 때 한 번만 보여주고 이후에는 다시 볼 수 없습니다.
등록 시점에 안전한 보관소에 옮겨 두세요.

분실하면 콘솔에서 회전(rotate)해야 합니다. 회전 직후 5분 동안은 옛 키와 새 키로
만든 서명을 둘 다 받아 줍니다. 이 5분이 무중단 교체를 위한 창입니다.

  권장 절차
  1) 콘솔에서 회전을 실행하고 새 키를 받는다
  2) 5분 안에 수신 서버의 키를 새 키로 교체·배포한다
  3) 배포 후 전달 로그에서 2xx 가 정상적으로 찍히는지 확인한다

5분이 지나면 옛 키 서명은 더 이상 통과하지 않습니다. 교체가 늦으면 서명 검증
실패가 이어지고, 이는 곧 1번의 재시도와 9번의 자동 비활성화로 이어집니다.

회전 이력도 전달 로그와 같은 탭(전달 탭)에서 확인할 수 있습니다.


수신 측 구현 체크리스트
----------------------------------------------------------------

  [ ] raw body 를 보존한 뒤, 파싱 전에 X-Signature 를 상수 시간 비교로 검증  (3)
  [ ] event_id 유니크 제약으로 멱등 처리                                      (5)
  [ ] occurred_at 기준 정렬, 오래된 이벤트는 무시                             (6)
  [ ] payload_url 분기 구현                                                   (7)
  [ ] 모르는 type 은 무시하고 2xx 반환                                        (8)
  [ ] 무거운 처리는 큐로 넘기고 10초 안에 응답 헤더 반환                      (4)
  [ ] 처리 실패는 반드시 비 2xx 로 반환해 재시도를 유도                       (1)
  [ ] 재시도 몰림(jitter 없음)에 대비한 유량 제어                             (2)
  [ ] 자동 비활성화 알림 메일 수신처 확인 및 대응 절차 마련                   (9)
  [ ] 공백 구간은 30일 안에 재전송 API 로 복구                                (10)
