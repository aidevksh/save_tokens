웹훅 전달 명세 — 신입 개발자 안내

이 문서는 우리 서비스가 외부 엔드포인트로 웹훅을 보내는 방식과, 수신하는 쪽이
반드시 지켜야 할 규약을 정리한 것입니다.


0. 전체 그림
------------------------------------------------------------
주문 도메인에서 상태 변화가 생기면 이벤트 버스에 이벤트가 하나 올라갑니다.
전달기(deliverer)는 그 이벤트를 구독 중인 엔드포인트마다 하나씩 HTTP POST 로
보냅니다. 엔드포인트는 팀별로 등록하고, 한 팀이 여러 개를 둘 수 있습니다.
전달기는 엔드포인트별로 독립된 큐를 쓰므로, 한 엔드포인트가 느려도 다른
엔드포인트의 전달은 밀리지 않습니다.

용어를 먼저 구분해 두세요. 이 둘을 섞으면 로그와 지표를 잘못 읽게 됩니다.

  - 이벤트(event): 도메인에서 발생한 사실 하나.
  - 전달(delivery): 그 이벤트를 엔드포인트 하나에 보내는 시도 하나.

이벤트 1건이 엔드포인트 3개에 나가면 전달은 3건입니다.
실패와 재시도는 전달 단위로 셉니다.


1. 재시도 횟수
------------------------------------------------------------
수신 서버가 2xx 를 돌려주지 않으면 최대 5회까지 다시 보냅니다.
5회를 모두 실패하면 그 이벤트는 폐기되고, 전달 로그에 `dropped` 로 남습니다.
즉 수신 측이 계속 2xx 를 주지 못하면 그 이벤트는 결국 유실됩니다.
처리에 시간이 걸리는 작업이라면 먼저 2xx 로 접수만 응답하고 뒤에서
비동기로 처리하는 편이 안전합니다.


2. 백오프
------------------------------------------------------------
재시도 간격은 지수 백오프입니다.
첫 간격이 2초이고, 실패할 때마다 2배로 늘어나며, 상한은 64초입니다.
간격에 무작위 흔들림(jitter)은 넣지 않습니다. 간격이 결정적이므로
재시도가 언제 올지 예측할 수 있습니다.

  1차 재시도 후 2초 → 4초 → 8초 → 16초 → 32초 (이후 64초에서 상한)


3. 서명 헤더
------------------------------------------------------------
모든 요청에 `X-Signature` 헤더가 붙습니다.
값은 요청 본문 전체를 엔드포인트 비밀키로 HMAC-SHA256 한 결과의
16진수 문자열입니다.

중요: 수신 측은 본문을 파싱하기 전에 이 값을 먼저 검증해야 합니다.
검증 전에 JSON 파싱을 하면 검증되지 않은 데이터를 다루게 됩니다.
서명 계산에는 파싱된 객체가 아니라 수신한 원본 바이트를 그대로 써야 합니다.


4. 타임아웃
------------------------------------------------------------
수신 서버가 10초 안에 응답 헤더를 보내지 않으면 실패로 처리합니다.
연결 타임아웃과 읽기 타임아웃을 따로 두지 않고 전체 10초로 잽니다.
따라서 핸들러의 무거운 처리는 10초 안에 끝내거나, 접수만 하고
백그라운드로 넘겨야 합니다.


5. 중복 전달
------------------------------------------------------------
전달 보장 수준은 at-least-once 입니다.
같은 이벤트가 두 번 이상 도착할 수 있습니다. 수신 측은 본문의 `event_id` 로
멱등(idempotent) 처리를 해야 합니다.

`event_id` 는 재시도해도 값이 같으므로 중복 판별 키로 쓸 수 있습니다.
이미 처리한 `event_id` 를 저장해 두고, 다시 들어오면 실제 처리 없이
2xx 만 돌려주는 방식이 일반적입니다.


6. 순서 보장
------------------------------------------------------------
이벤트 순서는 보장하지 않습니다.
나중에 발생한 이벤트가 먼저 도착할 수 있으므로, 본문의 `occurred_at` 을
기준으로 정렬해야 합니다.

도착 순서를 믿고 상태를 덮어쓰면 오래된 이벤트가 최신 상태를 되돌릴 수
있습니다. 저장된 `occurred_at` 보다 오래된 이벤트는 무시하도록 만드세요.


7. 페이로드 크기 상한
------------------------------------------------------------
본문은 256KB 를 넘지 않습니다.
넘는 경우 본문 대신 `payload_url` 필드가 들어가고, 수신 측이 그 주소에서
직접 내려받아야 합니다.

수신 핸들러는 두 가지 형태를 모두 처리할 수 있어야 합니다.
`data` 가 들어 있는 일반 본문과, `payload_url` 만 들어 있는 본문입니다.


8. 이벤트 타입
------------------------------------------------------------
현재 보내는 타입은 세 가지입니다.

  - `order.created`
  - `order.updated`
  - `order.canceled`

구독하지 않은 타입은 전달되지 않습니다.
다만 타입은 앞으로 늘어날 수 있으므로, 모르는 타입이 오면 오류를 내지 말고
무시하고 2xx 를 돌려주는 편이 안전합니다.


9. 자동 비활성화
------------------------------------------------------------
한 엔드포인트에서 다음 중 하나에 해당하면 그 엔드포인트를 자동으로
비활성화하고 관리자에게 메일을 보냅니다.

  - 연속 실패가 100회에 이른 경우
  - 실패 상태가 7일 이어진 경우

비활성화되면 전달이 멈추므로, 배포 사고로 엔드포인트가 오래 죽어 있으면
복구 후에도 이벤트가 오지 않는 상황이 생깁니다. 이때는 콘솔에서 다시
활성화하고 10번의 재전송 API 로 밀린 이벤트를 받아야 합니다.


10. 재전송 API
------------------------------------------------------------
`POST /webhooks/{id}/redeliver` 로 지난 이벤트를 다시 보낼 수 있습니다.

  - 대상 범위: 최근 30일치
  - 한 번 호출 한도: 최대 100건

30일이 지난 이벤트는 다시 보낼 수 없으므로, 장애 복구는 30일 안에
마무리해야 합니다. 재전송으로 들어온 이벤트도 중복 전달과 같으므로
5번의 멱등 처리가 그대로 적용됩니다.


전달 로그
------------------------------------------------------------
관리 콘솔의 전달 탭에서 볼 수 있습니다. 담기는 필드는 다음과 같습니다.

| 필드 | 뜻 |
|---|---|
| `delivery_id` | 전달 시도 하나의 식별자 |
| `event_id` | 원본 이벤트 식별자. 재시도해도 값이 같습니다 |
| `attempt` | 몇 번째 시도인지. 1 부터 셉니다 |
| `status_code` | 수신 서버가 준 HTTP 상태 코드. 타임아웃이면 비어 있습니다 |
| `duration_ms` | 요청을 보내고 응답 헤더를 받기까지 걸린 밀리초 |
| `result` | `ok` / `retrying` / `dropped` 셋 중 하나 |

`status_code` 가 비어 있으면 응답 자체를 못 받은 것(타임아웃)이고,
값이 있는데 `result` 가 `retrying` 이면 2xx 가 아닌 응답을 받은 것입니다.


본문 예시
------------------------------------------------------------
{
  "event_id": "evt_01H9Z2",
  "type": "order.created",
  "occurred_at": "2026-03-14T05:21:09Z",
  "data": {"order_id": "ord_8812", "amount": 42900, "currency": "KRW"}
}


비밀키 관리
------------------------------------------------------------
비밀키는 엔드포인트를 등록할 때 한 번만 보여주고 이후에는 다시 볼 수
없습니다. 등록 시점에 안전한 곳에 보관하세요.

분실하면 콘솔에서 회전(rotate)해야 합니다. 회전 직후 5분 동안은 옛 키와
새 키로 만든 서명을 둘 다 받아 줍니다. 이 5분이 무중단 교체를 위한
시간이므로, 그 안에 수신 측 설정을 새 키로 바꿔야 합니다.
회전 이력도 전달 로그와 같은 탭에서 확인할 수 있습니다.


수신 측 구현 체크리스트
------------------------------------------------------------
  1. 원본 바이트로 `X-Signature` 를 먼저 검증한다 (3번)
  2. 10초 안에 응답 헤더를 보낸다. 무거운 처리는 비동기로 (4번)
  3. `event_id` 로 멱등 처리한다 (5번)
  4. `occurred_at` 으로 정렬하고 오래된 이벤트는 무시한다 (6번)
  5. `payload_url` 만 오는 본문도 처리한다 (7번)
  6. 모르는 타입은 무시하고 2xx 를 돌려준다 (8번)
  7. 접수에 성공하면 반드시 2xx 를 돌려준다. 아니면 5회 뒤 폐기된다 (1번)
