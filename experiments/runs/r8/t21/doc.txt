웹훅(Webhook) 전달 명세 — 신입 백엔드 개발자용 설명 문서
================================================================

이 문서는 우리 서비스가 외부(수신 측) 서버로 주문 관련 이벤트를 보내는 방식을
처음 접하는 사람이 이해할 수 있도록 정리한 것입니다. 수신 서버를 직접 만들거나,
전달이 실패했을 때 원인을 찾아야 하는 상황에서 기준으로 삼으세요.


0. 전체 그림
------------

1) 주문 도메인에서 상태 변화가 생깁니다. (주문 생성, 수정, 취소 등)
2) 그 변화가 "이벤트" 하나로 이벤트 버스에 올라갑니다.
3) "전달기"가 그 이벤트를 구독 중인 엔드포인트마다 하나씩 HTTP POST 로 보냅니다.

엔드포인트는 팀별로 등록하고, 한 팀이 여러 개를 둘 수 있습니다.
전달기는 엔드포인트마다 독립된 큐를 씁니다. 그래서 어떤 팀의 수신 서버가 느려도
다른 엔드포인트로 가는 전달은 그 영향을 받지 않고 그대로 나갑니다.


용어 두 개를 먼저 구분하세요
----------------------------

- 이벤트(event): 도메인에서 발생한 사실 하나. 예) "주문 ord_8812 가 생성되었다".
- 전달(delivery): 그 이벤트를 엔드포인트 하나에 보내는 시도 하나.

이벤트 1건이 엔드포인트 3개로 나가면 전달은 3건입니다.
실패와 재시도는 이벤트 단위가 아니라 **전달 단위**로 셉니다. 즉 엔드포인트 A 로 가는
전달이 실패해도 엔드포인트 B 의 재시도 횟수와는 아무 상관이 없습니다.


수신 측이 알아야 할 10가지 규약
================================

1. 재시도 횟수
--------------
수신 서버가 2xx 응답을 돌려주지 않으면 전달기가 최대 5회까지 다시 보냅니다.
5회를 모두 실패하면 그 이벤트는 폐기되고, 전달 로그에 `dropped` 로 남습니다.
폐기된 뒤에는 전달기가 알아서 다시 보내지 않으므로, 필요하면 10번의 재전송 API 를
써야 합니다.

2. 백오프
---------
재시도 간격은 지수 백오프입니다. 첫 간격이 2초이고, 실패할 때마다 2배로 늘어나며,
상한은 64초입니다. 즉 간격은 2초 → 4초 → 8초 → 16초 → 32초 순으로 늘어나고,
그 이상 늘어나야 하는 경우에도 64초를 넘지 않습니다.
간격에 무작위 흔들림(jitter)은 넣지 않습니다. 간격이 고정되어 있으므로 언제쯤
다시 올지 예측할 수 있습니다.

3. 서명 헤더
------------
모든 요청에 `X-Signature` 헤더가 붙습니다.
값은 요청 본문 전체를 해당 엔드포인트의 비밀키로 HMAC-SHA256 한 결과의
16진수 문자열입니다.

중요: 수신 측은 본문을 **파싱하기 전에** 이 값을 먼저 검증해야 합니다.
서명 검증은 원본 바이트 그대로에 대해 계산해야 하므로, JSON 으로 역직렬화한 뒤
다시 직렬화한 문자열로 검증하면 값이 달라져 실패할 수 있습니다.

4. 타임아웃
-----------
수신 서버가 10초 안에 응답 헤더를 보내지 않으면 전달기는 그 전달을 실패로 처리합니다.
연결 타임아웃과 읽기 타임아웃을 따로 두지 않고 전체를 10초로 잽니다.
따라서 수신 핸들러에서 무거운 작업을 동기로 처리하지 말고, 일단 빠르게 2xx 를
돌려준 뒤 뒤에서 처리하는 방식이 안전합니다.

5. 중복 전달
------------
전달 보장 수준은 at-least-once(최소 한 번) 입니다.
같은 이벤트가 두 번 이상 도착할 수 있습니다. 예를 들어 수신 측이 처리를 마쳤는데
응답이 늦어 타임아웃으로 잡히면, 전달기는 실패로 보고 다시 보냅니다.
그래서 수신 측은 본문의 `event_id` 를 기준으로 멱등(idempotent) 처리를 해야 합니다.
이미 처리한 `event_id` 가 또 오면 다시 처리하지 말고 2xx 만 돌려주면 됩니다.

6. 순서 보장
------------
이벤트 순서는 보장하지 않습니다. 나중에 발생한 이벤트가 먼저 도착할 수 있습니다.
따라서 도착 순서를 그대로 믿지 말고, 본문의 `occurred_at` 을 기준으로 정렬해서
판단해야 합니다. 예를 들어 이미 더 늦은 `occurred_at` 의 상태를 반영해 두었다면,
그보다 이른 이벤트가 뒤늦게 와도 덮어쓰지 않아야 합니다.

7. 페이로드 크기 상한
---------------------
본문은 256KB 를 넘지 않습니다.
넘는 경우에는 본문 대신 `payload_url` 필드가 들어가고, 수신 측이 그 주소에서
직접 내려받아야 합니다. 수신 핸들러는 두 가지 형태(본문에 데이터가 다 들어온 경우,
`payload_url` 만 들어온 경우)를 모두 처리할 수 있어야 합니다.

8. 이벤트 타입
--------------
현재 보내는 타입은 세 가지입니다.

- `order.created` — 주문 생성
- `order.updated` — 주문 변경
- `order.canceled` — 주문 취소

구독하지 않은 타입은 전달되지 않습니다. 필요한 타입을 엔드포인트 등록 시 구독해야
받을 수 있습니다.

9. 자동 비활성화
----------------
한 엔드포인트에서 다음 중 하나에 해당하면 그 엔드포인트를 자동으로 비활성화하고
관리자에게 메일을 보냅니다.

- 연속 실패가 100회에 이른 경우
- 실패 상태가 7일 이어진 경우

비활성화되면 그 엔드포인트로는 더 이상 전달이 나가지 않습니다. 수신 서버를 고친
뒤에는 콘솔에서 다시 활성화해야 하고, 그 사이 놓친 이벤트는 재전송 API 로
받아야 합니다.

10. 재전송 API
--------------
`POST /webhooks/{id}/redeliver` 로 지난 이벤트를 다시 보낼 수 있습니다.

- 대상: 최근 30일치
- 한 번 호출에 최대 100건

30일이 지난 이벤트는 재전송할 수 없으므로, 장애를 오래 방치하지 않는 것이
중요합니다. 재전송으로 온 요청도 일반 전달과 같은 형식이며 `event_id` 가 같으므로,
5번의 멱등 처리가 되어 있으면 중복 반영 걱정 없이 재전송을 쓸 수 있습니다.


전달 로그
=========

전달 로그는 관리 콘솔의 "전달" 탭에서 볼 수 있습니다. 담기는 필드는 다음과 같습니다.

| 필드 | 뜻 |
|---|---|
| `delivery_id` | 전달 시도 하나의 식별자 |
| `event_id` | 원본 이벤트 식별자. 재시도해도 값이 같습니다 |
| `attempt` | 몇 번째 시도인지. 1 부터 셉니다 |
| `status_code` | 수신 서버가 준 HTTP 상태 코드. 타임아웃이면 비어 있습니다 |
| `duration_ms` | 요청을 보내고 응답 헤더를 받기까지 걸린 밀리초 |
| `result` | `ok` / `retrying` / `dropped` 셋 중 하나 |

디버깅 요령:
- `status_code` 가 비어 있으면 수신 서버가 10초 안에 응답 헤더를 못 보낸 것입니다(타임아웃).
- 같은 `event_id` 로 `attempt` 가 여러 줄 있으면 재시도가 돈 것입니다.
- 마지막 줄의 `result` 가 `dropped` 이면 5회 재시도까지 모두 실패해 폐기된 것입니다.


본문 예시
=========

```json
{
  "event_id": "evt_01H9Z2",
  "type": "order.created",
  "occurred_at": "2026-03-14T05:21:09Z",
  "data": {"order_id": "ord_8812", "amount": 42900, "currency": "KRW"}
}
```

- `event_id`: 멱등 처리의 기준 키
- `type`: 8번의 세 가지 중 하나
- `occurred_at`: 정렬 기준 (도착 순서가 아니라 이 값을 쓰세요)
- `data`: 타입별 실제 내용


비밀키 관리
===========

- 비밀키는 엔드포인트를 등록할 때 **한 번만** 보여주고 이후에는 다시 볼 수 없습니다.
  등록 시점에 안전한 곳(비밀 저장소 등)에 옮겨 두어야 합니다.
- 분실하면 콘솔에서 회전(rotate)해야 합니다.
- 회전 직후 5분 동안은 옛 키와 새 키로 만든 서명을 **둘 다** 받아 줍니다.
  이 유예 시간 덕분에 무중단으로 키를 교체할 수 있으니, 그 안에 수신 측 설정을
  새 키로 바꾸세요.
- 회전 이력도 전달 로그와 같은 탭에서 확인할 수 있습니다.


수신 서버 구현 체크리스트
=========================

1. `X-Signature` 를 원본 본문 바이트로 검증한다. (파싱보다 먼저)
2. `event_id` 로 이미 처리한 이벤트인지 확인하고, 처리했으면 바로 2xx.
3. 무거운 처리는 뒤로 미루고 10초 안에 응답 헤더를 보낸다.
4. 상태 반영은 `occurred_at` 순서로 판단한다.
5. `payload_url` 이 들어온 경우도 처리한다.
6. 실패가 쌓이면 자동 비활성화되므로 실패 알림을 모니터링한다.
