요청 제한(Rate Limit) 동작 설명서

이 문서는 우리 서비스의 요청 제한 동작을 처음 보는 사람을 위해 설명합니다.

1. 버킷 용량 = 60
   토큰 버킷 방식입니다. 각 API 키는 토큰이 최대 60개까지 담기는 양동이를 하나 가집니다.
   요청 1건마다 토큰 1개를 씁니다. 토큰이 남아 있으면 요청은 통과하고, 0개면 막힙니다.
   양동이가 가득 찬 상태에서는 순간적으로 60건까지 연속 처리할 수 있습니다(버스트 허용량).

2. 리필 속도 = 초당 1개
   쓴 토큰은 1초에 1개씩 다시 채워집니다. 즉 장기 평균 처리율은 초당 1건입니다.
   용량 60을 넘겨서 쌓이지는 않습니다. 60개가 찬 뒤로는 더 채워지지 않습니다.
   예: 60건을 한꺼번에 보내 토큰을 모두 소진하면, 그다음 요청은 1초 뒤에 1건, 10초 뒤에는 10건 가능합니다.

3. 집계 단위 = API 키
   제한은 API 키 단위로 계산합니다. IP 주소 단위가 아닙니다.
   - 같은 API 키를 서버 여러 대에서(= 서로 다른 IP에서) 쓰면 그 요청들은 하나의 버킷을 공유합니다.
   - 반대로 같은 IP에서 서로 다른 API 키로 보내면 각 키가 별도 버킷을 가집니다.
   따라서 NAT나 프록시 뒤에 있는 여러 사용자가 서로의 한도를 잡아먹는 문제는 생기지 않습니다.
   대신 키를 여러 인스턴스에서 공유하면 한도도 함께 나눠 쓰게 되므로, 워커를 늘릴 때는 키를 분리할지 검토해야 합니다.

4. 초과 시 상태 코드 = 429
   토큰이 없는 상태에서 들어온 요청은 처리하지 않고 HTTP 상태 코드 429(Too Many Requests)로 응답합니다.
   429는 "요청 자체가 잘못됐다"는 뜻이 아니므로, 잠시 뒤 같은 요청을 다시 보내면 성공할 수 있습니다.
   클라이언트를 만들 때 429를 400번대 일반 오류와 같이 취급해 즉시 실패 처리하지 않도록 주의하세요.

5. 재시도 안내 헤더 = Retry-After (초 단위 정수)
   429 응답에는 Retry-After 헤더가 함께 실립니다. 값은 초 단위 정수입니다(예: Retry-After: 5 → 5초 뒤 재시도).
   HTTP 날짜 형식이 아니라 정수 초라는 점을 기억하세요.
   클라이언트는 이 값을 그대로 대기 시간으로 쓰면 됩니다. 자체 추측으로 즉시 재시도를 반복하면 계속 429만 받게 됩니다.

6. 예외 = admin 스코프 키
   admin 스코프를 가진 API 키는 요청 제한에서 제외됩니다. 즉 버킷 소모나 429 응답 없이 호출할 수 있습니다.
   운영·관리 목적의 예외이므로, 일반 서비스 트래픽을 admin 키로 우회해 처리하지 않도록 합니다.
   admin이 아닌 모든 스코프의 키는 위 1~5번 규칙을 그대로 따릅니다.

요약

  항목            값
  버킷 용량        60
  리필 속도        초당 1개
  집계 단위        API 키 (IP 주소 아님)
  초과 시 응답      429
  재시도 안내       Retry-After 헤더, 초 단위 정수
  예외            admin 스코프 키는 제한 없음
