요청 제한(Rate Limit) 동작 설명서
=================================

이 문서는 우리 서비스의 요청 제한 동작을 처음 접하는 백엔드 개발자를 위한 설명서입니다.


1. 전체 그림: 토큰 버킷 방식
-----------------------------
우리 서비스는 "토큰 버킷(token bucket)" 방식으로 요청 수를 제한합니다.

- API 키마다 물통(버킷)이 하나 있고, 그 안에 토큰이 들어 있습니다.
  (버킷을 무엇 단위로 나누는지는 4절에서 자세히 다룹니다.)
- 요청 1건을 보낼 때마다 토큰 1개를 씁니다.
- 토큰은 시간이 지나면 일정 속도로 다시 채워집니다(리필).
- 토큰이 0개인 상태에서 요청이 오면 그 요청은 거부됩니다.

이 방식의 장점은 "잠시 몰아서 보내는 것(버스트)"을 허용하면서도 장기적인
평균 요청 속도는 일정하게 유지된다는 점입니다.


2. 버킷 용량: 60
-----------------
버킷에 한 번에 담을 수 있는 토큰의 최대 개수는 60개입니다.

- 즉, 토큰이 가득 찬 상태라면 연속으로 최대 60건의 요청을 즉시 보낼 수 있습니다.
- 버킷은 60개를 넘겨서 채워지지 않습니다. 오랫동안 요청을 보내지 않아도
  토큰이 100개, 200개로 쌓이지는 않습니다. 60개가 상한입니다.

이 60이라는 값이 "버스트 허용량"입니다.


3. 리필 속도: 초당 1개
-----------------------
소비된 토큰은 1초에 1개씩 다시 채워집니다.

- 장기적으로 보면 지속 가능한 요청 속도는 "초당 1건"입니다.
- 예: 토큰 60개를 한꺼번에 다 쓰면 버킷은 0이 됩니다. 그 뒤로는 1초에 1건씩만
  보낼 수 있습니다.
- 예: 60개를 다 쓴 뒤 10초를 기다리면 토큰 10개가 채워져서 다시 10건을
  연속으로 보낼 수 있습니다.
- 버킷을 0에서 다시 가득(60개) 채우려면 60초가 걸립니다.

정리하면 버킷 용량 60은 "순간 최대치", 리필 속도 초당 1개는 "평균 최대치"를
결정합니다.


4. 집계 단위: API 키 (IP 주소가 아님)
--------------------------------------
버킷은 **API 키 단위**로 관리됩니다. IP 주소 단위가 아닙니다.

이 차이가 실무에서 만드는 결과:

- 같은 API 키를 여러 서버, 여러 컨테이너, 여러 지역에서 나눠 쓰더라도
  버킷은 하나입니다. 각 인스턴스가 쓴 요청이 모두 같은 버킷에서 차감됩니다.
  따라서 인스턴스를 늘려도 총 허용량은 늘어나지 않습니다.
- 반대로, 여러 사용자가 같은 IP(예: 회사 NAT, 사내 프록시) 뒤에 있어도
  API 키가 다르면 서로의 요청 제한에 영향을 주지 않습니다.
- IP를 바꾸거나 프록시를 경유해도 제한을 피할 수 없습니다. 키가 같으면
  같은 버킷입니다.

클라이언트를 여러 대로 수평 확장할 계획이라면, 키를 분리할지 아니면
클라이언트 쪽에서 전체 요청 속도를 조절할지 미리 설계해야 합니다.


5. 초과 시 상태 코드: 429
--------------------------
토큰이 없는 상태에서 요청이 들어오면 서버는 HTTP 상태 코드 **429**
(Too Many Requests)로 응답합니다.

- 429는 "요청 자체가 잘못됐다"는 뜻이 아니라 "지금은 너무 빠르다"는 뜻입니다.
  요청 내용을 고칠 필요는 없고, 잠시 기다린 뒤 같은 요청을 다시 보내면 됩니다.
- 그래서 429는 4xx 중에서도 재시도가 의미 있는 코드입니다.
  400(잘못된 요청)이나 401(인증 실패)처럼 그대로 재시도해도 소용없는
  코드와 구분해서 처리해야 합니다.


6. 재시도 안내 헤더: Retry-After
---------------------------------
429 응답에는 `Retry-After` 헤더가 함께 옵니다.

- 값은 **초 단위 정수**입니다. 예: `Retry-After: 5` → 5초 뒤에 재시도하라는 뜻.
- HTTP 표준에서 이 헤더는 날짜 형식도 허용하지만, 우리 서비스는 초 단위
  정수만 보냅니다. 파싱할 때 날짜 형식을 고려할 필요는 없습니다.
- 클라이언트는 임의로 정한 간격이 아니라 이 값을 따라야 합니다. 값을 무시하고
  즉시 재시도하면 계속 429를 받게 되고, 불필요한 트래픽만 늘어납니다.

권장 처리 흐름:

    1) 응답 코드가 429인지 확인한다
    2) Retry-After 값을 정수로 읽는다
    3) 그 시간만큼 기다린다 (여러 클라이언트가 동시에 깨어나
       또 몰리는 것을 막으려면 약간의 무작위 지연을 더하는 것이 좋다)
    4) 같은 요청을 다시 보낸다
    5) 재시도 횟수에 상한을 둔다 (무한 재시도 금지)


7. 예외: admin 스코프 키
-------------------------
`admin` 스코프를 가진 API 키는 요청 제한에서 **제외**됩니다.

- admin 키로 보내는 요청은 토큰을 소비하지 않으며, 429를 받지 않습니다.
- 즉 위의 버킷 용량 60이나 초당 1개 리필은 admin 키에는 적용되지 않습니다.
- 주의: 제한이 없다는 것은 곧 실수로 서비스에 과부하를 줄 수 있다는 뜻입니다.
  admin 키를 일반 애플리케이션 트래픽이나 부하 테스트에 쓰지 마세요.
  운영/관리 목적으로만 사용하고, 노출되지 않도록 특히 조심해서 관리해야 합니다.
- 개발 중에 admin 키로 테스트하면 429 처리 경로가 한 번도 실행되지 않습니다.
  재시도 로직을 검증할 때는 반드시 일반 스코프 키로 테스트하세요.


요약 표
-------
| 항목 | 값 |
|---|---|
| 버킷 용량 | 60 (한 번에 보낼 수 있는 최대 요청 수) |
| 리필 속도 | 초당 1개 (지속 가능한 평균 요청 속도) |
| 집계 단위 | API 키 단위 (IP 주소 단위가 아님) |
| 초과 시 상태 코드 | 429 |
| 재시도 안내 헤더 | Retry-After (초 단위 정수) |
| 예외 | admin 스코프 키는 제한에서 제외 |
