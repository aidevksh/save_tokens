요청 제한(Rate Limit) 동작 안내 — 신입 백엔드 개발자용

이 문서는 우리 서비스가 API 요청량을 어떻게 제한하는지 처음 보는 사람이
이해할 수 있도록 정리한 것입니다.

--------------------------------------------------------------------
0. 큰 그림: 토큰 버킷(token bucket)
--------------------------------------------------------------------
요청 하나를 보낼 때마다 "물통에서 물 한 컵을 꺼낸다"고 생각하면 됩니다.
물통에는 정해진 최대 용량이 있고, 시간이 지나면 물이 다시 채워집니다.
물통이 비어 있는데 요청이 오면 그 요청은 거절됩니다.

- 물통 = 버킷
- 물 한 컵 = 요청 1건
- 물이 채워지는 것 = 리필

아래 1~6번이 이 물통의 구체적인 규칙입니다.

--------------------------------------------------------------------
1. 버킷 용량: 60
--------------------------------------------------------------------
버킷에 한 번에 담아둘 수 있는 최대 토큰 수는 60개입니다.
즉 오랫동안 요청을 보내지 않아 버킷이 가득 차 있는 상태라면,
한꺼번에 최대 60건의 요청을 연달아 보낼 수 있습니다.

이 60은 "쌓아둘 수 있는 여유분"이며, 순간적인 몰림(버스트)을 허용하는
크기입니다. 61번째 요청은 새로 채워진 토큰이 없다면 거절됩니다.
버킷은 60을 넘겨서 쌓이지 않습니다. 요청을 30분 쉬어도 61이 되지는 않습니다.

--------------------------------------------------------------------
2. 리필 속도: 초당 1개
--------------------------------------------------------------------
버킷에는 1초에 토큰 1개씩 다시 채워집니다.
따라서 장기적으로 유지 가능한 평균 요청 속도는 초당 1건입니다.

- 초당 1건 이하로 꾸준히 보내면 사실상 제한에 걸리지 않습니다.
- 60건을 한꺼번에 소진했다면, 버킷이 다시 가득 차기까지 60초가 걸립니다.
- 1건만 더 보내고 싶다면 1초만 기다리면 됩니다.

정리하면 이 정책은 "평균 초당 1건, 순간 최대 60건"입니다.

--------------------------------------------------------------------
3. 집계 단위: API 키 (IP 주소가 아님)
--------------------------------------------------------------------
버킷은 API 키 하나당 하나씩 존재합니다. IP 주소 기준이 아닙니다.

이 차이가 실무에서 의미하는 것:
- 같은 서버(같은 IP)에서 서로 다른 API 키로 요청하면 버킷이 분리됩니다.
  한쪽 키가 제한에 걸려도 다른 키는 영향을 받지 않습니다.
- 반대로 여러 서버, 여러 지역, 여러 컨테이너에 같은 API 키를 나눠 쓰면
  그 모두가 하나의 버킷을 공유합니다. 인스턴스를 늘려도 총 허용량은
  늘어나지 않습니다.
- 따라서 트래픽이 늘어 한도가 부족하다면, 서버를 늘리는 것이 아니라
  키를 분리하거나 한도 상향을 요청하는 방향으로 접근해야 합니다.

--------------------------------------------------------------------
4. 초과 시 상태 코드: 429
--------------------------------------------------------------------
버킷에 남은 토큰이 없는 상태에서 요청이 오면 HTTP 상태 코드 429
(Too Many Requests)를 반환합니다.

- 429는 "요청 자체가 잘못됐다"는 뜻이 아닙니다. 지금은 너무 빠르다는
  뜻이므로, 잠시 뒤 같은 요청을 그대로 다시 보내면 성공할 수 있습니다.
- 400번대이지만 재시도 가치가 있는 응답이라는 점에서 401/403과 다르게
  다뤄야 합니다. 401/403은 재시도해도 결과가 같습니다.
- 클라이언트 코드에서 429를 일반 오류와 함께 뭉뚱그려 처리하지 말고,
  별도 분기로 잡아 재시도 로직에 연결하는 것을 권장합니다.

--------------------------------------------------------------------
5. 재시도 안내 헤더: Retry-After (초 단위 정수)
--------------------------------------------------------------------
429 응답에는 Retry-After 헤더가 함께 내려갑니다.
값은 초 단위 정수입니다. 날짜 형식이 아닙니다.

예시:
    HTTP/1.1 429 Too Many Requests
    Retry-After: 5

위 응답은 "5초 뒤에 다시 시도하라"는 뜻입니다.

구현 시 주의할 점:
- 값을 정수(초)로 파싱하면 됩니다. HTTP 날짜 문자열 파싱은 필요 없습니다.
- 임의로 정한 대기 시간 대신 이 값을 사용하십시오. 서버가 알려준 값보다
  빨리 재시도하면 다시 429를 받게 됩니다.
- 여러 워커가 동시에 429를 받으면 같은 시점에 한꺼번에 재시도하게 되어
  다시 몰릴 수 있습니다. Retry-After 값에 약간의 무작위 지연(지터)을
  더해주는 편이 안전합니다.

--------------------------------------------------------------------
6. 예외: admin 스코프 키는 제한 대상이 아님
--------------------------------------------------------------------
admin 스코프를 가진 API 키는 요청 제한에서 제외됩니다.
버킷을 소모하지 않으며 429를 받지 않습니다.

주의:
- 개발이나 테스트를 admin 키로만 하면 제한 동작을 한 번도 겪지 못합니다.
  429 처리와 재시도 로직은 일반 스코프 키로 검증해야 합니다.
- 제한이 없다는 것은 보호 장치도 없다는 뜻입니다. admin 키로 대량 작업을
  돌릴 때는 서비스에 부하를 줄 수 있으니 호출 측에서 속도를 조절하십시오.

요약 표
--------------------------------------------------------------------
항목            | 값
--------------- | ------------------------------------------
버킷 용량       | 60
리필 속도       | 초당 1개
집계 단위       | API 키 (IP 주소 아님)
초과 시 응답    | HTTP 429
재시도 안내     | Retry-After 헤더, 초 단위 정수
예외            | admin 스코프 키는 제한 제외

--------------------------------------------------------------------
체크리스트 (클라이언트 구현 시)
--------------------------------------------------------------------
[ ] 평균 호출 속도를 초당 1건 이하로 설계했는가
[ ] 순간 몰림이 60건을 넘지 않는가
[ ] 같은 API 키를 여러 인스턴스가 공유하고 있지 않은지 확인했는가
[ ] 429를 다른 오류와 구분해 처리하는가
[ ] Retry-After 값을 읽어 그만큼 대기하는가 (지터 추가 권장)
[ ] admin 키가 아닌 일반 키로 제한 동작을 테스트했는가
