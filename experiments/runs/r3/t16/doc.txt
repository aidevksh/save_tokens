요청 제한(Rate Limit) 동작 안내 — 신입 백엔드 개발자용

우리 서비스는 "토큰 버킷(token bucket)" 방식으로 요청 수를 제한합니다.
물이 담긴 물통을 떠올리면 됩니다. 요청 한 번에 물 한 컵을 쓰고, 물은 일정 속도로 다시 채워집니다.
물통이 비면 더 이상 요청을 받지 않습니다.

1) 버킷 용량 = 60
   물통에 담기는 최대치가 60개입니다. 요청 1건이 1개를 씁니다.
   가득 찬 상태에서는 한 번에 60건까지 연달아 보낼 수 있습니다(순간 폭주 허용량, burst).
   용량을 넘겨 미리 쌓아둘 수는 없습니다. 아무리 오래 쉬어도 최대 60개까지만 회복됩니다.

2) 리필 속도 = 초당 1개
   쓴 만큼은 1초에 1개씩 다시 채워집니다.
   따라서 장기 평균 처리량은 초당 1건입니다. 60건을 몰아 쓰고 나면
   그 뒤로는 1초에 1건 페이스로만 통과합니다. 완전히 비운 물통이 다시 꽉 차려면 60초가 걸립니다.
   요약: 짧게는 60건까지 몰아쓰기 가능, 길게 보면 초당 1건.

3) 집계 단위 = API 키 (IP 주소가 아님)
   물통은 API 키마다 하나씩 따로 있습니다. IP 주소 기준이 아닙니다.
   - 같은 API 키를 서버 10대에서 나눠 쓰면 10대가 물통 하나를 공유합니다.
     즉 전체 합계가 초당 1건을 넘으면 제한에 걸립니다. 클라이언트를 늘려도 한도는 늘지 않습니다.
   - 반대로 IP가 같아도(예: 같은 NAT, 같은 사내망) API 키가 다르면 서로 영향을 주지 않습니다.
   실무 함의: 키를 공유해서 병렬 처리하면 서로의 한도를 깎아먹습니다.
   워크로드를 나눌 때는 키 단위로 나누는 것을 검토하세요.

4) 초과 시 상태 코드 = 429
   물통이 비었을 때 들어온 요청은 처리되지 않고 HTTP 429 (Too Many Requests)로 응답합니다.
   429는 "요청 자체가 잘못됐다"는 뜻이 아니라 "지금은 too fast, 나중에 다시 오라"는 뜻입니다.
   그래서 4xx 중에서도 재시도가 의미 있는 코드입니다.
   400(요청 형식 오류)이나 401/403(인증·권한 오류)과 달리, 요청을 고칠 필요 없이
   시간만 두고 그대로 다시 보내면 성공합니다.

5) 재시도 안내 헤더 = Retry-After (초 단위 정수)
   429 응답에는 Retry-After 헤더가 함께 옵니다. 값은 초 단위 정수입니다.
   예: `Retry-After: 5` → 5초 뒤에 재시도하라는 뜻.
   (날짜 형식이 아니라 숫자입니다. 파싱할 때 정수로 읽으면 됩니다.)

   클라이언트 구현 시:
   - 429를 받으면 즉시 재시도하지 말고 Retry-After 만큼 기다립니다.
     기다리지 않고 바로 다시 던지면 또 429를 받고, 로그와 트래픽만 늘어납니다.
   - 헤더가 없거나 값을 못 읽는 예외 상황에 대비해 기본 대기값을 두는 편이 안전합니다.
   - 여러 클라이언트가 동시에 429를 받으면 같은 시점에 몰려서 재시도하게 됩니다.
     대기 시간에 약간의 무작위 값(지터, jitter)을 더해 분산시키는 것을 권장합니다.

6) 예외 = admin 스코프 키는 제한에서 제외
   `admin` 스코프를 가진 API 키에는 위 제한이 적용되지 않습니다. 물통을 거치지 않고 통과합니다.
   운영/관리 작업이 트래픽 폭주 상황에서도 막히지 않게 하려는 장치입니다.
   주의: 편하다는 이유로 일반 업무용 코드에 admin 키를 쓰면
   보호 장치가 사라져 장애 시 서비스를 함께 밀어버릴 수 있습니다. 용도에 맞는 키를 쓰세요.
   또한 로컬에서 admin 키로 테스트하면 제한이 걸리지 않으므로
   429 처리 코드가 실제로 동작하는지 검증되지 않습니다. 429 경로는 일반 키로 시험하세요.

정리
- 물통 용량 60, 초당 1개 회복 → 순간 60건, 지속 초당 1건
- 물통은 API 키별(IP별 아님)
- 넘치면 429 + Retry-After(초) → 그 시간만큼 기다린 뒤 재시도
- admin 스코프 키는 제한 없음
