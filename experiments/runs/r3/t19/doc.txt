요청 제한(Rate Limit) 동작 명세 — 신입 개발자용 안내

이 문서는 우리 서비스가 과도한 요청을 어떻게 막는지를 처음 보는 사람이
이해할 수 있도록 설명합니다.

------------------------------------------------------------
1. 기본 개념: 토큰 버킷
------------------------------------------------------------
우리 서비스는 "토큰 버킷(token bucket)" 방식을 씁니다.
요청 하나를 보낼 때마다 양동이에서 토큰 하나를 꺼내 씁니다.
양동이가 비면 더 이상 요청을 받아주지 않습니다.
양동이에는 일정한 속도로 토큰이 다시 채워집니다.

------------------------------------------------------------
2. 버킷 용량: 60
------------------------------------------------------------
양동이에 한 번에 담길 수 있는 토큰의 최대 개수는 60개입니다.
즉 한동안 요청을 보내지 않아 양동이가 꽉 찬 상태라면,
순간적으로 최대 60건의 요청을 연달아 보낼 수 있습니다.
이것을 버스트(burst) 허용량이라고 부릅니다.
61번째 요청은 리필을 기다려야 합니다.

------------------------------------------------------------
3. 리필 속도: 초당 1개
------------------------------------------------------------
토큰은 1초에 1개씩 다시 채워집니다. 상한은 60개(2번 항목)이므로
그 이상으로는 쌓이지 않습니다.

정리하면,
- 지속 처리량(sustained rate): 초당 1건
- 순간 최대(burst): 60건

예시: 60건을 한 번에 다 쓰면 양동이는 0이 됩니다.
그 뒤에는 1초에 1건씩만 통과하고, 30초를 쉬면 토큰이 30개 회복됩니다.

------------------------------------------------------------
4. 집계 단위: API 키 (IP 주소가 아님)
------------------------------------------------------------
양동이는 API 키 하나당 하나씩 존재합니다. IP 주소 기준이 아닙니다.

실무에서 중요한 차이는 이렇습니다.
- 같은 API 키를 서버 여러 대에서 나눠 써도 양동이는 하나입니다.
  즉 서버를 늘려도 총 허용량은 늘어나지 않습니다.
- 반대로 같은 사무실(같은 IP)에서 서로 다른 API 키로 호출하면
  서로에게 영향을 주지 않습니다. 각자 양동이를 갖습니다.
- 따라서 "왜 내 요청이 막히나"를 조사할 때는 IP가 아니라
  어떤 API 키를 썼는지를 먼저 확인해야 합니다.

------------------------------------------------------------
5. 초과 시 응답: HTTP 429
------------------------------------------------------------
토큰이 없는 상태에서 요청이 들어오면 서버는 상태 코드 429를 돌려줍니다.
(429는 표준 HTTP 상태 코드로 "Too Many Requests"를 뜻합니다.)

429는 요청 내용이 잘못되었다는 뜻이 아닙니다. 지금은 너무 빠르다는
뜻이므로, 잠시 기다린 뒤 같은 요청을 다시 보내면 됩니다.

------------------------------------------------------------
6. 재시도 안내 헤더: Retry-After (초 단위 정수)
------------------------------------------------------------
429 응답에는 Retry-After 헤더가 함께 들어옵니다.
값은 초 단위 정수입니다. 예를 들어,

    HTTP/1.1 429
    Retry-After: 5

는 "5초 뒤에 다시 시도하라"는 뜻입니다.

클라이언트를 만들 때는 임의로 정한 대기 시간을 쓰지 말고
이 헤더 값을 읽어서 그만큼 기다린 뒤 재시도하도록 구현하세요.
값이 정수 초이므로 날짜 형식 파싱은 필요하지 않습니다.

------------------------------------------------------------
7. 예외: admin 스코프 키
------------------------------------------------------------
admin 스코프를 가진 API 키는 요청 제한을 적용받지 않습니다.
버킷 용량이나 리필 속도와 무관하게 통과하며 429도 받지 않습니다.

주의할 점은, 그래서 admin 키로 테스트하면 제한 동작이 재현되지
않는다는 것입니다. 제한 관련 동작을 확인할 때는 일반 스코프 키를
사용하세요.
