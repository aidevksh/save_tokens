요청 제한(Rate Limit) 동작 설명서

이 문서는 우리 서비스의 요청 제한이 어떤 원리로 동작하는지를 처음 보는 사람 기준으로 설명한다.
전체 구조는 "토큰 버킷(token bucket)" 방식이다. 요청 하나를 보낼 때마다 바구니에서 토큰 하나를
꺼내 쓰고, 바구니는 일정 속도로 다시 채워진다. 바구니가 비면 요청이 거절된다.


1. 버킷 용량 = 60

각 사용 주체는 최대 60개의 토큰을 담을 수 있는 바구니를 하나 갖는다.
요청 1건 = 토큰 1개 소비다. 바구니가 꽉 찬 상태(60개)라면 연속해서 60건까지 한꺼번에 보낼 수 있다.
즉 용량은 "순간적으로 몰아서 보낼 수 있는 최대 요청 수(버스트 허용량)"를 뜻한다.
용량을 넘겨서 토큰이 쌓이지는 않는다. 오래 쉬었다고 해서 70개, 100개가 되지 않고 60에서 멈춘다.


2. 리필 속도 = 초당 1개

토큰은 1초에 1개씩 다시 채워진다. 채워지는 상한은 위에서 말한 60개다.
따라서 장기적으로 유지 가능한 처리량은 초당 1건이며, 60은 그 위에 얹힌 여유분이다.

예시)
- 바구니가 꽉 찬 상태에서 60건을 순간에 보낸다 → 모두 통과, 잔량 0
- 그 직후 1건을 더 보낸다 → 거절
- 5초 기다린다 → 토큰 5개 회복 → 5건까지 다시 통과

설계할 때의 요점: 평균 초당 1건을 넘는 트래픽을 계속 흘리면 초반 60건을 다 쓴 뒤부터는
반드시 거절이 발생한다. 버스트는 잠깐의 스파이크를 흡수하는 장치일 뿐 평균 처리량을 늘려주지 않는다.


3. 집계 단위 = API 키 (IP 주소가 아님)

바구니는 API 키 하나당 하나씩 존재한다. IP 주소 기준이 아니다. 이 차이가 실제로 만드는 결과는 다음과 같다.

- 같은 API 키를 여러 서버·여러 컨테이너·여러 지역에서 나눠 쓰면 그 모두가 하나의 바구니 60개를
  공유한다. 인스턴스를 늘려도 한도는 늘지 않는다.
- 반대로 서로 다른 API 키는 같은 IP에서 나가더라도 각자 독립된 바구니를 갖는다.
  사무실 공용 IP를 쓰는 동료의 호출 때문에 내 한도가 깎이는 일은 없다.
- NAT·프록시·로드밸런서 뒤에 있어도 판정 기준은 바뀌지 않는다. 중요한 것은 요청에 실린 API 키다.

여러 워커가 한 키를 공유해야 한다면 클라이언트 쪽에서 전체 발신량을 조절하거나,
용도별로 키를 분리하는 방식을 고려한다.


4. 초과 시 상태 코드 = 429

토큰이 없는 상태에서 요청이 오면 서버는 HTTP 429 (Too Many Requests) 를 반환한다.
429는 "요청 자체가 잘못됐다"는 뜻이 아니라 "지금은 너무 빠르다, 나중에 다시 보내라"는 뜻이다.
따라서 400번대 다른 오류들과 같이 취급하면 안 된다.

- 400, 401, 403 등: 요청을 고쳐야 한다. 그대로 재시도하면 또 실패한다.
- 429: 요청은 그대로 두고 시간만 두었다가 다시 보내면 성공할 수 있다.

클라이언트 코드에서는 429를 별도 분기로 잡아 재시도 대상으로 처리한다.


5. 재시도 안내 헤더 = Retry-After (초 단위 정수)

429 응답에는 Retry-After 헤더가 함께 온다. 값은 초 단위 정수다.

    HTTP/1.1 429 Too Many Requests
    Retry-After: 3

위 예시는 "3초 뒤에 다시 시도하라"는 의미다. 날짜 형식이 아니라 정수 초라는 점에 주의한다.
직접 간격을 추측하지 말고 이 값을 그대로 사용하는 것이 원칙이다. 서버가 알려준 값이
현재 바구니 상태에 근거한 가장 정확한 대기 시간이기 때문이다.

권장 처리 순서
  1) 응답 코드가 429인지 확인한다.
  2) Retry-After 값을 읽어 그 시간만큼 기다린다.
  3) 기다린 뒤 같은 요청을 다시 보낸다.
  4) 헤더가 없거나 값을 해석할 수 없으면 적당한 기본값에서 시작해 재시도 간격을 점차 늘린다
     (지수 백오프). 여러 클라이언트가 동시에 깨어나 다시 몰리는 것을 막기 위해 약간의 무작위
     지연을 섞는 것이 좋다.
  5) 재시도 횟수에는 상한을 둔다. 무한 재시도는 장애를 키운다.

즉시 재시도(대기 없이 반복 호출)는 상황을 악화시키기만 하므로 하지 않는다.


6. 예외 = admin 스코프 키

API 키가 admin 스코프를 가진 경우 요청 제한이 적용되지 않는다. 토큰을 소비하지 않고
429도 발생하지 않는다. 운영·복구 작업이 한도 때문에 막히면 안 되기 때문에 둔 예외다.

주의할 점
- 편하다는 이유로 일반 애플리케이션 트래픽에 admin 키를 쓰면 안 된다. 보호 장치가 사라져
  실수 하나가 곧바로 서비스 전체에 부하로 이어진다.
- admin 키로 개발·테스트를 하면 제한에 걸리는 상황을 한 번도 겪지 못한 채 배포하게 된다.
  429 처리 경로는 반드시 일반 키로 검증한다.
- 예외는 admin 스코프에만 해당한다. 다른 스코프 키는 모두 위 규칙을 그대로 따른다.


요약

  버킷 용량        60건까지 몰아서 보낼 수 있다
  리필 속도        초당 1개씩 회복, 최대 60에서 멈춘다
  집계 단위        API 키별. IP는 무관하며 같은 키를 나눠 쓰면 한도도 나눠 쓴다
  초과 응답        HTTP 429
  재시도 안내      Retry-After 헤더(정수 초). 이 값만큼 기다린 뒤 재시도한다
  예외             admin 스코프 키는 제한 대상이 아니다

개발할 때 기억할 것 한 줄: 평균 초당 1건을 지키고, 429가 오면 Retry-After만큼 기다린 뒤
다시 보내도록 클라이언트를 만든다.
