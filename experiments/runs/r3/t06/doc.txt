요청 제한(Rate Limit) 동작 설명서
================================

이 문서는 우리 서비스의 요청 제한 동작을 처음 접하는 백엔드 개발자를 위한 설명서입니다.
우리 서비스는 "토큰 버킷(token bucket)" 방식으로 요청 수를 제한합니다.


0. 큰 그림: 토큰 버킷이란
-------------------------

물이 담긴 양동이를 상상하세요.

- 요청 1건을 처리할 때마다 양동이에서 물 1개(토큰 1개)를 꺼내 씁니다.
- 양동이에는 일정한 속도로 물이 다시 채워집니다.
- 양동이가 비어 있으면 요청을 받아줄 수 없습니다.

이 방식의 장점은 "평소에는 아껴 두었다가 순간적으로 몰아서 쓰는 것"을 허용한다는
점입니다. 아래 1번과 2번이 각각 "양동이 크기"와 "채워지는 속도"에 해당합니다.


1. 버킷 용량: 60
----------------

버킷에 담을 수 있는 토큰의 최대 개수는 60개입니다.

- 한 번에 최대 60건의 요청을 연속으로 보낼 수 있다는 뜻입니다.
  이것을 순간 최대 허용량, 즉 버스트(burst) 한도라고 부릅니다.
- 토큰이 60개를 넘겨서 쌓이지는 않습니다. 하루 동안 요청을 전혀 보내지 않았더라도
  다음 날 쓸 수 있는 버스트는 여전히 60건입니다. 아껴서 이월되지 않습니다.
- 처음 상태(요청을 아무것도 보내지 않은 상태)에서는 버킷이 꽉 차 있다고 보면 됩니다.


2. 리필 속도: 초당 1개
----------------------

버킷에는 1초에 토큰 1개가 다시 채워집니다.

- 즉 장기적으로 지속 가능한 요청 속도는 초당 1건입니다.
  60건을 한꺼번에 다 쓰고 나면, 그 뒤로는 1초에 1건씩만 보낼 수 있습니다.
- 예시:
  - 60건을 순간에 보내 버킷을 비운다 -> 다음 1건은 1초 뒤에 가능
  - 10초 동안 요청을 쉰다 -> 토큰 10개가 회복되어 10건을 몰아서 보낼 수 있음
  - 30초 쉬면 30개, 60초 이상 쉬면 상한인 60개까지 회복

정리하면 이렇게 기억하세요.
  버킷 용량(60) = 한 번에 몰아 쓸 수 있는 양
  리필 속도(초당 1개) = 계속 유지할 수 있는 평균 속도


3. 집계 단위: API 키 (IP 주소가 아님)
-------------------------------------

제한은 API 키 하나당 하나의 버킷으로 계산합니다. IP 주소 기준이 아닙니다.

이 차이가 실무에서 의미하는 것:

- 같은 API 키를 여러 서버, 여러 컨테이너, 여러 지역에서 나눠 쓰더라도
  버킷은 하나입니다. 인스턴스를 늘려도 총 허용량은 늘어나지 않고,
  오히려 여러 인스턴스가 같은 버킷을 나눠 쓰면서 더 빨리 소진됩니다.
- 반대로 서로 다른 API 키는 같은 IP에서 호출해도 각자 독립된 버킷을 가집니다.
  NAT나 사내 프록시 뒤에서 여러 팀이 나가더라도 서로 영향을 주지 않습니다.
- 따라서 429가 발생했을 때 "어느 서버가 범인인가"보다
  "어느 API 키가 한도를 넘겼는가"를 먼저 확인해야 합니다.
- 부하가 큰 배치 작업과 사용자 응답용 실시간 호출이 같은 키를 공유하면,
  배치가 버킷을 비워 실시간 트래픽이 막힐 수 있습니다.
  용도별로 키를 분리하는 것이 안전합니다.


4. 초과 시 상태 코드: 429
-------------------------

버킷에 남은 토큰이 없는 상태에서 요청이 오면 HTTP 상태 코드 429를 응답합니다.
(429 Too Many Requests)

- 429는 "요청 자체가 잘못됐다"는 뜻이 아닙니다. 지금은 양이 많아서 받을 수 없다는
  뜻이므로, 잠시 뒤 같은 요청을 다시 보내면 성공할 수 있습니다.
- 그래서 클라이언트는 429를 400번대의 다른 오류(예: 잘못된 파라미터)처럼
  "재시도해도 소용없는 실패"로 취급해서는 안 됩니다. 재시도 대상입니다.
- 반대로 429를 무조건 즉시 재시도하는 것도 안 됩니다. 재시도 시점은 5번 항목의
  헤더가 알려줍니다.


5. 재시도 안내 헤더: Retry-After (단위는 초, 정수)
-------------------------------------------------

429 응답에는 Retry-After 헤더가 함께 담깁니다.
값은 초 단위 정수입니다.

    HTTP/1.1 429 Too Many Requests
    Retry-After: 3

위 예시는 "3초 뒤에 다시 시도하라"는 뜻입니다.

주의할 점:

- 값은 밀리초가 아니라 초입니다. 3을 3밀리초로 오해해 곧바로 재시도하면
  429가 반복되기만 합니다.
- 값은 날짜 형식(HTTP-date)이 아니라 정수입니다. 날짜 파싱을 시도할 필요가 없습니다.
- 구현 권장: 429를 받으면 Retry-After 값만큼 기다린 뒤 재시도하고,
  재시도 횟수에는 상한을 둡니다. 여러 인스턴스가 같은 시점에 깨어나
  다시 몰리는 것을 막기 위해 대기 시간에 약간의 무작위 값(지터)을 더하는 것이
  좋습니다.
- 클라이언트 코드에 대기 시간을 상수로 넣지 말고, 반드시 응답의 Retry-After 값을
  읽어서 사용하세요. 서버가 판단한 값이 가장 정확합니다.


6. 예외: admin 스코프 키는 제한에서 제외
----------------------------------------

admin 스코프를 가진 API 키는 요청 제한을 적용받지 않습니다.
버킷 용량이나 리필 속도와 무관하게 호출할 수 있고, 429도 발생하지 않습니다.

실무에서 조심할 점:

- 개발이나 테스트를 admin 키로만 하면 제한 동작을 한 번도 겪지 못합니다.
  그 상태로 배포하면 운영에서 처음 429를 만나게 됩니다.
  재시도 로직 검증은 반드시 일반 스코프 키로 하세요.
- "제한이 없으니 편하다"는 이유로 일반 업무 트래픽을 admin 키로 돌리면 안 됩니다.
  보호 장치가 사라져 장애 시 서비스 전체에 부하가 전달됩니다.
- 장애 대응이나 운영 작업처럼 꼭 필요한 경우에만 admin 키를 쓰고,
  유출되지 않도록 특히 엄격하게 관리해야 합니다.


한눈에 보는 요약
----------------

  버킷 용량        60개 (한 번에 몰아서 보낼 수 있는 최대 요청 수)
  리필 속도        초당 1개 (유지 가능한 평균 요청 속도)
  집계 단위        API 키 단위. IP 주소 단위가 아님
  초과 시 응답     HTTP 429
  재시도 안내      Retry-After 헤더, 초 단위 정수
  예외             admin 스코프 키는 제한 대상에서 제외


클라이언트 구현 체크리스트
--------------------------

  1) 평균 호출 속도를 초당 1건 이하로 설계했는가
  2) 몰아서 보내는 구간이 60건을 넘지 않는가
  3) 429를 재시도 가능한 오류로 분류했는가
  4) Retry-After 값을 읽어서 그 시간만큼 기다리는가 (초 단위로 해석)
  5) 재시도 횟수 상한과 지터를 넣었는가
  6) 같은 API 키를 여러 인스턴스가 공유하고 있음을 감안했는가
  7) 테스트를 admin 키가 아닌 일반 키로 했는가
