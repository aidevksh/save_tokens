요청 제한(rate limit) 동작 명세 안내

이 문서는 우리 서비스의 요청 제한 동작을 처음 접하는 백엔드 개발자를 위한 설명입니다.
전체적으로 "토큰 버킷(token bucket)" 방식을 사용합니다. 요청을 보낼 때마다 바구니에서
토큰 1개를 꺼내 쓰고, 토큰이 비면 요청이 거절됩니다. 바구니는 시간이 지나면서 다시 채워집니다.


1. 버킷 용량: 60

바구니에 담길 수 있는 토큰의 최대 개수가 60개입니다. 요청 1건당 토큰 1개를 소비하므로,
바구니가 가득 찬 상태라면 한꺼번에 최대 60건의 요청을 연달아 보낼 수 있습니다.
이것이 순간적으로 몰아 쓸 수 있는 양(버스트 허용량)입니다. 60개를 다 쓰면 바구니가 비고,
다시 채워지기를 기다려야 합니다. 채워지는 양이 60개를 넘지는 않습니다 — 오래 쉬었다고
해서 100개, 200개가 쌓이지는 않고 60개에서 멈춥니다.


2. 리필 속도: 초당 1개

바구니는 1초에 토큰 1개씩 다시 채워집니다. 따라서 장기적으로 보면 평균 초당 1건이
지속 가능한 요청 속도입니다.

- 60건을 한 번에 다 쓴 직후에는 1초를 기다려야 다음 1건을 보낼 수 있습니다.
- 10초를 쉬면 토큰 10개가 회복되어 10건을 다시 몰아 보낼 수 있습니다.
- 빈 바구니가 완전히 다시 차기까지는 60초가 걸립니다.

정리하면 이 설정은 "평소에는 초당 1건, 다만 짧은 순간에는 60건까지 몰아쓰기 허용"이라는
의미입니다.


3. 집계 단위: API 키 (IP 주소가 아님)

바구니는 API 키마다 하나씩 따로 있습니다. IP 주소 기준이 아니라는 점이 중요합니다.

- 같은 API 키를 서버 여러 대에서, 서로 다른 IP에서 사용하더라도 바구니는 하나입니다.
  즉 모든 서버가 같은 60개를 나눠 씁니다. 인스턴스를 늘려도 총 허용량은 늘지 않습니다.
- 반대로 같은 IP(예: 같은 사무실, 같은 NAT 뒤)에서 서로 다른 API 키로 요청하면
  각 키가 독립적인 바구니를 갖습니다. 다른 팀이 많이 썼다고 내 키가 막히지는 않습니다.

그러므로 여러 워커가 하나의 키를 공유하는 구조라면, 워커들이 합쳐서 초당 1건을 넘지 않도록
전체 호출량을 조절해야 합니다. 부하가 커질 것으로 예상되면 키를 분리하는 것을 고려하세요.


4. 초과 시 상태 코드: 429

토큰이 없는 상태에서 요청이 들어오면 서버는 HTTP 상태 코드 429(Too Many Requests)를
반환합니다. 이는 요청 자체가 잘못되었다는 뜻이 아니고, "지금은 너무 빠르니 잠시 뒤에
다시 보내라"는 뜻입니다.

클라이언트를 만들 때는 429를 4xx 계열의 일반적인 오류(예: 400 잘못된 요청)와 다르게
처리해야 합니다. 400은 요청을 고쳐야 하지만, 429는 요청을 그대로 두고 시간만 늦춰
다시 보내면 됩니다. 429를 영구 실패로 간주해 작업을 버리지 마세요.


5. 재시도 안내 헤더: Retry-After (초 단위 정수)

429 응답에는 `Retry-After` 헤더가 함께 들어옵니다. 값은 초 단위 정수이며,
"이만큼 기다린 뒤에 다시 보내라"는 뜻입니다. 예를 들어

    HTTP/1.1 429 Too Many Requests
    Retry-After: 3

는 3초 후에 재시도하라는 의미입니다.

재시도 로직을 직접 만들 때는 임의로 정한 대기 시간을 쓰지 말고 이 헤더 값을 그대로
따르는 것이 좋습니다. 헤더를 무시하고 즉시 재시도하면 다시 429를 받게 되고, 서버에
불필요한 부하만 더합니다. 여러 클라이언트가 동시에 같은 시각에 재시도해 부하가 몰리는
것을 막기 위해, 헤더 값에 약간의 무작위 지연(지터)을 더하는 방식도 흔히 쓰입니다.


6. 예외: admin 스코프 키는 제한에서 제외

`admin` 스코프를 가진 API 키는 요청 제한을 적용받지 않습니다. 토큰을 소비하지 않으며
429도 받지 않습니다. 운영·관리 작업이 제한 때문에 막히지 않도록 하기 위한 예외입니다.

주의할 점이 있습니다.

- 개발 중에 admin 키로 테스트하면 제한 동작을 전혀 겪지 않아, 일반 키로 배포한 뒤에야
  429를 처음 만나게 됩니다. 재시도 로직을 검증할 때는 반드시 일반 키로 확인하세요.
- 제한을 피하려고 일반 용도의 호출에 admin 키를 쓰는 것은 올바른 해결책이 아닙니다.
  보호 장치가 사라지고 권한도 과도해집니다. 처리량이 부족하다면 호출 빈도를 조절하거나
  한도 상향을 요청하는 쪽으로 해결하세요.


요약

| 항목 | 값 | 실무상 의미 |
|---|---|---|
| 버킷 용량 | 60 | 한 번에 최대 60건까지 몰아쓰기 가능 |
| 리필 속도 | 초당 1개 | 지속 가능한 평균 속도는 초당 1건 |
| 집계 단위 | API 키 | IP가 아니라 키 단위. 서버를 늘려도 한도는 그대로 |
| 초과 시 상태 코드 | 429 | 영구 실패가 아닌 "잠시 후 재시도" 신호 |
| 재시도 안내 헤더 | Retry-After (초, 정수) | 이 값만큼 기다린 뒤 재시도 |
| 예외 | admin 스코프 키 | 제한 미적용. 테스트·운영 시 주의 |
