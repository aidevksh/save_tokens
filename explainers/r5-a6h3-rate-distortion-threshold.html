열 번의 2차 시행 전부 최종 파일이 기대 결과와 바이트 단위로 일치했습니다. 압축을 91.2%까지 밀어도 정보가 소실되지 않았다는 뜻입니다.

라운드 2가 찾은 '문턱'은 정보가 아니라 도구의 성질이었습니다

이 저장소는 앞서 "컨텍스트를 0줄로 줄이면 git apply 가 100% 거부한다"를 관측했고, 그걸 압축의 한계로 기록해 뒀습니다. 이번 1차 에이전트 두 곳도 직접 시험해 같은 결과를 보고했습니다 — --unidiff-zero 플래그 없이는 적용되지 않습니다.

그런데 똑같은 파일을 사람이나 에이전트가 받으면 문제없이 적용합니다. git apply 가 거부하는 이유는 정보가 없어서가 아니라, 위치를 검증할 근거가 없을 때 오적용을 막으려는 안전장치이기 때문입니다.

즉 왜곡은 압축률의 함수가 아니라 받는 쪽이 누구인가의 함수입니다. 받는 쪽이 에이전트라면 git apply 가 요구하는 컨텍스트 줄은 낼 필요 없는 잉여입니다 — 823자 대신 217자로 같은 일을 합니다.

가설이 예측한 급락 지점을 못 찾았습니다

세운 가설은 "압축을 올리면 어느 지점까지 품질이 평평하다가 문턱에서 급락한다"였습니다. 급락 지점을 찾으려면 깨지는 데까지 밀어야 하는데, 준비한 다섯 단계가 전부 안 깨졌습니다.

사전에 정해둔 기각 조건이 "전 구간 왜곡 0이면 이 범위에서 문턱 미관측"이었으므로 기각으로 판정합니다. "문턱이 없다"가 아니라 "여기까지는 없더라" 입니다.

다음에는 압축을 더 밀어야 합니다 — 예를 들어 줄 번호도 빼고 "복제본 수를 6으로, 환경을 production 으로…"라고만 쓰면 어디선가 반드시 깨집니다.

이 결과로 git apply 파이프라인을 바꾸지 마세요

받는 쪽이 스크립트나 CI 라면 라운드 2 결론이 그대로 유효합니다. 컨텍스트 0줄 diff는 표준 옵션으로 거부됩니다.

이 실험이 말하는 것은 소비자가 에이전트일 때 컨텍스트 줄이 낭비라는 것뿐입니다. 두 경우를 섞지 마세요.

수치는 전부 글자 수이며 토큰이 아닙니다. 그리고 이 결과는 변경 6곳·파일 120줄이라는 형상 하나에서 나왔습니다.
