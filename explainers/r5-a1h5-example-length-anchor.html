요청 제한 정책은 다음과 같다. 버킷 용량은 60이다. 즉 한 번에 최대 60개의 요청을 몰아서 보낼 수 있다.
리필 속도는 초당 1개다. 요청을 쓰면 버킷이 줄고, 1초에 하나씩 다시 채워진다. 최대치는 60을 넘지 않는다.
집계 단위는 API 키다. IP 주소가 아니므로 같은 서버에서 서로 다른 키로 보내면 각각 따로 집계된다.
버킷이 비었을 때 들어온 요청은 429 상태 코드로 거절된다.
거절 응답에는 Retry-After 헤더가 붙는다. 값은 초 단위 정수이며, 그 시간만큼 기다렸다가 다시 보내면 된다.
예외로 admin 스코프 키는 제한에서 제외된다. 이 키는 버킷을 소모하지 않고 429도 받지 않는다.

말로 시키는 것보다 보여주는 편이 셌습니다

같은 과제에서 48자짜리 간결성 지시("핵심만 간결히 쓰세요…")를 붙였을 때가 −69.3% 였습니다. 여기서는 148자짜리 예시 하나가 −82.7% 를 냈습니다.

지시문은 "얼마나 짧게"를 말로 전달합니다. 예시는 길이 자체를 그대로 보여줍니다. 모델은 눈앞의 형태를 따라가는 쪽이 더 정확합니다 — 문체, 절 구조, 그리고 분량까지 함께 옮겨왔습니다.

품질은 떨어지지 않았습니다. 요구한 6개 항목이 세 조건 모두 만점입니다. 419자 안에 6항목이 전부 들어갑니다.

'좋은 예시'를 붙이면 답이 길어집니다

예시를 고를 때 보통 잘 쓴 문서를 고릅니다. 잘 쓴 문서는 대개 깁니다. 그러면 산출물도 그만큼 길어집니다 — 이 실험에서 805자 예시가 1,810자짜리 답을 끌어냈습니다.

프롬프트에 붙이는 예시는 원하는 품질이 아니라 원하는 분량으로 써야 합니다. 예시가 곧 길이 지시입니다.

다만 예시 길이와 예시 구조를 분리하지 못했습니다. 긴 예시에는 제목과 번호 절이 함께 들어갔고 산출물도 그 구조를 따라했습니다. 순수한 길이 효과만 떼어내려면 구조를 고정한 대조군이 필요합니다.

2.2~2.8배는 법칙이 아니라 관측입니다

재료 하나, 길이 두 점에서 나온 값입니다. 예시 길이 3~4점을 찍어야 비례 관계인지 확인할 수 있습니다.

수치는 전부 글자 수이며 토큰이 아닙니다. 이 환경에는 API 키가 없어 실제 토큰을 셀 수 없습니다.

기준선(X0)도 이미 오염돼 있습니다. 답하는 쪽이 프로젝트 설정의 "결론부터, 서론 금지" 규칙을 물고 시작하므로 −82.7%는 하한입니다.
