조건 B
아무 말도 안 함
(간결성에 관한 문장 없음)
나온 답2,425자 평균
요청 제한(Rate Limit) 동작 안내 — 신입 백엔드 개발자용

우리 서비스는 "토큰 버킷(token bucket)" 방식으로 요청 수를 제한합니다.
물이 담긴 물통을 떠올리면 됩니다. 요청 한 번에 물 한 컵을 쓰고, 물은 일정 속도로 다시 채워집니다.
물통이 비면 더 이상 요청을 받지 않습니다.

1) 버킷 용량 = 60
   물통에 담기는 최대치가 60개입니다. 요청 1건이 1개를 씁니다.
   가득 찬 상태에서는 한 번에 60건까지 연달아 보낼 수 있습니다(순간 폭주 허용량, burst).
   용량을 넘겨 미리 쌓아둘 수는 없습니다. 아무리 오래 쉬어도 최대 60개까지만 회복됩니다.

2) 리필 속도 = 초당 1개
   쓴 만큼은 1초에 1개씩 다시 채워집니다.
   따라서 장기 평균 처리량은 초당 1건입니다. 60건을 몰아 쓰고 나면
   그 뒤로는 1초에 1건 페이스로만 통과합니다. 완전히 비운 물통이 다시 꽉 차려면 60초가 걸립니다.
   요약: 짧게는 60건까지 몰아쓰기 가능, 길게 보면 초당 1건.
↑ 여기까지가 전체의 4분의 1입니다. 실제로는 57~102줄이 나왔고, 항목마다 “실무 함의”와 마지막 요약표가 붙었습니다. (지면상 앞부분만 잘라 실었습니다)
조건 N
금지형으로 시킴
“장황하게 쓰지 마세요. 서론과 맺음말을 넣지 마세요. 같은 내용을 두 번 쓰지 마세요.”
나온 답914자 평균
요청 제한(Rate Limit) 동작 설명

방식: 토큰 버킷. 요청 1건이 토큰 1개를 소모하고, 토큰이 없으면 거절된다.

1) 버킷 용량 = 60
   버킷에 최대 60개까지 토큰이 쌓인다. 즉 한동안 요청이 없었다면 순간적으로 60건까지 연속 처리된다(버스트 허용량).

2) 리필 속도 = 초당 1개
   토큰이 1초에 1개씩 다시 채워진다. 따라서 지속 가능한 평균 속도는 초당 1건이고, 빈 버킷이 다 차기까지는 60초가 걸린다.

3) 집계 단위 = API 키
   버킷은 API 키마다 하나씩 존재한다. IP 주소 기준이 아니므로, 같은 IP에서 서로 다른 키로 호출하면 한도를 따로 쓰고, 반대로 여러 서버·여러 IP에서 같은 키를 쓰면 하나의 한도를 나눠 쓴다.

4) 초과 시 상태 코드 = 429
   토큰이 없는 상태에서 들어온 요청은 처리되지 않고 HTTP 429(Too Many Requests)로 응답한다.

5) 재시도 안내 헤더 = Retry-After
   429 응답에는 Retry-After 헤더가 붙고, 값은 초 단위 정수다. 예: `Retry-After: 5` → 5초 후 재시도.

6) 예외 = admin 스코프 키
   admin 스코프를 가진 키는 제한 대상에서 제외되어 버킷 검사를 거치지 않는다.
↑ 이건 잘리지 않은 전문입니다. 6개 항목이 다 있고, 물통 비유와 실무 함의만 사라졌습니다.
조건 P
지시형으로 시킴
“핵심만 간결히 쓰세요. 본문부터 시작해 본문으로 끝내세요. 각 내용은 한 번만 쓰세요.”
나온 답743자 평균
요청 제한은 토큰 버킷 방식으로 동작한다. 각 요청은 버킷에서 토큰 1개를 소비하고, 토큰이 없으면 거절된다.

버킷 용량은 60이다. 토큰이 가득 찬 상태라면 60개 요청을 연속으로 보낼 수 있다. 이것이 순간 최대 허용량(burst)이다.

리필 속도는 초당 1개다. 소비된 토큰은 초당 1개씩 다시 채워지며 용량 60을 넘지 않는다. 따라서 장기 평균 허용량은 초당 1요청이고, 비어 있는 버킷이 다시 가득 차려면 60초가 걸린다.

집계 단위는 API 키다. IP 주소가 아니므로 같은 서버에서 서로 다른 키로 보낸 요청은 각각 별도 버킷을 쓴다. 반대로 여러 대의 서버가 같은 키를 공유하면 버킷 하나를 함께 소비하므로, 인스턴스를 늘려도 총 허용량은 늘지 않는다.

제한을 초과하면 상태 코드 429를 반환한다. 클라이언트는 이를 영구적 실패가 아니라 잠시 후 재시도해야 하는 신호로 처리한다.

429 응답에는 Retry-After 헤더가 함께 온다. 값은 초 단위 정수이며, 토큰이 다시 생길 때까지 기다려야 하는 시간이다. 재시도는 이 시간만큼 대기한 뒤에 보낸다. 임의로 즉시 재시도하면 429가 반복될 뿐이다.

예외로 admin 스코프를 가진 키는 제한에서 제외된다. 이 키는 버킷을 소비하지 않고 429도 받지 않으므로 운영·점검 용도로만 쓰고 일반 트래픽 경로에는 사용하지 않는다.
↑ 이것도 전문입니다. 번호와 제목까지 사라지고 문단 7개만 남았습니다. 그런데도 6개 항목은 전부 있습니다.

세 조건 모두 요구한 6개 항목을 전부 설명했습니다(커버리지 6.0/6.0 만점). 길이가 3배 넘게 차이나는데 담긴 정보는 같았습니다. 9시행 전부 품질 검사 통과, 무효 0건. 지시문 두 개는 길이가 정확히 48자로 같습니다 — 프롬프트를 더 길게 써서 얻은 결과가 아닙니다.

왜 그냥 놔두면 3배가 되나

아무 말도 안 한 조건이 길어진 이유는 틀린 걸 쓴 게 아니라 안 물어본 걸 쓴 것입니다. 물통 비유로 개념 설명을 하고, 항목마다 “실무에서 이게 왜 중요한가”를 덧붙이고, 마지막에 요약표와 구현 체크리스트를 붙였습니다. 전부 친절하고 전부 맞는 내용입니다. 그리고 전부 요청에 없던 것입니다.

짧게 쓰라고 한 조건이 지운 것도 정확히 그 부분입니다. 요구한 6개 항목은 세 조건 모두 6/6으로 살아남았습니다. 즉 이 지시는 내용을 깎지 않고 덧붙임만 깎았습니다.

지시형이 금지형보다 더 짧게 나온 이유는 이 실험이 답하지 않습니다. 다만 금지형은 “무엇을 하지 말지”만 말하고 지시형은 “대신 무엇을 할지”까지 말한다는 차이는 있습니다. 금지형 조건의 답은 번호 붙인 항목 구조를 유지했고, 지시형 조건은 문단만 남겼습니다.

⚠ 이 숫자를 토큰 절감률로 읽으면 안 됩니다

여기 나오는 모든 수치는 글자 수입니다. 요금이 매겨지는 단위인 토큰이 아닙니다. 이 환경에는 토큰을 세는 수단(API 키)이 없어서 글자 수를 대신 썼습니다. 글자와 토큰의 비율은 언어와 기호 구성에 따라 흔들리므로, −69.3%는 토큰 절감률의 상한으로 읽어야 합니다.

특히 금지형 대비 지시형의 −18.7%는 방향만 믿을 수치입니다. 이유 두 가지입니다. 첫째, 3회씩 돌린 결과의 분포가 겹칩니다 — 지시형 한 시행(899자)이 금지형 두 시행(723자, 876자)보다 길었습니다. 둘째, 금지형 답에 영문이 조금 더 많은데(한글 비율 0.83 대 0.88) 영문은 한글보다 글자당 토큰이 적어서, 글자로 재면 금지형이 실제보다 불리하게 나옵니다.

반면 아무 말 안 함 대비 −62%/−69%는 이런 차이로 뒤집히는 규모가 아닙니다.

⚠ 기준선이 이미 “짧게 쓰는 중”이었습니다

“아무 말도 안 함” 조건은 사실 완전한 무처치가 아닙니다. 이 실험을 돌린 저장소에는 “결론부터 쓰고 서론·자평을 금지한다”는 규칙이 프로젝트 설정에 들어 있고, 그 규칙이 실험 대상 에이전트에게도 상수로 걸립니다.

즉 기준선은 이미 억제가 일부 걸린 상태입니다. 아무 규칙도 없는 맨 상태와 비교하면 절감폭은 −69.3%보다 더 클 가능성이 높습니다. 이 숫자는 하한입니다.

정확한 값은 시스템 프롬프트를 통째로 통제할 수 있어야 잴 수 있고, 그건 API 키가 있어야 가능합니다.

품질 검사가 놓친 것

품질 검사는 6개 항목이 들어 있는지만 정규식으로 확인했습니다. 서술이 앞뒤가 맞는지는 보지 않았습니다.

같은 라운드의 다른 조건에서 “버킷은 사용자마다 하나”라고 써서 “API 키마다 하나”라는 다른 절과 어긋난 사례가 실제로 있었습니다. 이 검사로는 잡히지 않는 종류의 오류입니다.

따라서 간결성 지시가 서술 정합성을 해쳤는지 여부는 이 실험이 답하지 못합니다. 다음 라운드에 정합성 게이트를 추가합니다.
