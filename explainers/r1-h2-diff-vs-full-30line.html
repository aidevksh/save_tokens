바뀐 데만 썼는데 더 길다

“파일 전체를 다시 쓰지 말고 바뀐 데만 내놔라”는 코딩 에이전트계의 통념입니다. 30줄 파일에서 그게 거짓이었습니다. 바뀐 데만 쓴 쪽이 더 길었습니다.

시킨 일 — 30줄짜리 설정 파일 deploy.yaml에서 6곳을 고치기. 고칠 곳은 replicas, env, logging.level, logging.format, autoscale.enabled, database.ssl.

기준 (비교 대상) 짧아짐 = 이득 길어짐 = 손해모든 수치는 문자 수 (토큰 아님)
1

입력 — 모든 조건에 똑같이 준 것

30줄 파일 전문과 고칠 곳 6군데를 양쪽에 똑같이 줬습니다.

프롬프트 (공통 부분)
## 변경 요청 (6곳)

1. `replicas` 를 3에서 6으로 변경
2. `env` 를 `staging` 에서 `production` 으로 변경
3. `logging.level` 을 `debug` 에서 `info` 로 변경
4. `logging.format` 을 `text` 에서 `json` 으로 변경
5. `autoscale.enabled` 를 `false` 에서 `true` 로 변경
6. `database.ssl` 을 `false` 에서 `true` 로 변경

품질은 완벽했습니다. 조건 B의 4/4가 표준 git apply -p1로 붙었고, 고친 결과 파일이 정답과 한 글자도 다르지 않았습니다. 무효 0건. 품질이 아니라 길이에서 졌습니다.

왜 더 길어졌나

고친 6줄을 표시하려면 diff는 삭제줄 6개 + 추가줄 6개 = 12줄을 씁니다. 원본의 2배입니다.

거기에 위치 표지가 붙습니다. 덩어리 3개 × 위아래 3줄씩 = 표지만 18줄. 30줄짜리 파일에서 18줄이면 원본의 6할을 다시 실어 나르는 셈입니다.

12 + 18 + 덩어리 머리글 3줄 + 파일 이름 2줄 = 35줄. 원본 30줄보다 많습니다. 애초에 이길 수가 없는 구조였습니다.

그래서 경계선이 있습니다

위 계산을 일반화하면 고친 줄 × 2 + 표지 줄 + 덩어리 수 + 2가 diff의 길이입니다. 이게 원본 줄 수보다 작아야 이깁니다.

표지 3줄 기준으로 계산하면 경계선은 약 40줄입니다. 40줄보다 짧은 파일은 그냥 전체를 다시 쓰는 게 짧고, 그보다 길면 diff가 이깁니다.

이 예측은 라운드 2에서 실제로 검증됐습니다. 같은 6곳 수정을 120줄 파일에 했더니 부호가 뒤집혀 −66.7%가 나왔습니다.

⚠ 이 기각을 “diff는 나쁘다”로 읽으면 안 됩니다

이 실험이 보인 것은 “30줄에서 졌다”이지 “diff가 나쁘다”가 아닙니다. 라운드 2가 파일 길이를 120줄로 늘리자 같은 diff가 −66.7%로 이겼습니다.

라운드 2 이후 이 가설은 조건부 채택으로 정정됐습니다 — “변경분만 출력하라”가 아니라 “파일이 경계선보다 길 때만 변경분만 출력하라”입니다.

정리

그래서 언제 이렇게 시키나

이런 걸 뱉을 때이렇게 시킨다결과
짧은 파일 고치기 — 대략 40줄 미만그냥 파일 전체를 다시 쓰게 둔다diff를 쓰면 +26.3% 역효과
긴 파일 고치기 — 대략 40줄 초과“unified diff로”라운드 2에서 −66.7% 확인
변경이 파일 전체에 흩어져 있음덩어리 수가 늘어 경계선이 올라갑니다. 다시 계산해야 합니다판단 필요
실험 방식 — 판정 기준을 데이터 보기 전에 고정했고, 실험을 수행한 에이전트에게는 이것이 무엇을 재는 실험인지 알려주지 않았습니다.
시행 — 조건당 4회, 총 8회. 전부 품질 게이트 통과, 무효 0건. 조건 B는 기계 적용(git apply)과 결과 파일 완전 일치까지 검사했습니다.
단위 — 문자 수 (proxy). 원 보고서는 공백 제외 문자 기준 +22.3%로 적혀 있고, 이 문서는 원시 문자 기준 +26.3%로 통일했습니다.
