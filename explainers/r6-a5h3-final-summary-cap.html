보고는 세 줄로

코딩 작업을 시키면서 "마지막 보고는 세 줄 이내로"를 한 줄 넣었습니다. 대화 보고문이 −48.6%, 코드는 그대로, 총합이 −17.4%. 테스트는 양쪽 다 9/9 통과입니다. 이 저장소에서 총량을 실제로 줄인 첫 억제 지시입니다.

시킨 일 — 할 일 목록 모듈에 complete() 함수를 추가하고 list() 에 상태 필터를 넣어 테스트 9개를 모두 통과시키게 했습니다. 시작 시점에 5개가 실패합니다. 조건마다 3회씩 돌렸습니다.

기준 (비교 대상) 짧아짐 = 이득 길어짐 = 손해모든 수치는 문자 수 (토큰 아님)

이 저장소에서 '재배분 함정'을 처음 뚫었습니다

앞선 두 라운드에서 비슷한 시도가 두 번 실패했습니다. "자기검증 지시를 빼라"(라운드 3)와 "입력에 있는 건 다시 쓰지 마라"(라운드 4)는 둘 다 한쪽에서 아낀 만큼 다른 쪽이 늘어 총합이 동률이었습니다.

이번엔 코드 쪽이 3자 움직였습니다. 사실상 0입니다. 총합이 실제로 −17.4% 줄었습니다.

차이는 처치의 종류에 있습니다. 실패한 둘은 "무엇을 쓰지 말라"(내용 규칙)였고, 이번 것은 "몇 줄로 쓰라"(분량 규칙)입니다. 라운드 4·5에서도 총량을 줄인 것은 전부 분량을 직접 지시했거나 형식을 바꾼 지시였습니다.

품질이 떨어지지 않은 것은 '보고문'에 한해서입니다

테스트는 두 조건 다 9/9 통과했습니다. 세 줄로 줄여도 일 자체는 똑같이 해냈습니다.

다만 이 실험이 잰 품질은 테스트 통과뿐입니다. 짧은 보고가 사람이 코드 리뷰를 할 때 충분한지, 나중에 이력을 되짚을 때 부족하지 않은지는 재지 않았습니다.

받는 쪽이 사람이고 그 보고가 유일한 기록이라면 세 줄이 너무 짧을 수 있습니다. 보고가 로그가 아니라 인수인계일 때는 다시 생각하십시오.

−17.4%를 토큰 절감률로 읽지 마세요

수치는 전부 글자 수입니다. 이 환경에는 API 키가 없어 실제 토큰을 셀 수 없습니다.

코드 변경분은 파일에 남은 것만 셉니다. 파일을 읽고 고치는 도구 호출 자체의 분량은 계측 밖이라, 실제 총출력에서 보고문이 차지하는 비중은 여기 계산보다 작습니다.

기준선도 이미 오염돼 있습니다. 답하는 쪽이 프로젝트 설정의 "결론부터, 서론 금지" 규칙을 물고 시작하므로 −48.6%는 하한입니다.
